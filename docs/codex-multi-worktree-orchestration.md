# Codex 多任务 Worktree 编排手册

更新日期：2026-09-15
适用范围：Orbit 及其他需要多条开发线并行、长期执行、独立提交和集中验收的 Git 项目。

## 1. 方法概述

这套方法使用一个“总控任务”协调多个“执行任务”。每个执行任务通常绑定自己的 Git Worktree，在独立 checkout 中开发、测试和提交；总控任务负责派发、跟踪、风险控制、收集 commit SHA、集成和全量验收。

```text
总控任务
│
├── A 线任务 ── A Worktree ── 独立提交
├── B 线任务 ── B Worktree ── 独立提交
├── C 线任务 ── C Worktree ── 独立提交
├── D 线任务 ── D Worktree ── 独立提交
└── E 线任务 ── E Worktree ── 独立提交
          │
          ▼
   总控收集 SHA、审查与排序
          │
          ▼
      集成到目标分支
          │
          ▼
   Web + App + 数据流全量验证
```

它的核心不是“让多个模型同时写代码”，而是同时建立四种隔离：

1. **目标隔离**：每条线有明确 Sprint、验收条件和停止条件。
2. **上下文隔离**：每个任务保留自己的对话历史和执行记录。
3. **文件隔离**：每条线通常在独立 Worktree 中工作。
4. **集成隔离**：Worker 只产出可审阅 commit，由总控或集成线决定何时进入目标分支。

## 2. 核心角色

### 2.1 总控任务（Coordinator）

总控任务不应成为所有代码的主要编辑者。它主要负责：

- 把产品需求转成 Sprint 和可验证的成功条件；
- 根据依赖关系拆分 A/B/C/D/E 线；
- 查找已有任务，读取其状态并发送后续任务；
- 维护文件所有权、契约依赖和合并顺序；
- 等待状态变化，处理真实阻塞；
- 收集 commit SHA、测试证据和运行时证据；
- 在所有线完成后进行集成与全量验证。

### 2.2 执行任务（Worker）

每个 Worker 负责一个边界清晰的结果，例如一个 Sprint、一个平台、一个领域模块或一种验证工作。Worker 应当：

- 开始前检查自己的 `HEAD`、分支和 `git status`；
- 阅读固定版本的规格和相关代码；
- 不覆盖或隐藏其他人的未提交改动；
- 按项目要求执行影响分析和 TDD；
- 在自己的 Worktree 中形成独立 commit；
- 返回 SHA、文件清单、RED→GREEN 证据、测试结果和剩余阻塞；
- 未经授权不自行合并、推送或部署。

### 2.3 集成者（Integrator）

集成者可以是总控任务，也可以是单独的集成任务。职责包括：

- 复核各 Worker 的基线和依赖；
- 按依赖顺序 cherry-pick 或 merge；
- 解决冲突，但不覆盖未归属的改动；
- 重新构建所有受影响的运行环境；
- 运行定向测试、跨端测试和全量测试；
- 将未满足的真实设备、账号、provider 或部署证据保留为明确阻塞。

## 3. Task、Worktree、Fork、Handoff 和 Subagent 的区别

| 机制 | 生命周期 | 文件环境 | 适合场景 | 不适合场景 |
|---|---|---|---|---|
| 独立任务 + Worktree | 长期、可反复继续 | 独立 Git checkout | Sprint、平台开发线、数小时或数天工作 | 大量修改同一批文件且没有所有权边界 |
| 向已有任务发送消息 | 延续已有任务 | 保留该任务原环境 | 给 B/C/D 线派发下一项 Sprint | 需要新的隔离基线或完全不同职责 |
| Fork 当前任务 | 新任务继承当前已完成历史 | 可选同目录或新 Worktree | 新工作高度依赖当前上下文 | 只为传达一份规格；此时明确交接更可靠 |
| Handoff | 同一个任务在 Local 与 Worktree 间移动 | 移动其关联 checkout | 回到日常 IDE、使用唯一设备或服务 | 创建新的并行执行线 |
| Subagent | 当前任务内的临时子线程 | 由当前运行环境管理 | 并行调查、测试、审查、总结 | 长期独立产品线和高冲突写入 |

官方 OpenAI 文档说明，Worktree 是同一 Git 仓库的第二份 checkout；各 Worktree 拥有自己的文件副本，但共享 commit 和分支等 Git 元数据，因此可以安全地并行工作。Handoff 的作用是把同一个任务及其代码在 Local 和 Worktree 之间移动，而不是复制一个新任务。

Subagent 是另一层机制：主 Agent 为边界明确的子问题创建临时 Agent 线程，等待它们完成并汇总结果。它尤其适合探索、测试、日志分析和多角度审查；多个 Subagent 同时写相同代码会增加冲突和协调成本。

## 4. 总控任务的控制循环

在当前桌面环境里，总控使用四类任务操作完成协调。下面是概念名称，不应当视为稳定的公共 CLI/API：

```text
发现：list tasks/threads
  ↓
核对：read task status and recent history
  ↓
派发：send a user-visible follow-up message
  ↓
等待：wait until active/completed/needs-attention
  ↓
回收：read result, commits, tests and blockers
  ↓
集成：review → merge/cherry-pick → full verification
```

刚才向 B 线交接 Sprint 0029 的实际流程就是：

1. 总控列出项目任务并定位 B 线；
2. 读取 B 线最近记录，确认上一个目标已收口、工作树可继续使用；
3. 发送一条完整的新任务消息，其中包含固定规格 commit、文档路径、执行顺序、安全边界和验收要求；
4. 等待 B 线由 `idle` 变为 `active`；
5. 后续继续等待它返回 commit SHA 和证据。

任务之间不会自动共享全部对话上下文。因此，派发消息必须是一个自足的执行包，不能只写“继续做刚才那个”。

## 5. 什么时候应该并行

满足以下条件时适合并行：

- 两项工作没有顺序依赖；
- 文件所有权基本不重叠；
- 各项都有独立成功条件；
- 测试和运行环境可以隔离；
- 任一执行线失败不会让其他线的结果失效。

以下情况应串行：

- B 的输入契约必须由 A 先冻结；
- 两条线会同时修改相同核心 service、schema 或导航文件；
- 只有一个 Simulator、数据库迁移环境或生产服务实例；
- 第二项工作的正确设计取决于第一项调查结果；
- 最终集成必须在所有功能提交之后进行。

建议优先并行读密集型任务，例如代码调查、影响分析、测试、审查和证据整理；写密集型任务必须先划定文件边界。

## 6. 标准执行流程

### 阶段 0：建立基线

总控记录：

- 目标集成分支和基线 SHA；
- 当前未提交改动及其所有者；
- 可用 Worktree 和任务；
- 唯一资源，例如 Web 端口、数据库、Simulator、真实测试账号；
- 已批准和未批准的操作，例如提交、合并、推送、部署和迁移。

### 阶段 1：拆分开发线

每条线至少定义：

| 字段 | 内容 |
|---|---|
| 目标 | 单一、可验证的产品结果 |
| 输入 | 固定规格版本、依赖 commit、设计稿 |
| 文件边界 | 独占文件、共享文件、禁止提前修改的文件 |
| 成功条件 | 功能、测试、运行时证据 |
| 输出 | commit SHA、文件清单、测试和阻塞 |
| 集成顺序 | 可并行、依赖谁、应当在谁之前合并 |

### 阶段 2：创建或复用任务

- 已有稳定职责和历史上下文时，复用现有 A/B/C/D/E 任务；
- 需要全新职责或新基线时，创建新的 Worktree 任务；
- 新 Worktree 应从明确分支或 SHA 开始；
- 不要让两个 Worktree checkout 同一个可变分支；
- 需要长期保存时使用分支或永久 Worktree；临时 Worktree 仍应在交付前提交。

### 阶段 3：发送自足交接包

交接必须包含：

1. 要做什么以及明确不做什么；
2. 固定规格文件和 commit；
3. 开始前的只读检查；
4. 文件边界和已知并行开发线；
5. 实现顺序和依赖；
6. TDD、影响分析和安全要求；
7. Web/App/数据库/provider 的运行时验收；
8. 提交、合并、推送、部署权限；
9. 阻塞时继续其他独立工作的规则；
10. 最终必须返回的证据格式。

### 阶段 4：等待事件，不进行高频轮询

总控应等待以下有意义的状态变化：

- Worker 开始运行；
- Worker 请求必要决定；
- Worker 完成一个提交；
- Worker 失败或发现高风险影响；
- Worker 完成目标。

状态没有变化时不需要反复发送“怎么样了”。对于用户明确要求的长期监控，可以使用计划任务或 heartbeat；其提示词应要求“无变化时保持安静，只在完成、失败、需要决定或发现风险时通知”。

### 阶段 5：Worker 交付

Worker 最终至少交付：

- 基线 SHA 和最终 SHA；
- commit 列表及顺序；
- 新增、修改、删除文件；
- 影响面和高风险项；
- RED 测试及失败原因；
- GREEN 测试及结果；
- 定向测试、类型检查、全量测试；
- Web 构建、重启、健康检查和浏览器证据；
- App 构建、Simulator/设备和真实账号证据；
- 数据库、provider、推送、跨端证据；
- 未完成项及其具体阻塞；
- 是否已经推送、部署或合并。

### 阶段 6：集中集成

集成者按以下顺序处理：

1. 检查目标分支未提交改动；
2. 检查每个 Worker commit 的父提交和依赖；
3. 先合并契约/数据权威，再合并消费者；
4. 每次集成后运行受影响的定向测试；
5. 所有提交进入后重新构建 Web；
6. 停止旧 Web 进程并启动新产物；
7. 让 App 指向同一 API、账号和数据库；
8. 在 Simulator/设备上验证真实业务流；
9. 执行两端类型检查和全量测试；
10. 更新 Sprint、Bridge 和最终报告。

## 7. 可复制提示词

### 7.1 启动总控任务

```text
你是这个项目的总控任务。先检查现有任务、Worktree、目标分支、未提交改动和运行环境。
把需求拆成互不依赖的开发线，为每条线定义目标、输入、文件边界、成功条件、输出和集成顺序。
复用合适的现有任务，否则创建独立 Worktree 任务。发送自足的执行说明，并等待确认启动。
Worker 只形成可审阅 commit，不得未经授权合并、推送、部署或覆盖其他线改动。
所有线完成后，收集 SHA、按依赖顺序集成，并运行 Web、App、数据流和全量回归验证。
```

### 7.2 给已有 B 线派发 Sprint

```text
请找到现有 B 线任务，读取它最近的状态、HEAD 和交付记录。
确认工作树可安全继续后，把 Sprint <编号> 的固定规格、依赖 SHA、文件边界、TDD 顺序、安全要求和运行时验收条件完整发送给 B 线。
不要只发送“继续执行”。等待 B 线进入 active 后再向我报告。
```

### 7.3 Worker 执行提示词

```text
请接管并完整执行 Sprint <编号>，不要停在调查或计划。
开始前只读检查 HEAD、分支、git status、目标分支差距和并行开发线；不得覆盖、stash 或丢弃不属于你的改动。
阅读固定规格 <路径或 SHA>。按既定顺序实施，严格 RED→GREEN；修改共享符号前做影响分析，提交前检查真实 diff。
Web 有源码变化时必须重新构建、停止旧进程并启动新产物；App 必须重新构建或刷新，并使用同一 API、账号和数据库做跨端验证。
形成独立 commit，但不合并、不推送、不部署，除非明确授权。
最终返回 commit SHA、文件清单、影响面、RED→GREEN、全部测试、运行时证据和剩余阻塞。
某一项受外部条件阻塞时继续其他无依赖工作；只有全部剩余事项都确实受阻时才停止。
```

### 7.4 检查全部开发线

```text
检查 A/B/C/D/E 所有任务。对每条线列出：状态、Worktree、HEAD、未提交改动、最近完成项、当前命令、阻塞、下一步和已交付 SHA。
对于无需用户决定却意外停止的任务，发送继续执行指令；不要重复启动已经在运行的命令。
只有完成、失败、出现真实风险或必须由用户决定时才通知。
```

### 7.5 集成提示词

```text
在所有开发线完成后，先核对目标分支和每个 Worktree 的提交、未提交改动及依赖顺序。
逐个审查并集成已批准 SHA，不覆盖用户改动。每次集成后运行受影响测试。
全部集成完成后，重新生产构建并重启 Web/API，检查 health；重新构建或刷新 App，在同一真实账号、API 和数据库上完成双向验证；最后运行两端 typecheck、全量测试和数据流审查。
未满足的实体设备、provider、推送或远程部署证据必须明确保留，不能由 mock 或单元测试代替。
```

## 8. Orbit 项目的额外约束

在 Orbit 中使用本方法时，还必须遵循：

- 涉及 App 可见行为、API、共享契约或状态同步时，先读 `bridge/status.md` 和 `bridge/handoffs.md`；
- App 开发过程中 Web/API 必须实际运行；Web 源码变化后必须重新生产构建并重启；
- Web 与 App 验收使用同一 API、账号、数据库和明确版本；
- 修改 function/class/method 前执行 GitNexus upstream impact；HIGH/CRITICAL 风险先报告；
- 提交前运行 GitNexus change detection，并检查实际 staged diff；
- 功能和 bugfix 使用 TDD，保留 RED→GREEN 证据；
- 外部 provider、推送、设备和真实账号证据不可用时，只阻塞对应验收，不阻塞其他独立实现；
- 不把“本地测试通过”写成“真实跨端/provider 已验证”；
- 最终由集成者确认所有 Worktree 的成果是否都已进入 `chat-agent`。

## 9. 常见失败方式

### 9.1 交接过短

错误：

```text
去把 0029 做完。
```

Worker 不一定拥有总控的完整上下文，会重新猜测范围或读取旧规格。应当附上固定版本、边界和验收条件。

### 9.2 多条线编辑同一核心文件

结果通常是冲突、互相覆盖或集成时无法判断哪个版本正确。解决方法是指定独占文件、共享文件释放时点，以及契约先于消费者的集成顺序。

### 9.3 所有 Worker 都从不断变化的分支开始

如果基线不固定，测试结果无法比较，提交依赖也难以重放。每次交接都应记录起始 SHA 和所需前置 SHA。

### 9.4 Worker 自行合并

Worker 可能看不到其他线的最新状态。默认应只提交，由总控或专门集成线集中处理。

### 9.5 把计划、单元测试或 commit 当作完成

产品完成通常还需要 Web 重建、实际服务、App 构建、真实账号、数据库和跨端回读。证据缺失时应保留为 blocked，而不是删除验收条件。

### 9.6 Worktree 缺少环境文件

Worktree 默认从 Git checkout 开始，被忽略的 `.env`、本地配置或证书不会自动存在。Codex 管理的本地 Worktree 可通过仓库根目录的 `.worktreeinclude` 复制明确列出的 ignored 文件。只列必要路径，不要复制宽泛目录、构建缓存或未知未跟踪文件。

### 9.7 并行数量过多

更多任务不一定更快。每条任务都会消耗独立模型 token、CPU、内存、端口、数据库连接和人工审查时间。并行度应受文件冲突、唯一运行资源和集成能力限制。

## 10. 启动与收口检查清单

### 启动前

- [ ] 目标分支和基线 SHA 已记录。
- [ ] 当前未提交改动及所有者已记录。
- [ ] Sprint 规格已经批准并固定版本。
- [ ] 各开发线依赖关系已画清。
- [ ] 文件所有权和共享文件释放点已明确。
- [ ] 每条线的 Worktree 与任务已确定。
- [ ] Web 端口、数据库、Simulator 和账号没有冲突。
- [ ] 提交、合并、推送、部署和迁移授权已区分。

### 每条线交付时

- [ ] 基线和最终 SHA 清楚。
- [ ] 工作树没有未知未提交改动。
- [ ] 文件清单与授权范围一致。
- [ ] RED→GREEN 证据存在。
- [ ] 定向测试和类型检查通过。
- [ ] 运行时证据与 mock/fixture 证据明确区分。
- [ ] 阻塞绑定到具体动作和具体外部依赖。

### 最终集成后

- [ ] 所有批准 commit 已进入目标分支。
- [ ] 没有遗漏或重复合并 Worktree 成果。
- [ ] Web 已用最终源码重新构建、重启并通过 health。
- [ ] App 已用最终源码构建或刷新。
- [ ] Web/App 使用同一 API、账号和数据库完成关键双向流。
- [ ] 两端 typecheck、定向测试和全量测试已记录。
- [ ] 数据迁移、provider、推送、设备和部署状态如实记录。
- [ ] Sprint、Bridge 和最终报告与代码事实一致。
