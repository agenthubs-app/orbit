# R03 关卡 1 审校：术语表与写作规范

- **审校日期：** 2026-10-10
- **审校人：** 独立 AI 审校（日语母语产品文案角色）
- **审校对象：**
  - `glossary.md` **版本 1.1**（2026-10-10；「待办（一项）」= タスク，「To-do」只作分段名）
  - `style-guide.md` 版本 1（2026-10-10）
- **对照材料：** `research.md`（调研依据）、`PLANNER.md` B / F 节、定稿设计稿 `01-system.html`（其中的日文按已批准的标准用词对待）、`kit/kit.js`。
- **范围说明：** 导航名（ホーム / 人脈 / iOrbit / イベント / Task / 受信箱 / 主催 / 設定）和 Task 分段（カレンダー / To-do / プラン / メモ）是用户已定的决定，本审校只记录风险，不作为严重 / 中等问题。

## 结论

**有条件通过**：没有严重问题，有 **11 个中等问题**。PLANNER F 节要求关卡 1「没有严重和中等问题」才能开始批量翻译，所以**全部中等问题处理完（改正，或经产品负责人明确接受并写进处理记录）之前，不能进入批量翻译**。

总体评价：术语选择大方向正确，大部分日文自然、符合日本商务用户预期（名刺 / 予定 / 下書き / 元に戻す 与 取り消す 的分工 / 〜できませんでした 句式 / 期限超過 / サンプル 等都很好）。主要问题集中在两类：
1. **写作规范里有几条规则与定稿设计稿直接冲突**（日英空格、人称、敬语、完了、按钮形式、长度上限），按术语表自己定的优先级 ①「设计稿优先」，这些规则本身就不成立；而且它们多数标了 ✔ 要做自动检查，照现在写会让 `copy-qa` 对已批准的文案报错，「自动检查零问题」的达标条件无法达到。
2. **核心概念覆盖不全**：设计稿里高频出现的状态和名词（判断待ち / 確認待ち / 承認待ち / 審査中、フォロー、面談、やりとり、通知、申込済み 等）没有进术语表，批量翻译时最容易各写各的。

## 问题清单

### 严重（0）

无。

### 中等（11）

**M1　日文与拉丁字母之间的空格规则与设计稿冲突**
- 位置：`style-guide.md` §1.3「日英之间」；`glossary.md` §1 iOrbit 行例句「iOrbitに聞く」、§6「iOrbit が一時的に使えません」。
- 问题：规范规定「不加空格（iOrbitに聞く）」，但定稿设计稿**一律加半角空格**：「iOrbit に聞く」（⌘K 两处）、「iOrbit が一時的に使えません」「iOrbit への質問」「Google カレンダー」「iPhone の確認」「AI の提案」「CFO Night Tokyo の参加を取り消しますか？」「Orbit からは送信しません」「鈴木さんと PoC 日程」。术语表内部也自相矛盾（一行无空格、一行有空格）。数字的空格更没有规律：「名刺 12枚」「今日やること 4件」「今月あと 2 回」有空格，「28件を表示」「あと30分」「話すこと3点を用意しました」没有，规范只写「按设计稿原文」，执行人无法据此判断新文案。
- 建议：按优先级 ① 改为「**拉丁字母单词（产品名、英文缩写）与日文之间加半角空格**；句读点、括号、「」两侧不加」（与设计稿和 Google、ChatGPT 实际写法一致，research §3.4 已列出这是分歧点）。数字给一条可执行的规则，例如：「数字 + 量词紧贴（12枚、4件、30分）；数字前接名词时加空格（名刺 12枚、今日やること 4件）；配额例外『今月あと 2 回』」。改完后同步修正术语表 iOrbit 行例句为「iOrbit に聞く」。

**M2　人称规则「不写あなたの」与设计稿冲突，并且会削弱「AI / 用户」的区分**
- 位置：`style-guide.md` §1.1「人称」。
- 问题：设计稿多处用「あなた」且是有意义的：「あなたの判断待ち」「あなたの目標を整理」「3ステップで、あなた専用の人脈プランへ」「評価結果に『あなたが補った項目』」「あなたの『会いたい人：VC』」「あなたのデータに切り替わります」。Orbit 的定位（处处有据、AI 不代替用户做决定）恰恰需要分清「AI 做的」和「你做的」。Apple HIG 反对的是可有可无的所有格（「あなたのお気に入り」），不是一律禁止。
- 建议：改为「不写可有可无的『あなたの』『私たち』；**需要区分用户与 AI / 他人时可以用『あなた』**（例：あなたの判断待ち、あなたが補った項目、送信はあなたが行います）。『私たち』一律不用，主语需要时写『Orbit』或『iOrbit』」。

**M3　「完了」专指待办完成，与设计稿首页「編集 ↔ 完了」冲突**
- 位置：`glossary.md` §5「保存」行禁用写法、「完成（待办）」行。
- 问题：设计稿首页编辑按钮在编辑态显示「完了」（`01-system.html:651`，`edit ? '完了' : '編集'`），这正是 iOS 用户熟悉的「編集 → 完了」退出编辑模式写法；行左滑也露出「完了」（`:227`）。术语表说「完了」只指待办完成、编辑确认一律用「保存」，与定稿冲突，也与 iOS 惯例冲突。
- 建议：区分两种场景：「**退出编辑模式**（不涉及表单提交）用『完了』，与『編集』成对；**提交表单 / 编辑后的确认**用『保存』；待办完成用『完了 / 完了にする』」。在「保存」行把禁用理由改成「表单提交按钮不用『完了』」，不要写成「完了专指待办」。

**M4　「明日へ」的依据失实：设计稿左滑标签是「明日」**
- 位置：`glossary.md` §5「推迟到明天」行、§8 第 4 条。
- 问题：术语表称「明日へ」是「设计稿左滑动作原文」「放不进 72px」，但设计稿左滑规格写的是「**露出 明日 / 完了**」（`01-system.html:227`）；「明日へ」只出现在说明文字里（「明日へ移動」「可撤销的动作（完了、明日へ、アーカイブ）」），不是按钮标签。从日语看，以助词「へ」结尾的按钮语感不完整（「次へ」是流程导航的固定说法，不能类推）；research §4.2 也建议「明日」或「明日にする」。
- 建议：左滑按钮写「**明日**」（与设计稿、iOS 期日快捷项一致，2 字），Toast 保持「明日に移動しました」，中文「明天」，英文「Tomorrow」。删除 §8 第 4 条或改写理由。

**M5　按钮形式规则不完整，会导致自动检查误报和执行人困惑**
- 位置：`style-guide.md` §1.1「按钮」；`glossary.md` 词性说明「动 = 按钮用名词形或『〜する』」、§5「删除」行。
- 问题：规则只允许「汉语名词形（保存）」或「〜する（削除する）」，但术语表和设计稿里大量合格按钮不属于这两类：和语动词原形「開く」「閉じる」「やめる」「元に戻す」「参加を取り消す」「設定を開く」、「名词 + を + 汉语名词」「下書きを作成」「名刺をスキャン」。另外「削除」和「削除する」什么时候用哪个没有规则（设计稿确认框用「削除する」「追加する」，Web 入口用「削除」）。PLANNER B 节写的是「动词原形或『〜する』」，规范比 PLANNER 还窄。
- 建议：改成三条可检查的规则：①按钮不用です・ます、不加「。」；②形式限于「汉语名词」「〜する」「和语动词原形」「〜を + 汉语名词 / 动词原形」；③**确认框和 AI 确认卡里的主按钮用『〜する』**（削除する、追加する、公開する），**页面和列表里的入口按钮用名词形**（削除、編集、保存）。「语气一致」自动检查只查①。

**M6　标 ✔ 的自动检查规则会命中已定稿文案，「零问题」达标条件无法达到**
- 位置：`style-guide.md` §1.1 Toast、§1.2 长度上限、§4 三语一致性；`glossary.md` §4「发送（禁用词）」。
- 问题（逐项）：
  1. **按钮 md ≤10 字**：设计稿已批准的按钮「再分析する（1回使います）」约 12.5、「今はしない（写真から選ぶ）」13、「ガイドを続ける（4 / 5）」约 11.5，都会超标。
  2. **禁用词「送る / 送信」**：草稿边界标准句「送信はしません · 送信はあなたが行います」、通知页「22:00〜7:30 は送りません」、轻询问卡「送りましたか？」都是设计稿原文，按「术语表禁用写法出现即报告」全部会被报。
  3. **Toast 主句只许过去式**：设计稿 Toast 有「接続後に同期します」「10月8日（木）朝 8:00 に通知」，规范没有区分主句 / 副句。
  4. **中日完全相同即报告**：「保存」在日中两语本来就相同，会被当成「没翻译」。
  5. **左滑 ≤4 字**：设计稿把「アーカイブ」（5 字）列为可撤销动作，若作为左滑按钮会超标。
- 建议：①长度上限按组件细分：全宽主按钮（lg / 底部固定）≤16，md ≤10，括号补充说明不计入或另设上限；②禁用词规则改为「禁止**以 Orbit 为主语的肯定式**：送信する、送る、送信しました、送信済み；允许否定式与询问用户式：送信はしません、送りません、送りましたか？」，并在术语表给出白名单；③Toast 分「主句（过去式 / 体言止め）」与「副句（可用现在时）」；④「中日相同」加白名单（保存、メモ类同形词逐条登记）；⑤明确「アーカイブ」是否上左滑，若上则左滑上限放到 5 或改用图标。

**M7　敬语规则过严，与术语表自己的规定和设计稿冲突**
- 位置：`style-guide.md` §1.1「敬语」。
- 问题：规则写「不用尊敬语和谦让语」，但术语表自己规定付费方案写「**ご利用プラン**」，设计稿有「大事なときだけ、**お知らせします**」「**お礼**の下書きを作成」「もう一度**お試しください**」。按字面执行，翻译会把「お知らせします」改成「知らせます」，对日本商务用户显得生硬、不礼貌。
- 建议：改为「允许定型的美化语和谦让定型句（ご利用、お知らせします、お試しください、お問い合わせください、お礼）；**禁止过度敬语**（〜させていただきます、〜でございます、ご〜になられます）；道歉『申し訳ございません』只用于严重故障」。

**M8　活动报名状态链不完整，「参加予定」对日本用户有歧义**
- 位置：`glossary.md` §3「计划参加」「参加确定」行。
- 问题：在设计稿里「参加予定」= **用户自己标记想去、但不一定已申込**（「参加予定に入っていますが、まだ申し込んでいません」）。但在日本的活动平台和日常商务用语里，「参加予定」通常被理解为「已经报名、会去」；英文「Going」（Facebook 惯例）同样意味着已回复出席。用户可能因此以为已经报名而错过早割或截止。另外，没有审核的活动报完名后是什么状态，术语表里没有（只有「参加予定」和审核后的「参加確定」，缺「申込済み」）。
- 建议：保留「参加予定」作为 chip（设计稿定稿），但在术语表里写清：①含义是「行く予定（未申込も含む）」；②**未申込时必须同时显示「未申込」标记或申込按钮**（设计稿推送已这样做）；③补一行「申込済み」（已报名，无需审核的活动，或审核前），状态链写成「参加予定 → 申込済み →（審査中）→ 参加確定」；④英文改为「Planning to go」或「Interested」，避免「Going」的已回复含义。

**M9　「待ち」类状态与申请类动作缺失，最容易混淆**
- 位置：`glossary.md` 整体（§3、§6 缺行）。
- 问题：设计稿同时有「判断待ち」（Task › To-do 的分组，用户要做决定）、「確認待ち」「承認待ち」（色板分开：薰衣草 / 杏）、「審査中」（主办方审核）、「キャンセル待ち」（候补）、「名刺交換の申請」「承認して交換」。这些都是核心状态，意义相近，术语表一个都没有定义（「参加確定」行只说「与審査中成对」）。调研里 Eight 对请求用「承諾」、LinkedIn 用「承認」，Orbit 选「承認」也需要写明。
- 建议：新增一个「状态与请求」小节，逐条写：谁在等谁、对应颜色、日 / 中 / 英。例如：判断待ち = 等你决定（中：待你决定 / EN: Needs your decision）；確認待ち = 等你确认 AI 的结果；承認待ち = 等对方同意（中：等待对方同意 / EN: Awaiting approval）；審査中 = 主办方审核中；キャンセル待ち = 候补（EN: Waitlisted）；申請 / 承認 / 承認して交換 的动作对应。

**M10　核心名词覆盖缺口**
- 位置：`glossary.md` 整体；对照 PLANNER B 节「产品里的所有名词」。
- 问题：以下在设计稿里高频出现、但术语表没有收录，批量翻译时会各写各的：
  - 「**通知**」（术语表「提醒」行说「通知」是另一个概念，但没有「通知」本身的行；research §4.1 有推荐）；
  - 「**フォロー / 要フォロー / フォロー完了**」（To-do 吸收的核心概念）；
  - 「**面談**」「**やりとり**」「**履歴**」「**記録 / 進捗を記録 / ひとこと記録**」；
  - 「**見直し / 月次の見直し / 再分析**」（配额相关，「1日の自動見直しは回数に含みません」）；
  - 「**取り込む / 取り込み**」「**手入力**」「**LinkedIn から取り込む**」；
  - 「**公開 / 公開済み**」「**アーカイブ**」「**マイページ**」「**招待リンク**」（术语表例句已出现「招待リンクをコピー」却没有定义）；
  - 「**おすすめ / 見送り推奨 / 今回は見送り**」。
- 建议：至少补齐上述条目；每条按现有字段写。

**M11　中文 / 英文撞名**
- 位置：`glossary.md` §1「待办容器」、§2「日程」「待办（一项）」「待办分段名」、§1「秘書」。
- 问题：
  1. 英文「予定 = Event」与「イベント = Events」撞名，日文特意分开的两个概念在英文界面里变成同一个词（例：Events 页里的「Add to calendar」后又出现「Event」）。
  2. 中文导航「待办」、分段「待办」、一项「待办」三处同名，导航路径会显示成「待办 › 待办」（设计稿写作「Task › To-do」）。
  3. 「秘書」英文写「Assistant」，而术语表明确说「AI 助手叫 iOrbit」，英文用户会把 Assistant 理解成 AI 助手本身，正好撞上该行自己的禁用说明。
- 建议：①予定英文改为「Calendar event」（列表里空间不够时可写「Event」但 Events 页内不用）或「Appointment」；②中文导航保留英文「Task」（与 iOrbit 一样不翻译，日文导航本来就是英文），或改为「事项」，分段与单项用「待办」；③秘書英文改为「Mail briefing」或「From your mail」，中文「秘书」可保留但在中英两语里注明「不是 AI 助手名」。

### 轻微（20）

**L1　受信箱的选择理由不成立（结论可以保留）**
- 位置：`glossary.md` §1 受信箱行、§8 第 1 条。
- 问题：理由说「受信トレイ」会让人以为是邮件，所以用「受信箱」。但「受信箱」在日本同样是邮件用语（Yahoo!メール、各运营商邮件的文件夹名就是「受信箱」；此为审校者经验，本次未取证，research 只记为「未查到」），邮件感并不比「受信トレイ」弱；中文「收件箱」、英文「Inbox」也都带邮件含义。并且受信箱里确实有「秘書」整理的邮件动态。
- 建议：理由改为「设计稿已定；『受信箱』对日本用户同样自然（日常邮件用语）」，删掉「避免误认为邮件」的说法；风险记录保留。

**L2　「秘書」的代发联想与草稿边界有张力**
- 位置：`glossary.md` §1 秘書行。
- 问题：日语「秘書」常让人联想到「替你发、替你回」，与「邮件止于草稿」的定位有张力（research §4.1 已提出）。例句「秘書から：高橋さんから返信」两个「から」连用，读起来别扭。
- 建议：设计稿已定，保留；在「用在哪里」补一句「秘書区域内的动作按钮只能是『下書きを作成 / 開く』，不得出现代发表述」。例句拆成「标题：秘書から ／ 条目：高橋さんから返信」。

**L3　重试按钮有两个写法**
- 位置：`glossary.md` §5「重试（按钮）」。
- 问题：设计稿重试卡用「再試行」，日历连携失败卡用「**もう一度**」+「あとで」（`01-system.html` ④ AI 确认卡失败态）。术语表只认「再試行」。
- 建议：明确一条：系统错误重试 =「再試行」；与外部服务连携失败、需用户先处理后再试的卡 =「もう一度」可保留，或统一为「再試行」并回报设计稿。

**L4　波浪线字符未定码位，且与 JTF 不一致**
- 位置：`style-guide.md` §1.3「范围」。
- 问题：规范写「全角『〜』（依据 JTF）」，用的是 U+301C（WAVE DASH）；research §3.3 记录 JTF 用的是「～」（U+FF5E）。设计稿用 U+301C。两个字形外观几乎一样，自动检查必须指定码位。
- 建议：写明「统一用 U+301C『〜』（跟随设计稿，偏离 JTF 的 U+FF5E）」，`copy-qa` 检查 U+FF5E 和半角「~」。

**L5　中点有两种用法，规范只写了一种**
- 位置：`style-guide.md` §1.3「分隔」。

- 问题：很多禁用项只在某个语境下才禁，按子串匹配会命中正常文案：
