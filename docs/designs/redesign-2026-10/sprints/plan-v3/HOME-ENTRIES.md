## 各入口的作用和使用频率

| 入口 | 作用 | 频率 | 现状 |
|---|---|---|---|
| 見直し | 让 AI 重新审视计划，每月 3 次 | 中：每月几次 | 顶栏已经有「✦ 让 AI 调整」，它就是这个入口（R37a 已经接上） |
| 待确认 | 记分提议（备注里聊到了几个问题）、候选人、阶段完成建议 | **高，而且要用户处理**：不点就不加分 | 在页底 |
| 目标切换 | 进行中最多 2 个目标，还有已达成的目标；列表里也放修改目标、添加目标 | 中：有两个目标的人常用 | 在页底 |
| 查看前提 | 只读查看制定计划时用到的资料和回答，改要去审视 | 低 | 在页底 |
| 手动编辑 | 审视后才有 1 次 | 低，而且有条件 | 在页底 |
| 标记达成 | 一个计划只用一次 | 很低，但很关键 | 在页底 |

## 方案 A（推荐）：高频的放头部，低频的收进「···」，待确认放在内容最前面

**对标**：
- Linear / Asana / Notion 的项目页：主操作放在标题栏，低频和破坏性操作收进「···」。Linear 的「Mark as completed」、Notion 的「Lock page」都在菜单里。
- 切换放在标题上：Linear 的项目名、GitHub 的仓库与分支名，标题本身就是下拉切换器。
- 需要你处理的事放在内容最前面：GitHub PR 页的「Review required」、Linear Inbox，都放在正文之前。
- App 端把「···」和切换做成 iOS 底部弹层（action sheet），和系统、Things、Linear iOS 一致。

**画法**（只加东西，原型已画的不挪、不改字）：
1. 顶栏：「✦ 让 AI 调整」原样不动，右边 8px 加一个 32px 的「···」圆钮，底色、颜色和 AI 钮一样。
2. 「···」菜单（Web 是下拉，App 是底部弹层）：
   - 查看前提；
   - 手动编辑（不可用时变灰，副文「审视后可再编辑 1 次」）；
   - 分隔线；
   - 标记目标达成。
3. 目标行「目标 · 拿到第一笔融资」：文字不变，末尾加「⌄」，整行可点。弹出的列表依次是：
   - 进行中 N / 2，当前目标打 ✓，每项带阶段进度；
   - 修改这个目标；
   - + 添加目标（满 2 个时变灰并写明原因）；
   - 已达成 · N（折叠）。
4. 待确认区：放在路线之下、「建议先从这 N 件开始」之上。卡片样式沿用 `.todo`，标题旁加珊瑚色数字角标，说明「你选之前不会加分」。
   - 有 3 种行：记分提议（就地「记分 / 不记分」）、候选人（› 去类型详情页）、阶段完成建议（「完成了 / 还没有」）。
   - **0 条整块不画**，最多显示 3 条。

**为什么推荐**：
- 待确认关系到分数，是用户必须处理的事，放在页底容易被漏掉。
- 低频的 3 个操作收进菜单后，页身就是原型画的样子，多出来的只有一个圆钮和一个 ⌄。

## 方案 B（备选）：头部完全不动，页底一张「这个计划」设置卡

**对标**：iOS 设置的分组列表；GitHub 仓库把管理类操作放在页面最底部。

**画法**：
- 待确认区和 A 一样，放在路线之下。这一条两个方案都需要。
- 页底在「为什么这么排」之后加一张卡，标题「这个计划」，共 4 行，每行是「标签 / 内容 / 操作 ›」：
  - 目标 → 切换；
  - 前提 → 查看；
  - 手动编辑（不可用时变灰）；
  - 达成 → 标记。

**取舍**：
- 好处：头部和原型逐像素一致。
- 坏处：切换目标和标记达成要滚到底才找得到；有两个目标的人每次切换都要先滚动。
