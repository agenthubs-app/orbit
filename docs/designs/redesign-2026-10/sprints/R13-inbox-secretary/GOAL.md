# Sprint R13 — 受信箱・秘書来源

## 要实现什么

接在 B 线 R11b 人脈之后，把 App 和 Web 的「受信箱」做成一个入口：上层切换「メッセージ / 通知」，通知内按「すべて / 秘書 / リマインダー / 提案 / 更新 / 履歴」筛选。消息保留现有线程、已读和离线队列；通知保留来源校验、已读、加入 To-do 与合法的稍后提醒。Web 旧抽屉换成列表和详情，App 旧屏换成新组件库画面。未知通知类型只跳过该条，未读总数仍以服务端为准。

**最先交付的独立里程碑**是「秘書来源契约 + 演示数据」，单独提交并交给 D 线 R10 首页「秘書から」组件。首页可以先按此契约接演示世界；R13 随后接真实来源。R26 的「评分变化 / 名单公开」通知与每日 Top-1 推荐是两种语义，分别保留；同一活动同时命中时，秘書预览只显示一张卡，理由优先用 R26 的 `event_pick`。R27 已生成的活动期限和会前通知由 R13 复用、校正分类和展示。每日推荐只从已有活动推荐中按规则选取，**零新增 AI 调用**。D-16 的 Gmail 正文读取和「メール要約」需要授权，本期隐藏入口、卡片和示例内容；原有 Gmail 元数据线程与邮件草稿仍按已有权限工作。

App `chat` / `chat/[id]` **并入**受信箱的消息列表和线程：旧直链先转到新位置，已验证的 Orbit 站内消息与离线待发送记录不能随旧屏消失。外部邮件和代写内容始终只到草稿。画板没有画出的站内发送状态需补画后才进入像素门禁。

R13 做站内收件箱和秘書来源；**R14 单独做推送**（投递偏好、静音、每日上限、7:50 合并、通知深链和双方邀请推送）。R13 不改变系统推送频率。首页 🔔 的正式入口由 D 线 R10 接入；确认入口上线后，由 C 线 R18 删除マイページ的「受信箱」行，B 线做端到端验收。

## 做完能看到什么

- App 首页 🔔 与 Web 左栏进入同一份受信箱；消息数、通知数、未读角标来自各自真实读模型，没有跨账号数据。
- 通知能按来源归入「秘書」，活动期限、会前准备、推荐及其详情落点可读；没有邮件正文授权时看不到邮件要约、授权诱导或付费 AI 占位。
- 通知的「既読」「タスクに追加」「1時間後に再通知」只在服务端支持该动作时出现；重复点或离线重试不会生成两份任务。来源取消或权限失效时不泄露原文。
- 消息列表进入线程，读旧消息、折叠历史、处理草稿；原 `/chat` 直链仍可到新消息页，离线已排队的站内消息继续安全同步。
- Web 1440 与 App 浅 / 深的已认可画板逐屏对齐。没有画板的宽度、隐藏邮件后的状态与异常状态标「设计稿无，附截图，不进门禁」，由主会话补画后重比。

## 怎么验收

先验收秘書来源契约里程碑的独立提交、App 同步副本和 D 线消费样例，再用本机演示数据及测试库走消息、通知、来源失效、账号隔离、离线队列、重复动作、旧直链和 R10/R18 跨线入口。验收须附 App / Web 消息与通知未读数、首页角标和服务端读模型的对账，以及离线操作回网后重新对账的证据；双生产者重跑也不能重复显示同一活动秘書卡。画板预检、逐屏像素、两端全量测试和独立复核按 [PLANNER.md](PLANNER.md) 执行。只在本机验证，不连 Neon、不做生产迁移或部署。本页是目标，实施状态以 Sprint 登记表和 REPORT 为准。
