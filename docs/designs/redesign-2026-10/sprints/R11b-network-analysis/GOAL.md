# Sprint R11b — 人脈分析：構造・機会・インサイト

## 要实现什么

从人脈一覧进入一张真正可用的分析页。App 和 Web 都有「構造」「機会」「インサイト」三段：看人脈分布和不足之处，找到值得再联系或能帮忙引荐的人，并从有依据的数据中看到趋势。点行业、地域或机会卡能打开对应名单，再进入 R11a 的联系人详情；名单人数、分项和具体人必须相符。

少于 **10 人**时整页锁定，只显示 `已有人数 / 10` 进度环、还差几人、加人入口和带「サンプル」标记的预告。到 **10 人**立即解锁，不要求 30 人；10–29 人可注明「参考値」，30 人起去掉该提示。门槛人数取 R11a summary 的 `total`，由新建的 `network-analysis/page-lock.ts` 导出 `NETWORK_ANALYSIS_UNLOCK_CONTACTS = 10`。对 R11b 分析页而言，**3 位已确认联系人**只约束 AI 快照生成与重算，不决定整页能否打开；R11a 与 R28 对既有门槛模块的调用、导出与含义保持原样。

App 接入现有 `GET /api/network/snapshot`，在结构、机会、洞察中显示有依据的分析、更新时间和更新状态；页面上的人数、比例与分布从真实联系人和计划数据计算，不拿 AI 文字里的数字代替。快照一次生成 zh/en/ja 三种文字，Web 与 App 的日文界面传 `ja`；日文快照暂不可用时只显示确定性统计，隐藏 AI 句。Web 改用新画面，补齐独立的「インサイト」页。b5 目前缺少的 Web インサイト、深色、1024、390 画板先由主会话在 b12 末尾补画并代定验收口径，之后才做相应像素门禁。

R11b **只读并复用 R11a 已交付的联系人数据层**。联系人列表、详情、浓度、来源、筛选、添加、删除和 pipeline 清理仍归 R11a；R11b 把 `/contacts/dashboard` 与 `/contacts/analysis/[dimension]/[bucketId]` 换成新屏，旧 `contacts/graph` 跳转到新分析页，不重写 R11a 的屏幕或数据契约。R11a 负责列表中的「人脈分析 · 10人から使えます · あと N人」入口卡，并使用本 Sprint 导出的门槛常量。

## 做完能看到什么

- 5 人时两端都只见锁定态；9 → 10 人时解锁三段；10 → 9 人时重新锁定，旧快照不泄漏。
- 14 人时显示可用的真实统计和「参考値」；286 人等较多数据时三段和下钻名单可操作。
- 構造的分布、機会的候选、インサイト的结论及「?」依据各有真实来源；缺证据的卡片不编数字。
- Web 1440 / 1024 / 390 的浅色与深色、App 模拟器浅色与深色按认可画板过门禁；不存在的画板先补画再比。
- App 的 `contacts/graph` 跳到新分析页，旧分析组件不再可达；既有分析和下钻路径落到新屏，深链不断。

## 怎么验收

按 5、9、10、14、286 人及无计划、无快照、更新中、读取失败分别操作三段和名单；核对人数、证据、返回位置、离线表现与旧链接。少于 10 人时不得读取或排队快照。服务端与 App 契约测试、两端渲染测试及全量回归零新增失败；每张认可的画板逐像素对照并由独立复核重跑。设计稿尚无的临时状态附截图，不计像素门禁。具体证据和停止条件见 [PLANNER.md](PLANNER.md)。
