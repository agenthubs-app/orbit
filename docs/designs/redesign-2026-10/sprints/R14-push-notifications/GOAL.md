# Sprint R14 — 推送与通知设置

## 要实现什么

接在 B 线 R13 受信箱与秘書来源之后，把通知设置从 R18a 留下的「準備中」接成两端可用的页面：App `/settings/notifications`、Web `/app/settings/notifications`，以及 App 的「秘書の設定」。复用现有推送注册、设备归属、通知投递和收件箱记录，不另建一套通知系统。

1. **D-17 频控与合并推送**：默认按账号时区 22:00–07:30 静音，每日全部推送合计最多 3 通，用户可调低至 1 或 2；用户消息与 automatic 共用账号级计数。静音期间产生的候选持有到静音结束后合并发送：结束早于 7:50 则 7:50 发，晚于 7:50 则结束时发；07:30–07:50 新候选等待同批合并。原通知仍写进受信箱，汇总推送计作当天 1 通。面談 30 分前提醒可由用户允许越过静音，但仍计入日上限。持有期间用户改偏好后重判候选；重复 worker、设备重试和跨日不能造成重复或漏计。
2. **通知与秘書设置**：沿用契约 7 的 `quietStart` / `quietEnd` / `dailyCap`、秘書三项和 `meetingException` 可选字段，落实默认值、保存、读取、CAS 冲突恢复与投递行为。设置只控制推送投递；受信箱记录和未读事实不因关掉推送而删除。秘書只开启 R13 已有真实来源；邮件摘要沿 IMPLEMENTATION-PLAN D-16 首期不做，隐藏其入口、开关与示例。
3. **安全落地与邀请**：本地推送白名单覆盖有效的 `/contacts/:id` 与 `/contacts/new/scan/:batchId`；R13-04 的 `/task?seg=` 合法分段推送深链由 R14 实施，R13 验受信箱内部落点。拒绝外部／伪造地址。邀请成功时邀请双方各有自己的站内通知和推送候选，复用 `contact` 来源类型与投递策略；点推送先过已登录及服务端 delivery 校验，再到有权限的目标。

## 做完能看到什么

- App 从「設定 → 通知」进入通知设置，从 R13 的秘書入口进入「秘書の設定」；Web 从「設定 → 通知」进入独立静态路由。R18a 的动态「準備中」占位自动让位，设置页和导航壳不由本 Sprint 改写。
- 用户改静音时段、每日 1–3 通、面談例外和可用的秘書来源后，两端刷新读回一致；系统推送未授权或设备未注册时，页面诚实显示状态并给出可执行的操作。
- 晚间通知在受信箱可读；默认 7:50 收到一通汇总，若静音结束晚于 7:50 则结束时收到；达到上限后仍可在受信箱查看。锁屏默认保护内容，推送只携带已验证的 `deliveryId`。秘書设置和推送示例中不出现邮件摘要。
- b5 #13 / #29、b11 #32 是页面画板基准。它们与已定契约相冲突的选项由主会话按 [PLANNER.md](PLANNER.md) §2 的代定先修画板；没有画板的主题、断点和错误态附截图，标「设计稿无」，不算像素门禁通过。

## 怎么验收

本机用可注入的时钟、数据库、设备及推送替身走「设置 → 夜间 defer → 7:50 合并 → 点开受信箱 → 点开联系人」和「面談例外 → 计入上限」操作链；验证双设备、并发、重试、CAS、跨时区、权限拒绝、邀请双方与非法深链。App / Web 对有画板的画面按逐带像素门禁核对；没有画板的状态留行为测试与截图。两端全量测试与类型检查零新增失败，由主会话独立复核。仅本机验证，不连 Neon、不做生产迁移、部署或真机分发；生产启用项登记为「待用户授权」。
