# 手机端 UI 共性根因与设计结论（2026-11-21，供 App 端照做）

来源：用户对 Web 手机端的两轮反馈（截图 4–10 号）＋ Web 全站 390 / 360 / 430 / 834 / 1440 扫描。
Web 侧修复见提交 1de3c164d、03e3e1388（已上线）与本轮提交（未部署）。App 端按下表逐条自查同类问题；不必界面一模一样，同一类型就算。

## 一、共性根因 → 规则（App 端照做）

| # | 根因 | Web 出现的页面 | 规则（App 端怎么做） |
|---|---|---|---|
| A | **数据少 / 空 / 未登录分支走了另一套布局**，那套布局没在手机宽度测过 | 探す ≤5 场或无计划时手机仍用宽屏布局，整页被撑到 630px | 每个列表页都要用「0 条 / 1 条 / 少量 / 未登录」四种数据各看一遍；不能只用本地多数据的 mock 验收 |
| B | **卡片套卡片**：空状态组件本身是一张卡，再放进卡里；或「叠层」装饰在没有后续卡时仍显示 | 待办「今天的一步」空时白卡里套白卡＋底下两层叠影；笔记页两块一样的空状态 | 卡片里的空状态只放文字（＋必要按钮），不再画卡面与光斑；「叠卡」只在后面确实还有卡时画，张数 = min(2, 剩余-1)；同一屏只出现一个空状态 |
| C | **模块粘连**：相邻两块之间间距为 0 | 活动页分段控件与搜索框；计划页步骤轮播的圆点与「该聊的人」卡 | 模块之间统一 14（手机）；分段控件下方 14；圆点与下一卡 14。设计稿里写 0 的以用户反馈为准改 14 |
| D | **横滑容器伸出页边但吸附没有留白**：容器 margin -18 / padding 18，snap 到容器边，第一张卡贴到屏幕边 | 计划页步骤轮播、探す「会见到想见的人」轮播 | 横滑列表的第一张卡与上下卡片同一左边线（18）；吸附位置留 18（Web：scroll-padding-inline: 18px；App：contentInset / snapToOffsets 从 18 开始） |
| E | **栅格在窄屏没有收成单列**：5/7 栏、span4 等在手机 / iPad 仍并排；或单列里子项仍按 12 栏 span，生出隐式列 | 「该聊的人」详情（人物画像 / 能见到的活动挤成窄列）；主办方页面列表与预览只有 60% 宽 | ≤1023（iPad 竖屏）多栏一律单列满宽；单列时每块占满整列 |
| F | **定宽元素伸出卡片**：写死 330 / 420 宽 | 「该聊的人」主卡三格统计（伸出 9px）；人脉「筛选」弹层 420 宽 | 卡内元素不写死宽度，最多 100%；弹层 / 底部弹层宽度不超过屏宽-16 |
| G | **标题栏一行塞不下**：「返回 | 标题 | 右侧多个文字按钮」 | 运营中心、运营台、导入页、「该聊的人」详情 | 放不下时标题一行、按钮一行；详情页的多个动作按「一个主按钮＋次按钮＋⋯」收（见设计稿②） |
| H | **左边线不齐**：同一列的卡片左右内边距不一样（16 vs 18、内层多 4） | 「该聊的人」详情页 16（全站 18）；iOrbit 建议卡比输入框缩进 4 | 手机全站左右 18，同一列的卡左边线必须一条线 |
| I | **点了要等**：进入详情页要等数据回来才有内容；看过的页面再进仍从空白骨架开始 | 点「该聊的人」5.6 秒才出主卡 | 点任何入口立即切页并显示该页骨架（App：push 后先出骨架屏，不等接口）；看过的页面再进先显示上次的内容，后台刷新；父页刚读过的数据不要重读 |

## 二、加载慢的根因（服务端，App 与 Web 共用同一套 API，服务端修复对 App 同样生效）

生产实测（2026-11-21，大阪边缘 → 新加坡函数 → 新加坡 Neon）：

| 现象 | 数字 | 根因 | 处理 |
|---|---|---|---|
| 空闲 10 秒后第一次请求慢 | `/api/changes` 1.37s（连续请求 0.27s），等 15 秒再请求 1.43s | 服务端连接池空闲 10 秒就断开，下次请求要经 Neon 连接池代理重新建连（TLS＋认证） | 空闲断开改 60 秒（`database-runtime-profile.ts`），并给所有连接池挂 error 处理，避免空闲连接被断时进程崩 |
| 每个请求的中间件都查库 | 3 小时 50 条查询里 44 条来自中间件，同一条「会话是否有效」占 43 条，热 79ms / 冷 560ms | 会话吊销检查每次都实时查库（D31 规定不缓存） | **未改**（D31 是用户定的安全规则）；若要再快，需用户决定是否允许缓存 30 秒 |
| 点进「该聊的人」5.6 秒才出主卡 | 服务端渲染 2.65s（冷）/ 0.6s（热）→ 地址栏 3.5s 才变 → 再并行读「类型详情」0.85s＋「整份计划」1.78s | ① 链接没被预取时（不在屏幕内、程序触发）切页要等服务端渲染回来；屏幕内的链接实测 13–15ms 就切到骨架；② 详情页每次整份重读计划（14KB） | ① 服务端耗时靠上面两行解决；② 计划页读到的计划 60 秒内复用，看过的详情先显示上次结果、后台刷新 |

App 端要做的：进入详情页先出骨架；计划等「父页刚读过」的数据在内存里复用（60 秒内、写操作后作废）；不要在同一页重复请求同一份数据。

## 三、需要用户确认的设计（设计稿已出，确认后两端一起实现）

1. 「该聊的人」详情页头部与主卡：`docs/designs/redesign-2026-10/plan-type-detail-redesign-proposal.html`
   - 标题行只有「返回＋标题＋小字 Step」；动作收成「＋ 线下聊过」（主）＋「✦ 下一步」（次）＋ ⋯（内含「这方面我已熟悉」）；手机放在主卡底部一行。
   - 主卡纵向：图标＋「角色 × 处境」＋一句话 → 三格一行（细分隔线，不是卡中卡）→ 进度整行。
2. 笔记页空状态与新建入口：`docs/designs/redesign-2026-10/memo-empty-entry-proposal.html`
   - 一屏只有一个空状态，说清能写什么（面谈 / 自由备忘录 / @ 关联人和活动 / 面谈可算进计划）；手机有内容时搜索框右侧常驻「＋」；空时空状态里的「添加备忘录」是唯一入口。
   - 待定：页签叫「笔记」、页内叫「备忘录」，建议统一一个词。
3. 活动卡片紧凑化：`docs/designs/redesign-2026-10/event-card-compact-proposal.html`
   - 推荐手机用「左图右文」列表行（88×88 缩略图，标题 ≤2 行，日期 · 地点一行，标签 · 人数 · 费用一行，整卡可点、去掉「详情」按钮），一屏约 3.8 张（现状约 1.6 张）；iPad / 电脑用矮封面卡（封面保持 2:1，标签＋费用同一行，去掉按钮）。
   - 有封面、无封面（emoji 色块）、已结束（置灰）三种卡同高。

以上三项在用户确认前两端都不要实现；确认后 App 端卡片、详情、笔记与 Web 保持一致。
