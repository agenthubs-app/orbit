# Orbit 人脉 AI 使用机会、成本与存储量分析

> 日期：2026-08-31\
> 范围：当前 Orbit Web/API 与 iOS App；以现有代码、测试数据、当前数据库和 Simulator 缓存实测为基础。\
> 货币：模型成本统一按美元计算；不包含税费、汇率波动、工程人力和第三方搜索服务。

## 1. 结论先行

### 1.1 一个联系人需要多少次 AI

“一个联系人需要多少次 AI”不是固定值，它取决于用户是否真的与此人发生互动。适合预算的年度分档如下：

| 联系人类型 | 有价值的 AI 机会/年 | 典型行为 | 当前单调用 Agent 架构下的模型成本/年 |
| --- | ---: | --- | ---: |
| 低活跃 | 2-3 次 | 名片录入、偶尔搜索、一次跟进文案 | **$0.002-$0.004** |
| 标准活跃 | 8-10 次 | 录入、会前准备、3-4 次检索、2-3 次跟进、一次会后总结 | **$0.007-$0.012** |
| 高价值活跃 | 20-30 次 | 高频会面、持续跟进、引荐、复盘和状态查询 | **$0.02-$0.04** |

如果未来把一次 Agent 交互普遍扩展为“规划、工具重规划、最终总结”三次模型调用，涉及 Agent 的成本会增加约 2-3 倍。标准联系人应按 **$0.015-$0.025/年**、高价值联系人按 **$0.05-$0.10/年** 预留。

### 1.2 一个联系人占多少存储

| 位置 | 标准预算 | 说明 |
| --- | ---: | --- |
| iOS 本地缓存 | **5-15 KB/联系人** | 列表、详情和少量证据的重复 JSON 快照；另有约 0.1-0.5 MB 固定缓存 |
| iOS 高活跃联系人 | **20-60 KB/联系人** | 多页面均访问、详情和历史证据缓存较多 |
| 服务端 PostgreSQL | **25-60 KB/联系人** | 联系人、连接、证据、记忆、任务和索引的综合规划值 |
| 长历史或异常活跃联系人 | **0.25-1 MB/联系人** | 大量互动、消息、证据和持续留存历史 |

头像、名片原图、附件和录音不包含在上述数字内。这些二进制资产应存对象存储，并单独预算，因为它们会远大于结构化联系人数据。

### 1.3 对成本模型最重要的判断

1. **AI 成本应主要按活跃用户和 AI 任务计费，而不是按联系人总数计费。** 一次“帮我找日本税务顾问”可以检索很多联系人，但通常只需要一次模型规划。
2. **存储成本才与联系人及历史记录近似线性增长。** 但在现有规模下，数据库基础套餐和计算资源的成本远高于纯磁盘增量。
3. **不要定时让模型逐个重算全部联系人。** 结构、行业、地区、关系强度、待联系状态等应先由 SQL/规则计算，只把少量候选和变化证据交给 AI。
4. 当前默认 `maxLoopSteps = 2` 实际通常只产生一次规划模型调用。这个约束是当前成本较低的关键，不应在没有预算保护的情况下全局提升。

## 2. 当前系统里 AI 真正出现在哪里

### 2.1 已上线或已有代码路径

| AI 机会 | 触发方式 | 计费归属 | 当前模型调用 | 备注 |
| --- | --- | --- | ---: | --- |
| Orbit AI 问答与人脉检索 | 用户主动提问 | 用户/查询级 | 通常 1 次 | 一次查询可涉及多个联系人 |
| 搜索词语言归一化 | 检索词不足或搜索回退 | 用户/查询级 | 0-1 次 | 有规划结果或规则可处理时不调用 |
| 名片 OCR | 用户拍摄/上传名片 | 联系人级 | 1 次 | Gemini 3.5 Flash-Lite，高分辨率图片 |
| 手工备注语言归一化 | 新增非拉丁文字备注 | 联系人级 | 0-1 次 | 只在需要时触发 |
| 邮件/跟进草稿 | 用户请求生成文案 | 联系人级 | 1 次，最多重试 1 次 | 重试用于处理不被证据支持的表述 |
| 活动后总结 | 新证据进入处理队列 | 联系人/证据级 | 1 次/证据版本 | 以证据哈希做幂等，失败才重试 |

对应实现：

- `repos/orbits/features/orbit-ai/live-agent-runtime.ts`
- `repos/orbits/features/orbit-ai/gemini-provider.ts`
- `repos/orbits/features/orbit-ai/language-normalization-service.ts`
- `repos/orbits/features/acquisition/gemini-business-card-ocr-provider.ts`
- `repos/orbits/features/chat/ai-email-draft-service.ts`
- `repos/orbits/features/events/post-event-artifact/processor.ts`

### 2.2 当前不需要 AI 的能力

以下功能目前由数据库、排序或规则完成，模型调用为零：

- 联系人列表筛选、行业/地区/角色分布；
- 关系价值和机会重新计算；
- 人脉分析图表；
- 下一步日期、提醒和待办状态；
- 联系人候选集初筛；
- 已存在数据的读取和 iOS 缓存。

这部分设计是合理的。`live-value-service.ts` 和 `live-opportunity-service.ts` 已采用规则重算，应该继续保持确定性。

### 2.3 可以增加，但必须克制的 AI 机会

未来一个活跃联系人还可能出现以下高价值场景：

1. 会前准备：汇总最近互动、未兑现承诺和可谈话题。
2. 跟进建议：根据关系阶段生成一条具体动作，而不是泛泛建议。
3. 引荐准备：明确双方价值和需要用户确认的边界。
4. 沉默关系唤醒：仅对高价值且长期未互动者生成候选文案。
5. 会后结构化：把自然语言记录拆成事实、承诺、待办和提醒。
6. 风险提示：发现承诺逾期、信息冲突或频繁失约时提醒。

这些能力不应每晚扫描每个联系人。推荐流程是：

`SQL/规则筛选变化 -> 选出 Top N -> 仅对用户打开或采纳的候选调用 AI`

## 3. Token 与单次调用成本

### 3.1 当前提示词实测

通过替换网络请求、只捕获发送给模型的 payload，对当前 Orbit Agent 进行了三档测量：

| 场景 | 总字符数 | UTF-8 字节数 | 规划输入 Token 估计 |
| --- | ---: | ---: | ---: |
| 最小上下文 | 13,279 | 13,851 | 约 3,500-4,200 |
| 标准上下文 | 14,180 | 15,660 | 约 3,800-4,600 |
| 重上下文 | 17,001 | 21,923 | 约 4,500-5,500 |

这里的 Token 是工程估计，不是厂商 tokenizer 的精确结果。当前运行时还会限制最近对话为 8 轮、记忆为 20 条、结果为 12 条，这些上限应保留。

### 3.2 价格基线

截至 2026-08-31，Orbit 默认文本模型是 `deepseek-v4-flash`，官方页面对应版本 `DeepSeek-V4-Flash-0731`。官方价格如下：[DeepSeek Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)

| DeepSeek V4 Flash | 非高峰 | 高峰 |
| --- | ---: | ---: |
| 缓存命中输入/百万 Token | $0.007 | $0.014 |
| 缓存未命中输入/百万 Token | $0.22 | $0.44 |
| 输出/百万 Token | $0.66 | $1.32 |

高峰为周一至周五 UTC 01:00-04:00、06:00-10:00，即日本时间 10:00-13:00、15:00-19:00，和主要工作时间高度重合。预算采用 **70% 高峰、30% 非高峰** 的保守混合价格：

- 缓存命中输入：$0.0119/百万 Token；
- 缓存未命中输入：$0.374/百万 Token；
- 输出：$1.122/百万 Token。

名片 OCR 当前使用 `gemini-3.5-flash-lite`。官方标准价格是输入 $0.30/百万 Token、输出 $2.50/百万 Token：[Gemini API Pricing](https://ai.google.dev/gemini-api/docs/pricing)。高分辨率图片约按 1,120 个图片 Token 处理，再加提示词和 JSON 输出，本文按 **$0.0012/张名片** 规划；图片 Token 规则见 [Gemini Media Resolution](https://ai.google.dev/gemini-api/docs/media-resolution)。

### 3.3 代表性任务的单次成本

计算公式：

```text
单次成本 = 命中输入Token / 1M * 命中价
         + 未命中输入Token / 1M * 未命中价
         + 输出Token / 1M * 输出价
         + 图片/搜索等附加成本
```

| 任务 | 规划用量假设 | 单次估算 |
| --- | --- | ---: |
| 标准 Orbit Agent 规划 | 输入 4,000，60% 缓存命中；输出 250 | **$0.00091** |
| 跟进/邮件草稿 | 输入 1,800，50% 命中；输出 250 | **$0.00063** |
| 会后结构化总结 | 输入 1,200，50% 命中；输出 250 | **$0.00051** |
| 翻译或搜索词归一化 | 输入 350；输出 80 | **$0.00022** |
| 名片 OCR | 输入约 1,400-1,800；输出 200-400 | **$0.0009-$0.0015** |

以上是模型推理成本，不包含 HTTP 基础设施、日志、队列和人工审核。

## 4. 年度 AI 使用模型

### 4.1 低活跃联系人

典型组合：一次 OCR、一次检索/会前查看、一次跟进草稿，部分联系人再发生一次语言归一化。

```text
约 $0.0012 + $0.00091 + $0.00063 + 可选 $0.00022
= $0.0027-$0.0030/联系人/年
```

预算区间取 **$0.002-$0.004**。

### 4.2 标准活跃联系人

典型组合：一次录入、4 次 Agent 检索或准备、3 次跟进草稿、一次会后总结、一次归一化。

```text
$0.0012 + 4*$0.00091 + 3*$0.00063 + $0.00051 + $0.00022
= 约 $0.0075
```

加入 20%-30% 的失败重试、用量波动和价格余量，预算区间取 **$0.007-$0.012**。

### 4.3 高价值活跃联系人

典型组合：12 次 Agent 查询/会前准备、8 次草稿、6 次会后处理，再加录入和归一化。

基础成本约 $0.020；加入波动后预算区间取 **$0.02-$0.04**。如果 Agent 普遍启用三段式循环，则改按 **$0.05-$0.10** 规划。

### 4.4 联系人规模换算

以标准联系人当前架构的中位预算 **$0.01/联系人/年** 计算：

| 联系人数 | 年 AI 成本 |
| ---: | ---: |
| 100 | $1 |
| 1,000 | $10 |
| 10,000 | $100 |
| 100,000 | $1,000 |

这张表只适合把“关系相关 AI”摊回联系人，不能替代用户级预算。用户可以不断与 Orbit AI 对话而不指向具体联系人，因此财务模型应以 MAU 和每月 AI 任务数为主。

## 5. 按活跃用户做预算

按标准 Agent 调用 $0.00091、OCR $0.0012，再加 25% 重试和波动准备金：

| 用户档位 | 文本 AI 任务/月 | OCR/月 | AI 成本/MAU/月 | 10,000 MAU/月 |
| --- | ---: | ---: | ---: | ---: |
| 轻度 | 10 | 2 | **约 $0.015** | **约 $150** |
| 标准 | 40 | 10 | **约 $0.061** | **约 $610** |
| 重度 | 120 | 25 | **约 $0.175** | **约 $1,750** |

如果标准用户的 40 次文本任务都升级成三次模型调用，10,000 MAU 的预算约为 **$1,500/月**。因此，与其按联系人限制，不如设置：

- 每用户每日 Agent 调用软上限；
- 每能力的最大循环步数；
- 自动重试上限；
- 项目月度美元预算和告警阈值；
- 高成本能力只对用户明确操作或已采纳建议触发。

## 6. 存储量实测

### 6.1 当前 PostgreSQL

对当前配置数据库进行了只读聚合查询，不导出联系人正文：

- `orbit_records` 总关系大小：22,061,056 bytes，约 21.0 MiB；
- 表数据：12,640,256 bytes；索引：8,749,056 bytes；
- 当前联系人：79；连接：78；证据：4,447；互动记忆：600；任务：144；消息：80；
- 单条联系人 payload 平均约 820 bytes；
- 将联系人及其连接、证据、记忆、任务、会议和消息关联后：
  - 逻辑行数据 P50：16,960 bytes；
  - P90：19,496 bytes；
  - 最大活跃样本：265,792 bytes。

逻辑行大小不等于物理磁盘大小，因为 PostgreSQL 还有索引、页面空隙、TOAST、MVCC、WAL 和备份。结合当前实测，服务端应按以下档位预算：

| 联系人规模 | 标准服务端存储预算 | 含义 |
| ---: | ---: | --- |
| 100 | 2.5-6 MB | 结构化联系人和常规历史 |
| 1,000 | 25-60 MB | 仍远低于常见数据库套餐额度 |
| 10,000 | 0.25-0.6 GB | 需要关注索引和历史保留策略 |
| 100,000 | 2.5-6 GB | 应分离冷历史和二进制资产 |

运维容量还应为 WAL、备份和迁移临时空间预留约 1.5-3 倍，但它不是每个联系人的永久净数据。

Supabase Pro 数据库包含的磁盘额度和超额单价应以部署时的套餐为准。当前官方文档给出 Pro 计划含 8 GB 磁盘，额外通用 SSD 为 $0.125/GB/月：[Supabase Disk Usage](https://supabase.com/docs/guides/platform/manage-your-usage/disk-size)。这意味着 10,000 个标准联系人的 0.6 GB，即使已超出免费额度，纯增量磁盘也只有约 $0.075/月；真正的固定成本主要来自项目套餐和计算资源，套餐见 [Supabase Pricing](https://supabase.com/pricing)。

### 6.2 iOS Simulator 本地缓存

iOS 当前 `snapshot-store.ts` 不是按联系人规范化存储，而是按 `baseURL + actor + path` 保存整个成功 GET 响应的 JSON 快照。不同页面会重复保存同一联系人信息，退出登录时会清空全部快照。

两份现有 Simulator 数据库的只读实测：

| 数据库 | 快照数 | JSON payload | SQLite 文件 |
| --- | ---: | ---: | ---: |
| 样本 A | 125 | 3,575,138 bytes | 4,304,896 bytes |
| 样本 B | 24 | 721,756 bytes | 921,600 bytes |

当前联系人 Dashboard 的 mock BFF 响应实测为 35,257 bytes，其中 4 个联系人列表部分是 9,217 bytes，固定分析与摘要部分约 26 KB。因此：

- 列表边际约 2.3 KB/联系人；
- 66 个联系人仅该页面约 178 KB 原始 JSON；
- 加 SQLite 页和元数据后约 0.20-0.23 MB；
- 详情、分析、价值证据等其他 endpoint 会再次缓存相关数据。

适合产品预算的 iOS 本地公式：

```text
本地缓存 = 0.1-0.5 MB 固定开销 + 5-15 KB * 常用联系人数量
```

| 常用联系人 | 预计 iOS 本地缓存 |
| ---: | ---: |
| 100 | 0.6-2.0 MB |
| 1,000 | 5-16 MB |
| 10,000 | 50-150 MB，不应全量同步 |

到 10,000 联系人时应采用分页、最近使用缓存和 LRU/TTL 清理，不能把所有详情长期保存在手机上。

## 7. 推荐的成本控制架构

### 7.1 触发原则

1. 用户明确请求时调用 AI。
2. 新证据进入时只处理一次，以证据版本或内容哈希保证幂等。
3. 主动建议先用规则筛选 Top N，用户打开或采纳后才生成完整内容。
4. 不对未变化的联系人定期重新总结。
5. 联系人统计、筛选、排序和关系状态继续用数据库与规则。

### 7.2 调用硬预算

- Orbit Agent 默认保留单次 planner 调用；只有真正需要工具结果二次推理时才提高循环步数。
- 搜索词归一化最多一次 fallback。
- 草稿安全修正最多重试一次。
- 活动后处理按证据哈希幂等，并限制任务最大重试次数。
- 每次请求限制历史轮数、记忆数、候选联系人数和输出 Token。
- 超过用户日预算时应明确降级到规则结果，而不是静默失败。

### 7.3 必须补充的成本账本

DeepSeek 路径已经能记录 prompt、completion、cache hit 和 reasoning Token；OCR 也记录 input/output Token。但其他通用文本调用还没有统一的成本事件。建议每次模型调用写入：

```text
actorId
capability
contactId（可空）
provider / model
promptCacheHitTokens / promptCacheMissTokens
outputTokens / reasoningTokens
priceVersion
estimatedCostUsd
durationMs
retryIndex
requestSucceeded
```

价格必须作为带生效日期的配置保存，不能把当前价格永久硬编码在业务代码中。

## 8. 决策建议

### 近期

1. 以 **$0.061/标准 MAU/月** 作为当前文本 AI + OCR 的预算基线。
2. 以 **25-60 KB/联系人** 作为服务端结构化存储基线。
3. 以 **5-15 KB/常用联系人** 作为 iOS 缓存边际基线。
4. 上线统一模型用量账本，连续观察至少 2-4 周，再用 P50/P90 实际数据替换本文估算。
5. 保持默认单调用 Agent，不全局打开三段式循环。

### 规模化前

1. 建立按能力、用户、模型和日期的成本看板。
2. 给主动建议增加候选预筛、每日上限和用户采纳率指标。
3. iOS 缓存增加 TTL/LRU 和单用户容量上限。
4. 将图片、录音、附件与 PostgreSQL 结构化数据分开核算。
5. 用真实留存和互动频次建立低活跃、标准、高价值联系人的动态分层，而不是给全部联系人分配相同 AI 预算。

## 9. 估算边界

- 价格是 2026-08-31 的官方公开价格，厂商可能调整。
- Token 数来自当前请求 payload 的字符/字节测量与工程估算，最终应以 provider usage 回传为准。
- 当前数据库是开发/测试数据，证据记录相对密集；已用 P50/P90 和分档避免直接按总表平均值外推。
- Simulator 缓存是 endpoint 快照，重复度取决于用户访问了多少页面，不能简单除以联系人总数。
- 本文不计搜索 grounding、邮件发送、推送、地图、对象存储、网络出口、监控和人工审核成本。
