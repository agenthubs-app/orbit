## 一、这一轮形成的产品共识

Orbit 第一版先收敛为几个清晰模块：

| 模块 | 用户要解决的问题 | 主要职责 |
| --- | --- | --- |
| 首页 | 今天最需要知道什么 | 展示近期待办、日程、推荐活动和人脉提醒 |
| 人脉 | 我认识谁 | 导入、查看、编辑基本信息和轻量 Memo |
| 活动 | 我可以去哪 | 推荐、浏览、搜索活动以及报名 |
| 日程 / To-do | 我要做什么 | 查看有时间的安排和无固定时间的事项 |
| I ORBIT | 下一步怎么想、怎么做 | 统一承载主动 AI 对话、分析、写作和建议 |

核心收敛方向：

1. 首页不再做成只有一个巨大输入框的普通 chatbot，也不保留多个重复的“进入”入口。
2. 主动 AI 尽量统一到 I ORBIT；人脉、活动、日程页面以查看、导入、编辑和轻量操作为主。
3. 第一版减少 CRM Pipeline、页面级“问 Orbit”按钮和复杂 Action，先保证最短闭环能真实跑通。
4. 个人基础资料与活动匹配资料分开；匹配资料按需补充，不阻塞普通使用。
5. 数据最终统一放在一个云端数据库中；如果当前 Neon 已接通并验证可用，就继续沿用 Neon，否则再评估 Supabase。Web / API 连接这一个云端权威库，App 通过同一套 API 使用它，不维护 Neon、Supabase、本地数据库之间的业务双写。

## 二、数据与系统边界

这部分是上线前必须先梳理清楚的基础工作。下表是讨论中形成的分类框架，不等同于已经确认的数据库 schema。

| 数据域 | 例子 | 初步分类 | 需要确认的联动 |
| --- | --- | --- | --- |
| 人脉 | 联系人、公司、邮箱、手机号、关系信息、Memo | 基础字段 + 动态关系记录 | 名片导入、账号匹配、I ORBIT 上下文、日程 |
| 活动 | 活动详情、报名状态、报名人数、活动匹配资料 | 动态业务数据 | 推荐、报名、匹配、主办方后台 |
| 日程 | 约见、会议、日期和时间 | 动态业务数据 | 人脉 Memo、To-do、外部 Calendar |
| To-do | 待完成事项、提醒、完成状态 | 动态业务数据 | 首页、I ORBIT、日程 / 提醒 |
| 用户资料 | 姓名、行业、职位、自我介绍、语言偏好 | 稳定基础字段 + 用户编辑 | 注册、匹配、公开展示、权限 |
| AI 结构化结果 | 摘要、匹配理由、建议、草稿、分析报告 | 派生数据 | 来源版本、失效、重新生成、人工确认 |

上线前每个数据域都需要明确：

- 哪些字段是长期稳定的静态字段；
- 哪些字段需要持续更新；
- 哪些字段由 AI 生成，生成依据和版本是什么；
- 哪些字段允许跨模块读取，读取权限属于谁；
- 哪些写入由用户确认后发生，哪些只能生成草稿；
- Web、App、数据库和外部服务各自的权威来源是什么。

## 三、优先级待办

优先级沿用讨论总结：P0 影响上线和主流程，P1 影响核心产品闭环，P2 属于增强能力或商业化探索。

### P0-A：上线、数据和主流程

#### P0-01 上线与数据架构梳理

**目标**：让线上服务、正式数据库、外部服务和 AI 数据边界可验证。

**工作内容**：

- 确认并接通唯一云端业务数据库：优先复用已经验证可用的 Neon；若当前实际标准是 Supabase，则统一使用 Supabase。
- Web / API 连接云端数据库，App 只通过同一套 API 访问业务数据；本地数据库、mock、fixture 和缓存不能作为线上业务事实。
- 接通线上服务及必要的外部服务。
- 盘点人脉、活动、日程、To-do、用户资料和 AI 派生数据。
- 为每个数据域记录权威来源、读写方、权限、更新方式和跨模块联动。
- 把另一套代码中的 To-do / 日程逻辑合并到当前线上系统，避免两套事实来源。
- 文字类数据统一在线上云端存储；图片和本地持久化不在本轮默认扩张。

**完整只读核查（2026-09-15）**：初始工作区配置的 `ORBIT_EVENT_DATABASE_URL` 指向本地 PostgreSQL；随后已创建独立 Neon `orbit` 项目（AWS Asia Pacific 1，Singapore），并将本地服务端环境变量切换到 Neon pooled 连接。通过 `pg` 执行只读连接查询成功，目标数据库为 `neondb`、schema 为 `public`，当前非系统表为 0；未执行迁移、建表、seed 或业务写入。现有 `sync-cloud-records.ts` 只证明存在“云端 Supabase → 本地 Postgres”的历史同步工具，不证明业务已经统一使用云端。App 通过 HTTP API 访问 Web/API 的边界已确认；但 Web/API 仍需重新启动并完成运行时健康验证，Web/App 是否已共用 Neon 数据仍待跨端回读确认。

**P0 顺序**：先做 Neon 项目、权限、schema 和连接能力的最小确认；确认目标真实可用后，再梳理数据域和权威来源；随后在隔离环境做迁移演练，最后才切换 Web/API 并完成 Web ↔ App 回读验收。不得先迁移、双写或把本地数据直接当作线上事实。

**完成标准**：能用一份数据流图和一份字段 / 权限清单说明“数据在哪里、谁能读、谁能写、何时更新”；本地验证不能被描述为远程生产已上线。

**当前 P0-1 交付物**：先使用 [P0-1 数据权威最小矩阵](2026-09-15-p0-1-data-authority-matrix.md) 作为迁移演练入口；完整历史兼容和非 P0 审计在首次演练通过后补齐。

#### P0-02 准备完整测试账号与测试数据

**工作内容**：

- 普通测试用户账号。
- 主办方账号。
- 可以和普通用户交互的另一用户账号。
- 为“小雨”建立可直接登录的测试账号。
- 用这些身份重新走真实流程，减少对 fake 数据和混合测试账号的依赖。

**完成标准**：角色、账号、数据归属和登录方式有可重复的 fixture 或运行手册；账号密码、token 等敏感信息不得写入本文件或提交到仓库。

#### P0-03 重新跑完整注册到使用流程

按以下顺序完成一次可复现的端到端验证：

`注册 / Google 登录 → 完善资料 → 浏览活动 → 报名 → 活动匹配 → 添加人脉 → 使用 I ORBIT → 创建或读取日程 / To-do`

重点检查：

- Google OAuth 配置是否完整；
- 新用户首次登录是否进入资料补充流程；
- Google 登录是否绕过了必要的个人资料；
- 每一步成功后的状态是否持久化并可刷新回读；
- Web、App、数据库和外部服务是否使用同一账号事实。

#### P0-04 修复活动报名逻辑

当前讨论中观察到的缺陷：

- 已过期活动仍可报名；
- 未来活动可能无法报名；
- 提交报名后没有显示“已报名”；
- 报名人数异常清零；
- 报名时的两道 AI 问题偶尔闪动、跳转或显示异常。

需要明确并测试的活动状态至少包括：

`未开始`、`可报名`、`报名截止`、`已报名`、`已结束`

**完成标准**：状态由服务端事实驱动；过期 / 未开放活动不能提交；成功报名后详情、列表和人数显示一致；刷新和重复提交不会丢失或重复写入；两道 AI 问题在完整流程中稳定显示。

### P0-B：产品结构和主入口收敛

#### P0-05 重做首页为 Dashboard

首页优先展示：

- 近期 To-do；
- 近期日程；
- 少量个性化推荐活动；
- 需要关注的人脉提醒；
- 清晰但不重复的 I ORBIT 入口。

首页不再以多个重复入口或单一巨大 Chat 输入框作为主结构，避免用户把 Orbit 误解为普通 chatbot。

**完成标准**：首次进入首页即可看见产品的四类核心价值，并能分别进入对应模块；空数据状态也要说明下一步，而不是只显示空白或无效按钮。

#### P0-06 重新设计底部导航和层级返回

讨论倾向的一级导航为：

`首页 / 人脉 / I ORBIT / 活动 / 我的`

其中 I ORBIT 位于中间作为核心入口。最终中文标签、图标和“我的 / 设置”的归属仍需结合现有导航和视觉规范确认。

交互原则：

- 一级 Tab 页面保持干净，不额外堆叠返回按钮；
- 进入二级页面后提供明确返回；
- 一级入口不重复提供同一功能的多个路径。

#### P0-07 将主动 AI 功能统一到 I ORBIT

以下能力默认收口到 I ORBIT：

- 写邮件和沟通草稿；
- 如何联系某人、如何推进关系；
- 针对某个联系人的分析；
- 基于活动 / 人脉给建议；
- 根据历史信息生成沟通内容。

人脉、活动、日程页面只保留必要的查看、导入、编辑和轻量操作，不在每个页面重复放“问 Orbit”按钮。

**完成标准**：从任一业务页面都能把对象带入 I ORBIT；I ORBIT 能在权限范围内读取对应上下文；生成内容先作为可复核草稿，不把模型输出直接当成已执行动作。

### P1-A：注册与个人档案

#### P1-08 简化个人资料

- 行业放在职位之前；
- 行业使用结构化固定选项；
- 职位根据行业提供推荐选项，同时允许自定义；
- 删除“通用档案里的开场白”；
- 自我介绍保留一句话即可，避免多个重复字段。

#### P1-09 拆分个人基础资料与活动匹配资料

**个人基础资料**：正常使用 Orbit 所需，包含身份和长期有效的信息。

**活动匹配资料**：按活动或匹配需要补充，包含：

- 我能提供什么；
- 我想寻求什么；
- 我感兴趣 / 想聊什么；
- 本次活动的参与目标。

匹配资料不要求注册时全部填写；用户参加活动前再引导补充。可提供入口“完善资料，让其他人更了解你”。

#### P1-10 将匹配字段结构化

“我能提供什么”“我想寻求什么”“感兴趣的话题”优先使用预设标签和多选，减少完全自由输入，以便稳定匹配。标签集合、上限和版本需要在实现前结合当前 taxonomy 核对。

### P1-B：人脉和名片

#### P1-11 完成名片导入中心

- 支持手机拍照扫描，而不是只有文件上传；
- 支持双面名片；
- 保留每面图片、OCR 字段和来源；
- 连续扫描作为后续增强：自动检测名片 → 自动截帧 → 用户确认 → 扫描下一面 / 下一张。

连续扫描不是第一版上线阻塞项，除非它成为当前采集流程的必要能力。

#### P1-12 优化 OCR 后确认页

- 公司名过长时可以完整查看；
- 中文、日文、英文不混杂显示；
- 字段和说明使用自然的产品语言；
- 统一语言系统，但姓名、公司名、OCR 原文和用户输入等业务内容不能被误翻译。

#### P1-13 区分已注册与未注册联系人

联系人分为：

1. 已注册的 Orbit 用户；
2. 仅通过名片导入、尚未注册的联系人。

匹配方式暂定为 `email OR 手机号` 硬匹配：

- 找到账号：绑定为 Orbit 用户，可进入站内关系能力；
- 找不到账号：不显示站内聊天按钮；
- 未注册联系人显示“邀请加入 Orbit”，生成邀请链接 / 邀请文案。

具体匹配优先级、隐私提示、重复联系人合并和错误匹配处理仍需单独确认。

#### P1-14 简化联系人详情页

- “关系背景”和“简介”目前有重复，需要合并或重新定义；
- 关系背景与关系时间线避免重复表达同一事实；
- 允许用户手动添加简单 Memo，例如“9 月 20 日与田中见面”。

#### P1-15 禁止未注册联系人创建站内对话

未注册联系人不能显示或触发站内对话入口。可以生成外部邀请或沟通草稿，但不得伪造一个不存在的站内会话。

### P1-C：I ORBIT

#### P1-16 支持在聊天中引用联系人

提供类似 `@` 引用的交互：用户可以搜索联系人、点击联系人或输入 `@某人`，再围绕该联系人提问，例如：

- “我下周要见 @田中，帮我准备一下。”
- “帮我给 @田中 写一封 follow-up 邮件。”

引用对象必须绑定稳定联系人 ID，不依赖用户手打完整姓名。

#### P1-17 为 I ORBIT 提供受控数据工具

至少需要受权限和操作者隔离保护的只读能力：

- 读取人脉信息；
- 读取指定联系人的历史上下文；
- 读取活动信息；
- 读取日程；
- 读取 To-do。

需要排查当前“没有授权读取人脉和活动”的错误。AI 不应绕过服务层直接读取数据库；工具返回应带来源、时间和权限边界。

#### P1-18 修复 AI 会话历史与新对话入口

- 返回页面时不重复触发完全相同的 AI 请求；
- 对已存在且未变化的分析复用历史结果；
- 信息发生变化时明确标记需要重新分析，而不是静默重复生成；
- 恢复正常的“新对话”输入入口；
- 提供基本会话历史管理。

### P1-D：日程与 To-do

#### P1-19 明确日程与 To-do 的定位

- **日程**：有明确日期 / 时间的安排；
- **To-do**：需要完成，但不一定有具体时间的事项。

首页统一展示最重要的近期内容；两个对象不能因为 UI 合并而丢失各自的语义和状态。

#### P1-20 让人脉 Memo 与日程联动

当用户记录“9 月 20 日和田中见面”这类包含明确时间和联系人的 Memo 时，可以形成日程或提醒。需要定义：日期解析、模糊日期、时区、用户确认和失败回滚。

#### P1-21 暂停复杂 CRM Pipeline

第一版暂不继续维护“待联系 / 推进中 / 长期维护 / 归档”等复杂关系阶段。关系推进先通过：

`人脉 + Memo + To-do + 日程 + AI 提醒`

实现。若未来重新引入阶段，必须先证明它解决了真实用户问题，而不是仅增加页面和状态。

#### P1-22 后续接入外部 Calendar

中长期考虑接入：

- Google Calendar；
- Apple Calendar；
- 邮件中的日程信号。

目标是让 Orbit 成为商业日程聚合中心，并支持导出到系统 Calendar。该项依赖 OAuth、权限、同步冲突、隐私和 provider 成本评估，不作为当前主流程完成的默认前置条件。

#### P1-23 评估桌面 / 手机小组件

候选内容：今日 To-do、今日约见、接下来活动。先作为产品探索项，不在当前第一版主流程中插入实现依赖。

### P1-E：活动模块

#### P1-24 重新设计活动列表

参考 Meetup 等成熟产品的信息架构经验，重点学习：

- 卡片密度；
- 字体尺寸；
- 一级 / 二级页面层级；
- 分类和搜索；
- 推荐布局。

参考的是可用性模式，不复制对方品牌、Logo、文案或像素级布局。当前“大卡片从上排到下”的列表需要重新评估。

#### P1-25 同时支持推荐与全部活动

- 首页只展示少量个性化推荐活动；
- 活动页提供浏览和搜索全部活动的能力；
- 推荐不能阻断用户主动发现活动。

#### P1-26 提前展示 Orbit 的 AI 活动价值

不要让用户经过“注册 → 登录 → 进入活动 → 长距离滚动”后才看到差异化能力。可以在首页或活动列表中逐步加入：

- 推荐活动 Banner；
- AI Matching 标签；
- “为什么推荐这个活动”；
- “你在这里值得认识的几类人”。

这些文案必须建立在真实活动和匹配数据上，不能用静态假理由替代真实依据。

### P2：人脉分析、目标与商业化

#### P2-27 简化人脉分析页面

暂不维护复杂的“概览 / 结构 / 机会”多层信息架构。基础页面先展示结构化分析：行业、地区、角色、关系分布；AI 分析和行动建议作为独立的按需能力。

#### P2-28 AI 人脉分析按需触发

候选分析包括：

- 当前人脉缺口；
- 关键机会；
- 可以重新联系的人；
- 为实现目标应该认识什么人。

新增联系人后可以提示“人脉结构发生变化，是否重新分析？”。只有用户确认或主动发送后才生成，需保留来源版本和生成时间。

#### P2-29 保留长期目标，但定义为用户自己的目标

长期目标不是“我要从某个联系人身上获得什么”，而是用户自己的方向，例如进入 AI 创业、寻找投资或拓展日本市场。

AI 可以基于目标判断：需要什么类型的人脉、推荐什么活动、当前网络有什么缺口。目标字段的入口、隐私和可编辑性需要与个人资料统一设计。

#### P2-30 暂不确定免费 / 付费限制

讨论过的候选限制包括：AI Chat 消息次数、AI 人脉分析次数、免费名片数量。当前不提前固定“100 / 1000 张”等数字，等实际模型成本、OCR 成本、存储成本和用户行为数据出现后再决定。

## 四、建议的第一轮实现顺序

会议总结给出的开发顺序为：

1. 上线和数据库、外部服务边界；
2. 测试账号与完整流程；
3. 首页和底部导航重构；
4. I ORBIT 收口 AI 入口和工具；
5. 注册资料与基础 / 匹配资料拆分；
6. 名片导入和人脉基础闭环；
7. 活动报名状态与报名流程 Bug。

这是交付顺序建议，不代表每项都必须一次性做完。每项完成前应先确认其依赖已经具备，并以真实运行时证据关闭，而不是只以静态页面或类型检查通过作为完成依据。

## 五、端到端验收清单

- [ ] 新账号可以注册或通过已配置的 Google OAuth 登录。
- [ ] 首次登录会补充必填基础资料，且不会绕过资料流程。
- [ ] 行业、职位、自我介绍和匹配标签符合新的字段规则。
- [ ] 首页能看见近期 To-do、日程、推荐活动和必要的人脉提醒。
- [ ] 底部导航入口唯一、层级返回清晰，一级页面不堆重复入口。
- [ ] 活动列表同时支持推荐、全部浏览和搜索。
- [ ] 活动报名状态、报名人数、提交结果和刷新回读一致。
- [ ] 过期活动不能报名，未来可报名活动不能被错误阻止。
- [ ] 活动匹配问题稳定展示，答案不会因页面跳转丢失。
- [ ] 名片支持导入、OCR 后人工确认，双面数据不会互相覆盖。
- [ ] OCR 确认页面不混用产品语言，长公司名可查看。
- [ ] 已注册联系人和未注册联系人显示不同能力；未注册联系人不能创建站内对话。
- [ ] 联系人 Memo 可以保存，并在明确日期 / 时间时形成待确认的日程或提醒。
- [ ] I ORBIT 可以通过联系人引用读取授权范围内的人脉上下文、活动、日程和 To-do。
- [ ] I ORBIT 不重复生成相同分析，且新对话入口和历史会话可用。
- [ ] AI 输出以可复核草稿 / artifact 形式出现，不冒充已执行的外部动作。
- [ ] Web、App、API 和数据库使用同一账号和同一权威数据，刷新后状态一致。
- [ ] 线上部署、OAuth、数据库和外部 provider 的验证状态被单独记录，未验证项不标记为已上线。

## 六、明确暂缓或不作为当前默认范围

- 连续自动扫描名片的完整流水线；
- 桌面 / 手机小组件；
- Google Calendar、Apple Calendar 和邮件日程的完整双向同步；
- 复杂 CRM Pipeline 和关系阶段体系；
- 每个模块独立的“问 Orbit”按钮；
- 过早确定免费名片数量或 AI 次数上限；
- 为了填充演示而伪造联系人、报名人数、组织者或对话记录。

## 七、需要在实现前单独确认的问题

1. 底部导航最终采用哪些中文标签，“我的”是否承载组织者入口和设置。
2. 活动组织者是否与普通用户共用账号模型，还是通过同一账号的角色 / 权限区分。
3. email 与手机号匹配时的优先级、隐私提示、重复联系人合并和误匹配处理。
4. Memo 自动生成日程时，哪些日期表达需要用户确认，哪些情况只生成 To-do。
5. I ORBIT 的联系人引用、历史上下文和跨模块读取范围，以及每类结果的来源展示方式。
6. Google / Apple Calendar 的同步方向、冲突处理、权限范围和上线时点。
7. 目标、匹配标签和 AI 分析报告的隐私边界及删除 / 撤销策略。
8. 免费 / 付费限制要基于哪些真实成本和用户行为指标决定。
