# 同步写入锁顺序修订建议（待批准，尚未实施）

本建议只修订已批准全域离线规范中的服务器锁顺序，不改变数据授权、离线范围或云端权威，不是重开已关闭的 Sprint。

## 为什么需要修订

现有正确性修复 `441ff085a72ac58ad9d251a8982b07e77759960a` 要求旧领域写入先取得共享同步锁，再取得数据行锁。这是为了让同步水位不会越过尚未提交的写入。

新中文规范 §5、0033 Task5 和0034 Task5却写为“回执锁 → 领域 transaction/CAS → 共享同步锁”。CAS 如果先锁住数据行，就可能与旧写入形成死锁：旧写入持同步锁等数据行，新写入持数据行等同步锁。不能混用这两种顺序，也不能仅靠重试掩盖。

核对依据：旧修复中的 `shared/storage/postgres-live-record-store.ts`、`scripts/sync-cloud-records.ts` 和 `features/sync/migrations.ts`；当前中文规范 §5 与两份实施计划。原子笔记删除 `03bfe4aa5793e4107658cb856d76be641c479340` 也依赖这套同步锁基础。

## 建议采用的唯一顺序

在同一数据库连接、同一事务中：

1. 完成认证与授权，开启事务；需要幂等回执的入口取得回执锁并检查已存在回执。
2. 新操作取得共享同步写入锁。
3. 才取得领域数据行锁，执行版本比较与领域写入。
4. 写入同步 revision/journal 与最终回执，一次提交；任一步失败则整体回滚。

重放已有最终回执的请求不用再次写领域数据。旧领域入口不反向取得批量回执锁。旧领域自身的锁也必须逐入口核对，不能仅调整批量入口就认为全系统一致。跨多行写入仍按固定顺序取得数据行锁。

“开启事务”不等于“已取得数据行锁”：事务可以先开启，但 CAS、UPDATE、SELECT FOR UPDATE 必须在共享同步锁之后。共享锁持有到事务结束；不能用无效果的同名 SQL 函数顶替真实协议。读取端冻结水位仍遵守同一提交边界。

## 批准后需要做什么

- 同步修正中英文规范、0033 Task5 与0034 Task5的文字和接口调用顺序。
- A线与B线消费同一个锁协议，D45只有在真实迁移和实际写入入口验证就绪后接入原子笔记删除。
- 先在隔离 PostgreSQL 中验证旧领域写入与新批量写入竞争、同请求重放、更新/删除竞争、写入后异常回滚和水位不漏提交，不能把跳过当通过。
- 迁移上线前核对所有受影响领域入口；当前 MAIN 实际缺 `orbit_records_acquire_sync_write_lock`，本建议没有运行迁移，也没有因此修改业务数据。

这项修订本身不会完成全域离线、历史回填、撤权或笔记删除验收；这些原验收条件全部保留。
