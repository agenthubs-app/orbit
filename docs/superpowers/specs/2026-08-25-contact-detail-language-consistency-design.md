# Orbit 联系人详情语言一致性设计

## 状态

已由用户于 2026-08-25 确认产品方向。本规格覆盖账号语言偏好、联系人详情、关系价值、证据数据、Web、iOS、数据库修复和回归验证。

## 目标

联系人详情必须只使用用户当前选择的一种界面语言。中文用户看到中文说明，英文用户看到英文说明，日文用户看到日文说明；姓名、公司品牌、产品名和 `AI` 等专有名词可以保留原文，但同一段说明不得再拼接中文、英文和日文。

同时修复当前数据库中的过期生成数据，并保证后续重新计算关系价值、重新生成证据或跨设备登录时不会再次产生混合语言。

## 当前问题与根因

### 数据层存在过期的多语言拼接内容

本地数据库 `orbit_records` 中的部分 `evidence` 记录把多种语言预先拼进一个 `summary`。例如联系人证据同时包含日文姓名、英文身份和中文身份。部分 connection evidence 还引用了错误联系人，说明数据库保留了旧版生成结果，而当前代码仓库中的生成 fixture 已经更新。

这不是客户端渲染可以可靠修复的问题。客户端无法判断某个英文片段是需要翻译的说明、品牌名还是姓名，也不能保证从拼接文本中正确恢复原始语义。

### 服务层直接输出英文展示文案

联系人详情服务中的来源标签包含硬编码英文，例如 `QR scan at`。关系价值服务直接生成 `Business relevance`、`Relationship strength`、`Follow up about ...` 等英文说明。即使清理数据库，重新计算后仍会产生英文内容。

### 客户端只有局部中文清洗逻辑

iOS 当前通过少量固定词典和“优先选择中文片段”的启发式逻辑清洗文本。它只能覆盖已知短语，不能处理动态内容，也不支持真正的中文、英文、日文三语选择。Web 目前也主要依赖浏览器本地设置，没有形成账号级、跨设备一致的语言能力。

### 语言偏好不是账号级事实

Web 有 `zh | en | ja` 的本地语言状态，但 iOS 没有统一语言偏好，部分请求仍硬编码 `zh`。账号和个人资料中也没有可供所有客户端共享的 `preferredLanguage`。因此系统无法可靠回答“这个用户选择了什么语言”。

## 设计原则

1. 账号语言是跨设备的唯一事实来源，客户端本地设置只承担首次加载和离线缓存。
2. API 返回单一语言的展示结果，不把三种语言一起交给页面选择或拼接。
3. 动态业务含义使用结构化代码表达，展示文案由本地化层生成，不在领域服务中硬编码英文句子。
4. 原始内容与翻译内容分开保存，不破坏用户输入，也不丢失来源文本。
5. 数据修复只处理可证明为系统生成的旧记录，不改写用户手工创建的联系人、备注或证据。
6. 找不到目标语言时使用确定性的回退顺序，并把回退记入可观测日志，禁止静默拼接多种语言。

## 统一语言模型

### 支持语言

共享契约继续使用：

```ts
type OrbitLanguage = "zh" | "en" | "ja";
```

`zh` 当前表示简体中文。若未来支持繁体中文，再扩展为明确的语言标签，当前实现不得提前引入未使用的变体。

### 账号偏好

账号或账号个人资料增加 `preferredLanguage: OrbitLanguage`。现有账号迁移默认值按以下规则确定：

1. 已存在合法服务端语言值时保留；
2. 小雨测试账号和当前中文演示账号设置为 `zh`；
3. 其他历史账号根据最后一次已知合法偏好迁移；
4. 无法判断时使用产品默认值 `zh`，并在迁移报告中列出。

Web 修改语言时同步写入账号偏好，同时保留现有 cookie/local storage 作为首次渲染缓存。iOS 登录或启动后从个人资料刷新偏好，并保存本地缓存。未登录页面可以使用设备语言映射；登录后以账号偏好为准。

### 请求语言解析

受认证 API 使用统一 `resolveRequestLanguage` 规则：

1. 合法且获准的显式请求语言；
2. 当前认证账号的 `preferredLanguage`；
3. 产品默认语言 `zh`。

客户端通过统一请求头传递语言，例如 `X-Orbit-Language: zh`。服务端必须校验枚举，不接受任意 locale 字符串。请求覆盖用于用户刚切换语言而资料写入仍在传播的短暂窗口，不允许覆盖其他账号的偏好。

## 内容存储模型

### 用户原始内容

用户输入的备注、介绍和证据保留：

```ts
type LocalizedContent = {
  originalText: string;
  originalLanguage?: OrbitLanguage;
  translations?: Partial<Record<OrbitLanguage, string>>;
};
```

`originalText` 不因切换语言被覆盖。翻译由明确的翻译流程写入 `translations`，每个值只包含对应语言，不得保存 `ZH: ... EN: ... JA: ...` 形式的拼接结果。

本期不要求自动翻译所有用户私有备注。没有目标语言翻译时，页面显示原始内容，并以轻量语言标记说明它是原文；不得把机器猜测的半句译文和原文拼在一起。

### 系统生成内容

来源类型、关系阶段、关系价值因素、行动类型、时间范围等系统语义只保存稳定代码和参数。例如：

```ts
type RelationshipValueFactor = {
  kind:
    | "business_relevance"
    | "relationship_strength"
    | "trust_level"
    | "relationship_stage"
    | "source_evidence_quality";
  score: number;
  level?: string;
};

type RelationshipAction = {
  kind: "follow_up" | "invite" | "introduce" | "prepare" | "review";
  subject?: string;
  dueWindow?: "within_24_hours" | "this_week" | "next_week" | "no_deadline";
};
```

客户端或共享 presentation 层根据代码和参数生成中文、英文或日文。领域服务不得再返回完整英文句子作为唯一业务事实。

### 专有名词

以下内容默认保留原文，不作为“混合语言错误”：

- 人名；
- 公司、品牌、产品和活动正式名称；
- 用户明确输入的称谓；
- `AI`、`SaaS`、`CRM` 等通用缩写。

职位、关系说明、来源说明、价值解释、行动建议和系统标签必须按目标语言展示。若公司与职位组合展示，只允许公司名保留原文，职位使用目标语言。

## API 与服务边界

### 联系人详情响应

联系人详情服务接收已解析语言，并返回：

- 原始身份字段和必要的专有名词；
- 单一目标语言的来源标签；
- 单一目标语言的证据展示文本，或带原文语言标记的原始内容；
- 结构化关系阶段和关系价值；
- 单一目标语言的行动文案；
- 可选的 `contentLanguage`，供客户端判断是否发生原文回退。

响应不得包含供页面自行选择的三段拼接文本。兼容期可以保留旧字段，但旧字段必须由同一个本地化结果投影，不能继续透传旧 summary。

### 来源证据

来源证据拆分为稳定来源代码和描述参数，例如：

```ts
type EvidenceSource = {
  type: "qr_scan" | "event" | "manual" | "introduction" | "import" | "message";
  sourceName?: string;
  occurredAt?: string;
};
```

`QR scan at 二维码交换记录` 改为按语言生成的一条自然表述。来源名称如果是用户输入或正式活动名则保留原文，前后系统说明使用目标语言。

### 关系价值

关系价值服务负责计算分数、因素代码、等级代码、关系阶段代码和建议行动参数。共享 presentation 模块负责三语文案。Web 与 iOS 应消费同一套代码定义和翻译资源；iOS 继续通过现有 contract 同步方式使用共享定义，不直接依赖 Web 页面源码。

动态主题作为参数插入本地化模板。若主题本身只有原文，不翻译它，但模板其余部分必须使用目标语言。这样可以显示“本周跟进 North Star Foods 的门店合作”，而不是把完整英文建议混入中文页面。

### 错误处理与可观测性

服务在以下情况记录结构化警告，并附 workspace、record id、字段和请求语言，不记录敏感正文：

- 目标语言缺失而回退到原文；
- 发现旧式多语言拼接标记；
- evidence 引用的人物与 connection/contact 不一致；
- 未知的关系价值代码；
- 非法请求语言。

未知代码必须显示受控的通用文案并上报，不能直接把内部英文代码展示给用户。

## Web 设计

Web 保留当前语言选择界面和视觉风格，只调整状态来源和详情内容管线：

- 登录后读取账号 `preferredLanguage`；
- 切换后立即更新本地状态，并异步持久化账号偏好；
- 联系人详情请求携带当前语言；
- 页面不再通过遍历 React tree 翻译动态业务正文；
- 现有静态界面字典继续使用，但联系人证据和关系价值来自结构化本地化结果；
- 切换语言后重新获取或重新投影详情，页面中不能残留上一个语言的段落。

本期不重做联系人详情的布局、颜色、图标、间距和交互结构。

## iOS 设计

iOS 新增统一语言状态，并接入现有认证和 profile 启动流程：

- 登录成功后加载账号语言；
- 启动时先使用缓存，服务端返回后校正；
- 所有 API 通过统一 client 注入语言请求头，删除页面级硬编码 `zh`；
- 联系人详情、关系价值和来源证据消费结构化字段；
- 删除 `preferredChineseSegment` 一类启发式文本拆分作为主路径；
- 兼容旧服务响应的逻辑只保留在明确的 adapter 中，并在兼容窗口结束后删除；
- 切换语言时使相关查询失效并重新加载，不要求用户退出登录。

本期保持当前联系人列表和详情视觉方案不变，只修正语言和必要的语言切换状态。

## 数据修复与迁移

### 修复范围

迁移只处理满足以下全部条件的记录：

- 属于指定 workspace；
- 来源可证明为 Orbit fixture、seed 或系统生成 provider；
- record id 或 provenance 能与当前生成 fixture 对应；
- 未被用户编辑，或存在明确的 generated checksum 可证明仍为旧生成值。

用户手工联系人、用户备注、手工证据、消息正文和无法确认来源的记录一律不自动改写，进入人工复核报告。

### 迁移步骤

1. 创建带时间戳的目标记录备份或导出，记录 workspace、id、record type、旧 payload checksum。
2. dry-run 扫描过期多语言拼接、错误人物引用、旧英文关系价值和缺失语言元数据。
3. 对当前 fixture 有权威对应项的 generated records 执行幂等 reconcile。
4. 把可结构化的旧关系价值转换为代码和参数；无法无损转换的记录标记为需要重新计算。
5. 校验 evidence 的 contact/connection/person 引用一致性。
6. 输出 manifest：扫描数、修改数、跳过数、冲突数、失败数和每类记录 id。
7. 任意批次发生约束错误时回滚该批次，并明确报告，不允许部分成功后静默继续。

迁移脚本支持 `--dry-run`、限定 workspace 和限定 record type。重复执行不得产生额外翻译、重复证据或 checksum 变化。

### 回滚

回滚工具根据 migration manifest 和备份 checksum 恢复本次修改的记录。若迁移后记录又被用户修改，回滚必须拒绝覆盖并报告冲突，由人工处理。

## 兼容与发布顺序

1. 先增加共享语言类型、账号偏好字段和 locale resolver，旧客户端仍能读取兼容字段。
2. 增加结构化证据和关系价值响应，同时由服务端生成旧字段的单语投影。
3. 更新 Web 和 iOS 消费新字段，统一请求语言并移除页面级英文硬编码。
4. 在 dry-run 报告通过后修复本地数据库的系统生成记录。
5. 运行三语回归、重算回归和跨设备偏好回归。
6. 一个客户端兼容周期后删除旧式多语言 summary 解析与旧关系价值 prose 字段。

数据迁移不能早于新服务兼容能力发布；否则旧代码可能在下一次重算时重新写入英文文案。

## 测试策略

### 领域与服务测试

- `resolveRequestLanguage` 的显式语言、账号偏好和默认回退顺序；
- 非法语言值被拒绝或安全回退；
- 每个关系价值因素和行动类型都有 `zh/en/ja` 文案；
- 动态主题和专有名词在三种语言中保持原文；
- 联系人详情响应每个展示字段只有一种语言；
- 关系价值重新计算后不会恢复硬编码英文；
- 未知代码走受控 fallback 并产生警告。

### 数据一致性测试

- generated contact evidence 不包含 `ZH:`、`EN:`、`JA:` 拼接标记；
- connection evidence 引用的人物与关联 contact 一致；
- migration dry-run 的计数稳定；
- migration 重复执行无变化；
- 用户创建或已编辑记录不被修改；
- 回滚检测迁移后的并发用户修改。

### Web 与 iOS 回归

分别使用 `zh`、`en`、`ja` 打开同一联系人，验证：

- 姓名和品牌保持一致；
- 来源证据、关系价值、行动建议和系统标签使用所选语言；
- 不出现另两种语言的系统句子；
- 切换语言后无需重新登录；
- Web 修改语言后 iOS 下一次同步得到相同偏好，反向亦然；
- 缺少翻译的用户原文只显示一次，并带正确的原文语言状态。

中文页面的自动检查允许专有名词和缩写白名单，不使用“页面不能出现任何拉丁字符”这种会误伤姓名、品牌与 `AI` 的规则。

## 验收标准

1. 小雨账号设为中文后，`contact_001` 的来源证据、关系价值和行动建议不再出现英文或日文系统说明。
2. 同一联系人切换到英文或日文时，所有系统说明统一切换，姓名和品牌不被错误翻译。
3. 数据库中已识别的系统生成多语言 evidence 被修复，错误人物引用被纠正；迁移报告可审计、可重复、可回滚。
4. 关系价值重新计算和联系人详情重新加载不会重新产生英文硬编码。
5. Web 与 iOS 使用同一个账号语言偏好，不再存在 iOS 页面级硬编码语言。
6. 用户手工内容没有被迁移脚本覆盖；无法判断来源的记录被明确列为冲突或待复核。
7. 现有联系人页面视觉布局和交互结构保持不变。

## 非目标

- 本期不实现所有用户私有内容的自动机器翻译；
- 不重做联系人详情视觉设计；
- 不把姓名、品牌和活动正式名称强制翻译；
- 不在本期扩展繁体中文或其他语言；
- 不使用客户端正则表达式永久修补旧的三语拼接数据。

## 主要风险与约束

- 旧记录缺少 provenance 时无法安全判断是否由系统生成，必须跳过而非猜测。
- 账号偏好写入和客户端即时切换可能短暂不一致，因此请求语言覆盖和缓存更新需要原子化处理。
- Web 与 iOS 的本地化资源可能漂移，共享代码枚举和覆盖率测试必须在 CI 中约束。
- 动态 AI 文案不能只要求模型“用某种语言回答”；模型输出必须经过结构化 schema 校验，语言选择、fallback 和重试策略由代码控制。
- 发布期间需要兼容旧客户端，但兼容字段也必须是单语投影，不能继续暴露污染数据。
