# 活动 AI 生成三语化：校准记录（2026-11-22）

用途：交给代码审阅（Codex）判断问题出在哪、成熟产品怎么做。文中所有片段都已脱敏，人名、公司名、可识别的自我介绍都换成了占位符，只保留能说明问题的形状。

## 0. 背景与目标

- **生成什么：** 主办方给一场活动生成「推荐（每人推荐 4 个想见的人和理由）」和「分桌（2 轮，每桌主题、理由、破冰问题、每人的提示和入座理由）」。原来只生成中文。
- **改成什么：** 发布时一次生成日、中、英三语。
- **要求：** 70 人规模也要一次性、准确、快速地生成，不要 fallback。
  - 三种语言的内容要互相一致；
  - 英文里不能混入中文或日文；
  - 人名和公司名必须是资料原样；
  - 全部通过才发布，失败的批次只重试那一批，不拿原文顶替。
- **流水线（原有，未改）：** 推荐分片 → 分组特征分片（只用中文，不展示，用于分桌）→ 确定性分桌（不调用 AI）→ 每桌每轮生成内容 → 全部完成才能发布（原子发布）。任务带 lease 和重试，已完成的任务落盘。
- **校准方式：** 本机内存里跑一次完整生成，使用生产 AI 配置，不连接任何数据库，不产生任何通知。
  - **第 0 轮：** 70 个虚构参加者。
  - **第 1 轮起：** 70 人名单。其中 61 人取自中日交流会的真实报名资料（本机 party-app 备份，报名回答多为日文），另 9 人由这些资料的字段交叉组合而成、使用虚构姓名。
  - **活动配置：** 每人推荐 4 人，每桌 6 人，2 轮，每个任务最多尝试 3 次。

## 3. 各类失败的代表形状（已脱敏）

### 3.1 英文里混入中文或日文（第 0–2 轮的主因）

- 英文照抄了日文报名回答里的词：`"<人A> is seeking 資金調達 partners …"`、`"… in AI・ソフトウェア …"`。
- 第 1–2 轮修复后仍「不合格」的英文句子，经本地分析，**残留的几乎全是人名或公司名的一部分**：只写了姓（`<姓>`）、去掉了全名中间的空格（`<姓><名>`）、只写了公司的主体名（`<公司名去掉「株式会社」>`）、繁体写成简体（`<姓名的简体写法>`）。这些不是没翻译，而是名字没有按资料原样写。
- 英文里还经常把名字改成罗马字（`"<人A的罗马字写法> …"`）。现有检查发现不了罗马字化的名字。

### 3.2 三语结构不配对（第 0 轮）

- 初版让模型分别写 ja、zh、en 三个完整对象，经常出现「ja 3 条理由 / en 2 条理由」，或某种语言缺一个键。第 1 轮改成逐句配对后基本消失。
- 偶尔仍有某一句缺少 en（例如 `icebreakers[1] = {"ja":…,"zh":…}`），每轮 0–3 次。

### 3.3 分桌某种语言「不符合封闭 schema」（第 1、3 轮的主因）

- 名为 `closed_schema_ja` 的失败其实与语言无关：拆分后第一个检查的语言恰好是 ja，所以报成 ja。
- 根因是模型抄写长 id 时抄错了：每人提示的键 `participant:sim-48` 被写成 `participant:sim:48`，于是和 `members` 对不上。生产环境里的 id 更长，这个问题会更严重。
- 第 4 轮改用短键 M1..Mn 后，这一类消失。

### 3.4 JSON 不合法

- **第 0 轮 6 次：** finish_reason=stop，输出只有 1.1–1.7k token，远低于 max_tokens，不是截断。当时没有保存原文，具体原因无法确定。
- **第 4 轮 4 次（分桌）：** JSON.parse 在文末报「Expecting ','」。模型在写完 `memberPrompts`（成员键 → 两句的映射）之后漏掉了一个 `}`，导致整个文档少一层闭合。第 5 轮把每人的内容放进 `members[]` 的同一行后，没有再出现。

### 3.5 中文修复后仍违规（每轮都有，第 7 轮最多）

- 违规词全部来自真实资料里的业务缩写：`"A"`（`M&A` 被分词规则拆成 `M`、`A`）、`"Web3"`、`"Pre-A"`（融资轮次），以及 `DX`、`SNS`、`VC`、`LLM`、`PR`。原来的中文白名单只有 AI、SaaS、KPI、API、B2B、LP、IP、CEO、Scope 这 9 个。
- 中文修复会尝试「翻译」这些缩写，结果修完还是违规，这一批就失败。
- 注意：这条中文规则也是生产上现有的单语生成在用的，所以现在线上用真实数据生成，很可能也会撞上这个问题（未在线上验证）。

### 3.6 占位符（第 6、7 轮）

- 模型用 `{SOURCE}` 指代「这一行是给谁的推荐」，第 6 轮出现 185 处。第 7 轮起服务端按所在行把它换成该行的 sourceKey。
- 偶尔出现 `{1}`、`{2}`（无法判断指谁），或者 `{ S1}`（带空格）。

### 3.7 同一行重复推荐同一人（第 7 轮 4 次）

- `S2: [S2C1, S2C8, S2C2, S2C8]`，同一候选人出现两次，原有的封闭 schema 拒绝。第 8 轮起服务端去重（保留第一次）并重排名次，不编造任何内容。

### 3.8 误判（第 6 轮）

- 名单里没有名字的人，我组名单时临时用了「参加者N」这样的名字，结果和日文里常见的「参加者を」只差一个字，被「改写名字」检查误判。第 7 轮起该检查只认「汉字换成另一个汉字」，名单里也改用了虚构姓名。

## 5. 我的判断

**已消除的：**
- 三语条数不配对：逐句配对后基本消失。
- 分桌 id 抄错：改用短键后消失。
- 分桌少一个 `}`：改成成员行后消失。
- 英文照抄日文资料词：提示词改成「必须翻译」，再加一次修复。
- 人名和公司名被改写、截半、改成简体：AI 不再看到也不再写名字，服务端按 id 填入。

**还在的：**
- 中文缩写违规：第 8 轮已放宽，待验证。
- 推荐重复同一人：第 8 轮已去重，待验证。
- 偶发的「缺一种语言」或未知占位符：靠重试兜住。
- 推荐阶段的单次耗时偏长：2 人一批平均 31–35 秒，最长 46 秒。

**根因（我的看法）：**
1. **一次输出承担太多：** 选人、排序、三语写作、结构、引用都在同一次输出里，而且每批输出 5–6k token。任何一个细节错，整批作废。
2. **很多规则只写在提示词里，没有用 schema 强制：** DeepSeek 的 `json_object` 只保证是 JSON，不保证结构。成熟做法是用 JSON Schema 或 function calling 的严格模式（例如 OpenAI Structured Outputs、Gemini responseSchema），从解码层面保证结构。DeepSeek 目前没有严格 schema 模式。
3. **让模型抄写本应由程序填入的东西：** 长 id、人名、公司名都属于这一类。抄得越多，错得越多。第 4、6 轮把它们改成短键和占位符，效果明显。
4. **校验规则没先用真实数据校准：** 中文白名单、改名检查都出现过误判，导致本来合格的输出被判失败。

**怀疑但没有证实的：**
- 把「选人和理由」（单语，中文）与「翻成另外两种语言」拆成两步，可能更稳：翻译是逐句、可并行的短输出，结构由服务端控制。代价是关键路径多一段，约 10–20 秒。
- 每批 2 人、每人 4 条推荐、三语，单次输出约 6k token，是耗时的主要来源。如果把推荐的翻译拆出去，推荐那一步可以回到每批 6 人。
- 生产上目前的单语（中文）生成，可能也被 3.5 的缩写问题影响（需要看线上任务的失败记录）。

### 离线回放（不调用 AI）

用现在的规则重新检查已保存的输出：

- **第 5 轮「通过」的输出：** 当时的英文检查是放宽的，允许名字的一部分和繁简变体。用现在的严格规则检查它展示给参加者的英文，汉字或假名片段的分布是：

  | 类别 | 次数 |
  |---|---|
  | 资料原样的全名或公司名 | 446 |
  | 名字片段（只有姓、公司的主体名） | 189 |
  | 名字的单字变体（例如繁体写成简体） | 3 |
