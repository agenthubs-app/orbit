# Epic：agent-design（Orbit Agent 第一版）

2026-11-15 开启 · 工作分支 `orbit-agent-claude` · 状态登记见 [SPRINTS.md](SPRINTS.md)

## 目标

把 [Orbit Agent 第一版软件设计稿](../../superpowers/specs/2026-11-15-orbit-agent-v1-software-design.zh-CN.md) 做成可用的产品：用户用一句话查询自己的资料、准备多项修改，看到具体变化并点击确认后，Orbit 才执行。

设计稿是本 epic 唯一的产品依据。设计稿里“2026-11-15 已定的事项”就是各 sprint 的产品批准，不再逐个 sprint 重复索要。

## 范围

设计稿所述功能全部属于本 epic，分 19 个 sprint 交付。不在范围内的只有设计稿明确排除的三项：自动整理记忆、用分类器自动放行写入、批准后让模型继续执行。

## 本 epic 的规矩

沿用 [Web sprint 规则](../../../repos/orbits/docs/sprints/RULES.md)：每个 sprint 有 GOAL 和 PLANNER，最多五项验收，一次 Generator 执行，证据放在所有仓库之外，付费模型调用在 REPORT 里记录次数和 token，生产写入、部署、push 需要单独授权。

与现有规则不同的五处，都以用户 2026-11-15 的指示为准。

1. **每个 sprint 多一道门：离线 Agent 用例必须通过。** 现有规则取消了独立评审和评分表；本 epic 只在 Agent 行为上恢复它。评审由 Claude 在订阅会话里完成，不调用其他 API。规范见 [eval/README.md](eval/README.md)。
2. **每次测试都留痕。** 被测 Agent 的全部输入输出写进测试日志，运行结果登记在 [eval/RUNS.md](eval/RUNS.md)。
3. **分支。** sprint 分支从 `orbit-agent-claude` 建，合回 `orbit-agent-claude`。何时并入 `chat-agent` 由用户在 epic 收口时决定。
4. **编号。** 用 `AG00`–`AG18`，文档放在本目录下，不占用 `W` 和四位数字两个序列，避免与 `chat-agent` 上并行推进的 sprint 撞号。
5. **方案复核不用 Codex。** 2026-10-21 起已禁用。

另有两条沿用用户既有的做法：界面改动先出视觉稿，批准后再动界面代码；界面文字用日常说法。

## 对测试的要求

用户 2026-11-15 提出六条，[评测规范](eval/README.md)逐条落实。

1. **每个 sprint 都要通过 Agent 测试。** 从产品的正常入口执行，由 Claude 根据实际输出和证据逐例评价，保留完整的输入、输出、调用和结果日志。
2. **数据有不同规模。** 小、常规、较大三个独立账号，覆盖 Memo、日程、自建活动、系统活动、人脉、Todo、记忆和对话上下文。
3. **数据有真实的干扰。** 相似或同名的记录、多实体关联、跨页检索、新旧信息冲突、长对话。
4. **数据和服务在本机运行。** 数据库、应用服务、存储和日志都用本机的隔离环境，不访问远程数据库和 Vercel 这类托管服务；数据获取仍走产品的实际链路。
5. **可以用真实的模型 API。** 被测 Agent 可以调用 DeepSeek 和 Gemini；评价用订阅完成。超时、错误这类需要固定结果的场景可以模拟，但要和真实调用分开记录。
6. **关注费用。** 记录调用次数和能拿到的用量、费用信息，便于判断余额是否够用。

第 5 条的原文写的是“Codex 使用订阅进行评价”。本 epic 按第 1 条和此前的指示由 Claude 评价；Codex 自 2026-10-21 起已停用。

## 怎样算完成

- 19 个 sprint 全部 completed，各自的门槛用例在一次完整运行里全部通过。
- 四类不变量零违规：越权读取、未批准或重复的写入、跨账号记忆、已忘记的条目被再次使用。
- 封存集 30 例至少通过 27 例，并逐类报告通过数和具体失败。
- Web 与 App 用同一个测试账号、同一张卡片完成跨端验收。
- 每次成功请求的费用、各路径的 p95 延迟、追问轮数、模型调用上限命中率有报告。
