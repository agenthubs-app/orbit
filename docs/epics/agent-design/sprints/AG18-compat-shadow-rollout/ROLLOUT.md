# Agent 第一版上线手册（AG18）

按设计稿 §8 第 5 步的顺序放量，每一步都写明先查什么、过了才走下一步、出问题拨哪个开关。格式参照
`docs/superpowers/specs/2026-09-30-staging-production-release-design.md`（测试服先过、同一个提交晋级、正式库的写入另走备份与试算）。

**凡是标「需用户授权」的步骤，本手册只写做法，不代表已经批准。** 部署、push、在正式库上跑回填或任何写入、
改正式站的环境变量，都要用户每次明确说可以。本手册里的命令默认只对本机库或测试服。

## 两个开关（CONVENTIONS §2）

| 开关 | 取值 | 作用 |
|---|---|---|
| `ORBIT_AGENT_V1_MODE` | `off` | 只有旧通路（协议 2、不带版本），与 AG01 之前一样。**不是回退用的**：它会恢复旧通路的直写待办和打字“确认”。 |
| | `shadow` | 用户拿到旧通路的回答；新通路在应答之后对同一条消息只读地跑一遍，只留按账号分开的比较记录（`agentV1ShadowComparisons`）。协议 3 不开放，新版客户端退回协议 2。 |
| | `on` | 协议 3 开放；协议 2 和不带版本的旧客户端也交给新流程，由服务端代为等待，卡片变成文字说明和“到新版 App 或网页上确认”。旧草稿卡、旧待办页的接受按钮不再批准任何东西。 |
| `ORBIT_AGENT_V1_PROPOSALS` | `open` | 正常。 |
| | `paused` | **回退开关。** 聊天、定时任务、MCP `propose_change` 都不再出新卡；等确认的卡点了得到“这项修改现在没有执行”；执行队列不领取（已批准的留在原地，结果未知的留在待核对）；已完成的回执照常可读；打字“确认”和“新建待办”都不写入。恢复＝改回 `open`。 |

两个开关都是部署的环境变量：改了要重新部署才生效（正式站上「需用户授权」）。评测里由运行器按用例设置（`settings: { shadow: on }`、`rollback: {}`），只在 `ORBIT_AGENT_EVAL=1` 的评测服务上有效。

## 五步

### 第 1 步：先部署能读新旧字段的版本（开关 `off`）

- 做法：部署本 sprint 的合并提交，`ORBIT_AGENT_V1_MODE=off`、`ORBIT_AGENT_V1_PROPOSALS=open`。测试服先做，过了再到正式站。**部署需用户授权。**
- 查：`/api/health` 200；`/api/ai/conversations/protocol` 返回 `protocolVersion: 2`；旧版 App 和新版网页各发一条只读问题，回答与部署前一致；`npm run agent-eval:run -- --all` 在合并提交上的结果与上一次门槛对照（不新增失败）。
- 出问题：回到上一个部署（Vercel 的上一版 deployment）。这一步不改数据，可以直接回。

### 第 2 步：只在新字段缺失时回填（先试算，再执行，再重跑看是不是 0 行）

- 做法：`npm run db:backfill:agent-v1`（默认只读试算，列出每个集合的计数和处理不了的行）→ `-- --preview`（另存每一行的计划）→ `-- --apply`（只写本机库）。远程库要再加 `--confirm-remote=<host>/<database>`。**在正式库上试算和执行都需用户授权；执行前先做备份（Neon 分支或 pg_dump），备份方式也要用户确认。**
- 规则：待办的 `relatedContactIds`、`relatedEventRefs` 和笔记的 `eventRefs` 只在缺失时由旧的单值或 `eventIds` 写成零或一项的数组；已有数组一概不动；不改更新时间和版本号。日程（从没有单值字段）、联系人的 `version`（关系初始化依赖它为空）、参会自述（不从报名推断）都不回填。
- 查：执行后马上再跑一次试算，`to fill` 全部是 0；处理不了的行逐条看过，留在原样。
- 出问题：回填只加字段、读取方本来就把缺失当成单值，停在这一步不影响任何回答；要撤就按备份恢复（需用户授权）。

### 第 3 步：旧端局部更新保护多值数据（已在代码里，随第 1 步上线）

- 做法：无需操作。待办、笔记、日程的旧接口只提交它认得的字段时，新字段原样保留（`tests/agent-v1/rollout/field-preservation.test.ts`）。
- 查：测试服上用旧版 App 只改一条有两位联系人的待办的标题，再在网页上看这条待办，两个人都还在（AE-CMP-002 的做法）。

### 第 4 步：按账号分组的只读影子运行，看分歧，通过两端业务验收后再开写

- 做法：`ORBIT_AGENT_V1_MODE=shadow` 部署（**需用户授权**）。跑一段时间后出报告：`npm run agent-v1:shadow-report -- --out <文件>`（只读；远程库要 `--confirm-remote`，**需用户授权**）。
- 查：报告按账号分组，每条分歧带委托编号和两边结果；`串到别的账号的记录` 必须是 0；`读到不该读的记录` 必须是 0；“一边出错”逐条看原因。影子通路的模型调用单独一栏，费用要在用户定的上限内。
- 过了再开写：`ORBIT_AGENT_V1_MODE=on`（**需用户授权**）。开写后看：旧版 App 发消息拿到的是同一次调用里的完整回答；要改记录时看到文字说明和“到新版 App 或网页上确认”；旧端打“确认”不写入（AE-CMP-001）。Web↔App 用同一测试账号对同一张卡回读一次。
- 出问题：影子阶段改回 `off` 即可（影子不写业务数据）；开写之后出问题走下面的「回退」，不要改回 `off`。

### 第 5 步：回退（出了问题时）

- 做法：`ORBIT_AGENT_V1_PROPOSALS=paused` 重新部署（**正式站需用户授权**）。`ORBIT_AGENT_V1_MODE` 保持 `on`，不改回 `off`。
- 马上做：`npm run agent-v1:reconcile -- --out <文件>`（只读对账清单；远程库要 `--confirm-remote`，**需用户授权**）。逐条看四类：等确认（停住，可以否决，不能确认）、已批准未执行（批准时间和批准人、操作键都列着，队列不领取）、执行中结果未知（待核对，按 AG02 的三种处理之一，只在恢复后点）、已完成（回执可读）。
- 恢复：改回 `ORBIT_AGENT_V1_PROPOSALS=open` 重新部署（**需用户授权**）。已批准未执行的沿用原操作键继续执行，不会有第二次效果；等确认的卡在点确认时按 AG02 的核对规则重新对照当前数据，变了就出新版卡，用户再看一遍才可确认。恢复后再跑一次对账清单，确认“已批准未执行”变成“已完成”或有失败回执。

## 已知限度

- 离线的旧版 App 已经显示过的内容收不回（设计稿 §7）；在线读历史时，用到已删除或不能再打开的记录的回答不再返回正文。
- 影子阶段用户看到的是旧通路的回答，它的质量就是旧通路的质量（例如旧通路找不到联系人“小林”时，用户也看不到）；比较报告里能看到新通路这一次会怎么答。
- 回退期间定时任务照常计算，出卡的那一期记成“没有出卡（修改暂停）”，恢复后下一期才会再出卡。
