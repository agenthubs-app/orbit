# Sprint AG18 — 新旧版本并存不丢数据，放量有依据，出了问题能退回

## 要实现什么

新版 Agent 的各部分都做完以后，证明它可以安全地交给用户：还没升级的旧版 App 照常能用，也不会把新加的内容冲掉；新旧两套先在后台回答同样的问题，差别逐条列出；出了问题能马上停下新的修改提议，做完的留着记录，没做的停住等核对；最后用全部测试场景和一组开发时从没看过的场景打分，并和改动前比花费和速度。

## 做完能看到什么

- 旧版 App 还能提问、看回答。要改资料时，它看到的是一段文字说明，并被引导到新版 App 或网页上点确认；在旧版里打“确认”不会改任何东西。旧版只改待办标题时，这条待办关联的几位联系人和活动都还在。
- 打开后台对比后，用户看到的仍是旧版的回答；新版对同一句话只读地算一遍，结果按账号分开存，每一处不一样都列出来。新版这边出错，不影响用户拿到回答。
- 演练一次退回：退回后不再出新的确认卡；还没执行的修改停住，可以逐条核对；已经完成的照常能看到结果；打字“确认”或直接让它建待办，都不会写入。
- 一份对比报告：每次成功请求花多少钱、各类请求里慢的那一头要多久（95% 的请求在多少秒内完成）、平均追问几轮、多少次碰到调用次数上限，和改动前那次全量测试并排比较。

## 怎么验收

- 本机测试：222 个公开场景全部通过；越权读取、没点确认就写入、跨账号用到记忆、忘掉的又被用上，这四类问题一次都没有；30 个封存场景至少通过 27 个，按类列出通过数和每一个没过的。每个场景由两个互不相见的 Claude 会话分别评审。
- 演练：在本机测试环境里做一次退回、核对、再恢复，逐张卡核对状态和结果记录。
- 本 sprint 只在本机完成。合并到主线 `chat-agent`、在正式数据库上跑迁移或补数据、部署、推送代码，都要你另外明确决定，不在本 sprint 里做。
