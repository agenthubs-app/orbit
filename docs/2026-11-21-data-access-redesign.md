# Orbit 数据访问层整体方案（v4，2026-11-21，待用户确认，未授权开工）

> 历史：v1 → v2（主会话 13 条）→ v3（Codex 审阅 `2026-11-21-data-access-redesign-codex-review.md`）→ **v4（Codex 成熟做法对照 `2026-11-21-data-access-mature-practice-codex.md`）**。两份报告引用的代码都已回读核实（§8）。
> 用户约束：要快，但**不能因此从数据库多读**，进出流量不能有明显变化；**D31 不放宽**。
> 核心判断（与 Codex 一致）：Orbit 最该先改的是「**少读、少重复读、继续显示已读内容**」——这同时改善速度和数据库流量；数据库休眠只解释久未访问后的首次等待，解释不了每次切页都慢。

## 1. 现状

### 1.1 运行环境（已核实）

| 项 | 事实 |
|---|---|
| 函数 | Fluid compute；Node 24；`sin1`（新加坡） |
| 中间件 | Next 16 proxy，独立 Node 函数实例 |
| 用户入口 | 日本经 `kix1`，到新加坡往返约 70ms |
| 数据库 | Neon `ap-southeast-1`（同区域）；**直连**（非 pooler）；PG 18.7；探针读到 `max_connections = 901`（随 compute 大小变，不作固定容量） |
| 存储 | 通用记录表 `orbit_records`（JSON 载荷）＋各功能专表（计划 `plans / plan_items / plan_log`、活动 `event_ops_*`、评估 `event_assessments`）；**通用表与 JSON 本身不是慢的根因**，问题在条件是否在库里执行、返回多少、读几遍 |
| 连接池 | 9 处构造器、按进程缓存；一次请求通常用 1–3 个；空闲 60 秒（已推送未部署） |
| App | 带 Auth.js 会话 cookie，与网页同一鉴权链；**已有本地同步**（笔记、任务、已报名活动、人脉），**计划不在同步域** |

### 1.2 已测数字（样本小，P0 后替换）

| 项 | 实测 | 说明 |
|---|---|---|
| 点进「该聊的人」到主卡出现 | 5.6s（RSC 2.65s → 路由 JS 0.4s → 两个并行接口取最慢 1.78s → 渲染与测量粒度 0.6s） | 1 次，冷 |
| 同一接口空闲后 / 连续 | 1.37–1.43s / 0.25–0.33s | 各 5 次，**10 秒 idle 的线上版本** |
| 单条最简查询 | p50 79ms，p90 562ms | 仅 50 条日志 |

浏览器端资源加载、JS 执行、主内容出现时间尚未测量（放进 P0）。

### 1.3 鉴权前置 SQL（修正）

`proxy 会话检查（auth.ts JWT 回调）→ 注销门禁（实例内 15 秒缓存，可能命中）→ handler 会话检查 → profiles → accounts`

普通私有接口在业务查询前**通常 4–5 条，兼容路径 6 条**；页面导航在 proxy 里另有新用户引导检查（解析 actor＋读 profile）。同一次 RSC 渲染内的重复调用已由 React cache 合并。

### 1.4 逐屏读取账本（**源码静态估算，不是线上实测**；P0 后用实测逐屏替换，验收按屏对照）

计数口径：读取语句；不计事务开始/结束、首次结构检查、外壳通知、变更游标与 App 后台同步。计划、活动类数字是条件化样例（一个目标、约三场需处理的活动），生产用户的实际日志 / 候选 / 报名量未知。

| 屏 | 一次打开的读取（估算） | 读回了哪些不显示的 / 怎么增长 |
|---|---|---|
| 首页（默认布局） | ≥10 个不同资源接口；仅公共鉴权约 40–60 条，叠加待办、活动、计划后可达上百条 | 活动小卡调用完整「我的活动」读取，待办小卡调用完整待办聚合；秘书预览最多查看 500 条通知选少量卡；布局返回前部分卡未挂载，形成第二段等待 |
| 人脉列表（Web） | 全局汇总、列表、匹配汇总、目标关系 4 次调用，约 35–43 条 | 列表已在库里分页；但每个列表 / 汇总调用又各自读计划（目标相关的人）与邀请关系；无筛选时有重复汇总调用 |
| 活动列表 | 挂载即读评估、未来、过去、额度；探す 再读目录；有目标时数十到上百条 | 未选中页签也读；「我的活动」读 180 天前到 365 天后、每来源 ≤200 行再挑 10 条，逐条取评估重算 |
| 活动详情 | 常见路径数十条，可达约 50 条 | 读本人活动时间线、两条途径的计划上下文、联系人、主办历史；名单可见时**先读全场报名资料，最后通常只显示 8 位** |
| 计划概览 | 概览＋目标列表约 35–50 条；Web 之前还读摘要选目标 | 概览内部重复读类型与日志；**本月额度逐个目标读整份日志**；为少量活动装配活动事实 |
| 「该聊的人」 | 父概览可复用约 22–32 条；不可复用并重读概览约 50–70 条（两接口并行，时间不相加） | 为显示一个类型读**全部类型**的候选、相关联系人、日志、活动条目；整份概览只为 Step 序号等小字段 |
| 笔记（Web） | 首屏 4 个列表请求，约 20–28 条 | **每次读该用户全部笔记**（`limit: "unbounded"`，取 `note` 对象，含正文；`payloadFields` 只排除了操作历史等）再在应用里筛选、排序、截 20 条；**3 个请求只为页签数量**却也返回列表；1,000 篇笔记即四次各 1,000 篇 |
| 待办 | 无计划十几条；有计划和活动 30–50 余条 | 普通任务、关系跟进已在库里分页与计数（做得好）；计划机会、草稿等来源成本高；三组来源串行等待 |

增长方式（源码确认）：笔记随本人全部笔记增长；计划随目标数、完整日志、所有类型候选增长（相关联系人一次最多 200）；活动事实随活动数 × 每场报名者数增长；计划的 60 天活动窗口查询**无 SQL 行数上限**，先取再截 20。

### 1.5 其他已确认的问题

- **计划读取持有连接时再借连接**：计划仓储读取借出一条连接开只读事务，回调内 `reviewBudget()` 又向另一个事务池借（`plans/v2/repository.ts:631` → `service.ts:457` → `service-factory.ts:56`）。
- **冷路径结构检查**：活动评估、邀请模块在请求路径上准备迁移（`assessment/configured.ts:157`、`invite-codes/configured.ts:177`）。
- **活动事实缓存失效判断有正确性缺陷**：命中缓存时只比较报名人数（`orbit-event-facts.ts:84`）；人数相同也可能换人、改资料，匹配结果随之改变，却会继续用旧事实。
- **变更游标没有 plans / events 区域**（`change-tokens.ts:18`）。
- **读取收据通道会写库**（insert `orbit_read_receipts`，`read-receipts-sink.ts:76`）；读取指标里的字节是 JSON 序列化估算，不等于 Neon 计费流量。
- **Web 首屏顺序**：服务端返回页面 → 加载并运行脚本 → 客户端再请求接口 → 显示；接口之间的并行消不掉前面这段串行等待。

## 2. 成熟做法（摘要，出处见两份 Codex 报告）

- 数据库：按常用查询设计索引；**真正在库里分页**；列表只取卡片字段；计数在库里算（注意计数仍可能扫描范围）；只有确认被频繁重复计算才预存汇总。
- 服务端：避免 N+1、批量取关联；权威鉴权在 DAL、每请求一次、不跨请求缓存认证结果；按屏装配「恰好够用」的答案并共用基础资料，**只把几个接口包成一个、内部仍重复读，收益有限**；私有缓存返回前仍完成本请求的安全检查。
- 客户端：先显示上次内容、新鲜期内不读、同一资源在途去重、写后只作废受影响资源；骨架只减少空白，不减少读取。
- 规模取舍（几百到几千用户的小团队）：一个 Postgres、一套后端、按页需要的小查询、正确索引、现有客户端缓存、必要的局部同步。

---

## 3. 约束

- **D31**：每个新的私有请求实时确认撤销状态，在任何实例上都成立；不放宽、不用跨请求认证缓存换速度。
- **注销门禁**：同 D31，只在 DAL 实时查，不进令牌。
- **读取量**：每期上线后，同场景的 SQL 数与返回量不增加；按访问量归一化后总查询不增加，并保留总量护栏。
- **成本**：不常驻心跳、不关闭缩到零、不付费升级、不迁区。

## 4. 验收（逐屏对照 §1.4 账本，P0 实测替换估算后为准）

1. 该屏**主内容更早出现**（浏览器端主内容出现时间，同版本、同数据、同操作序列）。
2. 该屏 **SQL 条数与返回行 / 字节不增加**（P1 各项应明显下降）。
3. 真实流量不明显增加（按访问量归一化；Neon 控制台出站流量单独看）。
4. **D31 完整成立**（最终入口：页面、接口、Server Action、`/api/auth/session`；跨实例撤销、并发、存储故障）。

## 5. 分期（每项单独上线、可单独回退；上线均需部署授权）

### P0 轻量测量（闸门）

- 日志专用通道，**不复用会写库的读取收据通道**；只写运行日志、不增加查询；限期 1 周。
- 分段：连接等待 / 建连 / SQL / 渲染（并行 SQL 不相加）；场景：新实例、连接过期、数据库休眠、客户端缓存命中、连续切页；浏览器端：资源加载、JS 执行、主内容出现时间。
- 产出：逐屏实测表替换 §1.4 估算；回滚：开关关闭。

### P1 去掉重复读与无关读（主要提速与减读收益，按屏逐个上线）

| 屏 / 模块 | 改法 | 读取量 |
|---|---|---|
| 计划（概览、该聊的人） | 一次计划读取内复用类型、日志、活动事实；`overview()` 不再重复读；类型详情只读本类型，并从已读数据给出 Step 序号与统计——**两端不再为此请求整份概览 / `overviewRecent`** | 查询与行数下降 |
| 计划本月额度 | 改为针对本月的汇总查询（`plan_log` 按月份与事件类型计数），不再逐目标读整份日志；依赖完整历史的分数逻辑照旧正确汇总，不靠截断历史提速 | 行数明显下降 |
| 活动列表 | 只读当前页签所需；页签上的数字用单独的计数；「我的活动」在库里按条件与上限取，评估批量取 | 明显下降 |
| 活动详情 | 全场人数、认识的人数、匹配统计在库里计算；名单只返回排序后要显示的少量卡片。**不能简单给名单查询加 `limit 8`**——排序依赖全场匹配，需先在库里算出排序键再取前 N | 返回字节下降（大活动时明显） |
| 笔记 | 在库里分页（游标）；一次请求同时返回三个页签的数量（库里计数）；列表只取卡片字段（标题、摘要、日期、类型、关联数），正文在详情时读 | **明显下降** |
| 人脉 | 列表 / 汇总不再各自重读计划与邀请关系（同一请求内共用一次）；去掉无筛选时的重复汇总调用 | 查询下降 |
| 首页 | 小卡用小摘要读取（只取卡上显示的几条与计数），不调用完整的待办 / 我的活动服务；秘书预览按显示条数取 | 行数与重复读下降 |
| 冷路径迁移 | 活动评估、邀请模块的迁移准备移到部署时执行 | 冷路径少一段 |
| 客户端缓存 | 计划概览、笔记列表、该聊的人重访先显示已有内容、新鲜期内不读；同资源在途去重；写后只作废受影响资源。plans / events 无变更游标区域：沿用「本会话写后作废、回到前台重读」，**不新增轮询区域** | 重访读取下降 |
| 活动事实缓存（缺陷修复） | 失效判断从「人数相同」改为**版本标记**：报名头表 `event_ops_membership_heads` 已带 `sync_revision`（已核实，`event-operations/storage/sync-revision.ts:23`），缓存记下读取时该活动报名头的最大 revision，命中前用一条只返回一个值的查询比较，不同就重读；参加者资料（职业等）变更所在的表是否也带 revision **实施时先核实**，若没有，则把该表相关行的最大 `updated_at` 一并纳入版本标记 | 正确性修复；比重读整份名单更省 |

### 鉴权统一（DAL，D31 不变；全入口验证后才撤 proxy 查库）

- 新 DAL 一次查询取回：会话有效性（D31）＋注销门禁＋身份（profiles / accounts）＋引导状态。auth.ts JWT 回调里的查库迁出，回调只解码；`/api/auth/session` 返回前先过 DAL（旧会话返回空并清 cookie）；`/api/auth/**` 不整体视为公开。
- 每请求一次：RSC 用 React `cache`；Route Handler / Server Action 每个入口独立 ALS `run()` 作用域、立即保存鉴权 Promise；**不进入跨请求去重**（沿用每次撤销检查唯一 key）；私有缓存命中前先完成本请求实时校验；保留注销门禁的路径 / 方法例外与 canonical 归属语义。layout 继续读身份初始化 `SessionProvider`，不作为安全总闸。
- 全覆盖：统一包装器；自动化测试枚举全部 `/api` 路由方法、Server Action、`page.tsx` 与读数据的服务端组件；验收在最终入口上做（页面 307、接口 401、Action 拒绝、session 返回空；跨实例撤销、并发、存储故障失败即关）。现有直接调 proxy 的集成测试改为验证最终入口。
- 回滚：开关恢复 proxy 查库（并存一版）。

### Web 首屏取舍（定案）

- **Web**：一级页与「该聊的人」、活动详情的首屏，由页面服务端组件**直接调用同一读取服务**（与接口共用，不另写一套），把结果作为初始数据交给客户端并写入「上次结果」缓存，客户端在新鲜期内不再请求同一份——**替换**而不是**新增**客户端那次读取，读取量不变或下降，并消掉「返回页面 → 运行脚本 → 再请求」的串行等待。依赖 P1（读取服务已瘦身）与鉴权统一（服务端组件经 DAL），在它们之后按屏上线；点击导航时由已有的 loading 骨架先出（链接预取了骨架），数据随服务端渲染流式到达。
- **App**：继续用现有本地同步（人脉、笔记、任务、已报名活动从设备先读）；**不把计划加进同步域**（那会引入首次下载、删除传播、冲突处理，属于「完整同步引擎」级别的新工作）。App 的计划屏从 P1 的瘦身接口直接受益（类型详情不再请求整份概览），并补消费缺口：已同步的域，屏幕一律先读设备、后台刷新。
- 理由：两端共用同一读取服务，Web 用服务端首屏去掉自己特有的瀑布，App 用已有的本地数据；都不增加数据库读取。

### 连接生命周期（独立治理项，不计入主要提速收益）

- 给**现有各池**接 `attachDatabasePool`，保留 error 监听；「60 秒 idle」由它替换。目的是防止函数挂起后遗留连接，**不承诺建连次数或等待占比下降**。
- 合池不作为整体目标：先列出全部「持有连接时再借连接」的调用（静态检索＋运行时检测，已知一例为计划读取 → `reviewBudget()`），改为传递已有 executor 或移出持连接范围；之后仅在实测证明有收益的地方合并，并统一配置、关闭所有权与计量层。容量按实际 compute、实例分布（含滚动部署、后台任务）与连接持有时间重算；直连暂保留。

### 暂缓 / 删除

- 服务端缓存：P1 后另评估。活动当天预热：暂缓（原做法无法可靠预热）。按下预取：不做。放宽 D31：删除。

## 6. 不做的事

- 整体迁走 JSON 记录表（不是根因；逐热点在库里筛选、分页、计数即可）。
- 全面合池（只在实测有收益处、修完嵌套借连接后局部合）。
- 只为减少接口数而新增一层服务（内部仍重复读则收益有限；只在确有跨模块首屏依赖处做聚合，且共用基础读取）。
- 独立缓存系统（Redis 等）。
- 完整同步引擎（不把计划加进 App 同步域，不自研增量同步）。
- 常驻心跳、广泛预取（进入视口即预取）、付费常驻（关闭缩到零 / 升级套餐）。

---

## 7. 能否解决「点开加载很久」——待验证

- P1 是对计划、活动、笔记、人脉、首页**最有把握**的一期：既缩短等待，又减少读取。
- 鉴权统一去掉每个请求上重复的会话检查与 proxy 里的引导检查；对两端都有效。
- Web 服务端首屏去掉「页面 → 脚本 → 接口」的串行等待；App 由本地数据先显示。
- 连接生命周期不计入提速预期。
- 长时间无人访问后的第一次打开（新实例＋数据库唤醒＋首次建连）仍会慢；本方案不承诺这一下的时长，由 P0 分场景测出后再写。
