# Orbit 数据访问层整体方案（2026-11-21，待用户确认）

> 背景：用户反馈「每个界面都慢」。上一轮做了两个逐点修补（连接空闲 10→60 秒、「该聊的人」复用计划缓存），用户要求按成熟产品的思路结合产品目的整体重新设计，不做局部最优。本文先讲现状（全部为生产实测），再对标，再取舍，最后给目标与分期。**确认前不实现。**

---

## 1. 现状全貌（生产实测，2026-11-21）

### 1.1 一次页面打开经过的步骤

用户在日本（Vercel 边缘 `kix1` 大阪）→ 函数在新加坡 `sin1` → Neon 生产库也在新加坡（`ap-southeast-1`，经只读探针确认，同区域）。

以点进「该聊的人」详情为例（实测 5.6 秒出主卡）：

| 步骤 | 做了什么 | 实测耗时 |
|---|---|---|
| ① 浏览器 → 边缘 → 新加坡 | 每个请求一个往返（日本↔新加坡约 70ms） | 每请求约 70ms |
| ② 中间件（proxy.ts） | 解 JWT → **查库一次**确认会话仍有效（D31）→ 账号注销状态（实例内 15 秒缓存，未命中再查库）→ 页面请求再**查库一次**看新用户引导是否完成 | 热 79ms／冷 560ms 每次查询 |
| ③ 服务端渲染（RSC） | layout 里 `auth()` **再查一次会话** | 热约 0.6s、冷 1.2–2.6s（整段） |
| ④ 浏览器下载 JS、水合 | 约 32 个脚本 626KB（压缩后） | 约 0.1–0.3s |
| ⑤ 页面组件发起数据请求 | 「类型详情」与「整份计划」两个接口，每个接口又走一遍 ①②，路由里 `auth()` 再查会话 + 读身份 | 0.85s／1.78s（并行） |
| ⑥ 出主卡 | | 共 5.6s |

一个接口请求在服务端**真正取数之前**至少串行 3 次数据库往返：中间件查会话 → 路由查会话 → 读身份；页面请求还多一次引导状态。

### 1.2 关键数字

| 项 | 实测 | 怎么测的 |
|---|---|---|
| 同一接口空闲后 vs 连续 | `/api/changes` 空闲后 1.37s，连续 0.27s；等 15 秒后 1.43s | 内置浏览器（已登录生产）连续请求 |
| 单条最简查询（只返 1 行） | p50 79ms、p90 562ms | 生产 `postgres_read_metric` 日志 50 条 |
| 查询来自哪里 | 50 条里 44 条来自**中间件**，其中 43 条是同一条「会话是否有效」 | 同上，按 source / 指纹统计 |
| 冷启动（新进程） | 24 小时 127 次，其中**中间件 108 次**、页面/接口函数 19 次 | 统计每个新进程打印的 pg SSL 警告 |
| 服务端渲染 | 热 0.57–0.63s，冷 1.2–2.6s | 同一页 RSC 连续请求 |
| 接口 | 热 0.25–0.4s，冷 1.1–1.4s | 同上 |
| 从构建机（美东）连生产库 | 建连 1.3s，`select 1` 每次 215ms | 只读探针（构建内跑脚本后故意失败，不上线） |
| 独立连接池 | 9 处各自 `new Pool`（记录存储、事务、计划、匹配、活动运营、名片导入…），一次请求可能要在 2–3 个池里分别建连 | 代码检索 |

### 1.3 根因归纳

1. **中间件查库**：每个页面和接口请求都在中间件里查库；中间件是独立函数、冷启动最频繁（108/127），它的连接几乎每次都要新建（TLS + 认证约 8 个往返），所以单条查询经常 0.5 秒。
2. **同一请求重复鉴权**：中间件查一次会话，路由/页面再查一次；读身份又是一次。三次串行往返在每个请求上重复。
3. **连接生命周期不对**：池子各自为政、空闲 10 秒就断（上一轮改 60 秒）、没有在函数挂起前收尾，导致「空闲后第一次」反复付建连成本。
4. **瀑布式取数**：HTML → JS → 再发接口，接口再走一遍中间件；一页要 2–3 个接口，且父页刚读过的数据子页再读一遍。
5. **Neon 休眠**：库空闲 5 分钟后休眠，唤醒约几百毫秒（生产库不在连接器可见范围内，无法直接看配置；冷查询 560ms 与 Neon 文档的唤醒量级一致，和冷连接叠加）。

## 2. 成熟做法对标（同样是 Vercel + Neon / Next.js）

| 主题 | 成熟做法 | 出处 / 哪类产品 | Orbit 现状 |
|---|---|---|---|
| 连接方式 | Vercel Fluid 上用 `pg` + **一个**连接池 + `@vercel/functions` 的 `attachDatabasePool`：每个热实例只建一次连接，函数挂起前自动关闭空闲连接；HTTP 驱动只在冷启动极多且无法池化时用 | Neon「Connecting to Neon from Vercel」（2026-11-18 更新）、Vercel「Connection pooling with Vercel Functions」 | 9 个池、手动 idle 超时、无挂起前收尾 |
| 中间件里做什么 | 中间件（Next 16 叫 proxy）只做**乐观检查**：读 cookie 里的签名会话，不查库；**权威检查**放在数据访问层（DAL）里、靠近取数处，一次请求只做一次（React `cache` 去重） | Next.js 官方 Authentication 指南（Optimistic checks in Proxy, secure checks in DAL）；Auth.js「Edge compatibility」拆分配置 | 中间件查库 2 次 + 路由再查 |
| 会话撤销又不每次查库 | 短时效签名令牌 + 后台刷新：令牌里带「上次校验时间/会话版本」，过期才查库；敏感操作（改密码、删号、付款、写操作）每次实时校验 | Clerk（会话令牌 60 秒、后台刷新）；Auth0 / OAuth（短期 access token + refresh 轮换）；GitHub「sudo mode」（敏感操作二次确认）；OWASP Session Management（撤销延迟与令牌时效的权衡） | 每个请求实时查（D31） |
| 读取分层缓存 | ① 客户端「上次结果」立即显示、后台重读（stale-while-revalidate）；② 服务端按「用户+资源」缓存，写操作时按标签失效；③ 变更游标只告诉客户端哪些区域变了 | SWR / TanStack Query 默认行为；Next.js `use cache` + `revalidateTag`；Linear / Notion 的「本地数据 + 增量同步」；GitHub 通知接口的 ETag/304 | ① 已有（orbit-last-answer）；② 没有；③ 已有（/api/changes + ETag） |
| 一页一次取数 | 首屏数据在服务端（离库近）一次聚合读出并随页面流式下发，而不是浏览器拿到 JS 后再发多个接口；或每屏一个「视图接口」（BFF） | Next.js App Router 推荐的服务端取数 + Streaming；Shopify / Airbnb 的 BFF 每屏一个聚合接口 | 多数页面客户端取数，每屏 2–4 个接口 |
| 预取 | 链接进入视口/手指按下就预取页面与数据 | Next.js `<Link>` 预取；Instagram / Twitter 列表进详情的「按意图预取」 | 页面预取有，数据预取没有 |
| 数据库休眠与成本 | 低流量用缩到零省钱；生产按流量规律设最小算力或只在高峰前预热，不用全天心跳 | Neon「Scale to zero」与「Cost optimization」文档；活动类产品（Luma、Eventbrite 主办方工具）在活动开始前扩容 | 默认 5 分钟休眠；历史上 10 分钟心跳把额度耗尽 |

## 3. 结合 Orbit 的取舍

**访问模式**：平时零散（同一人隔几分钟到几小时才点一次，实例和库大多是冷的）；活动当天集中（几十到两百人在 1–3 小时内同时用会场页、名单、交换）。所以：
- 平时的体验取决于「冷路径」有多短 → 关键是**减少串行往返次数**和**不在每个冷实例上反复建连**，而不是延长热态时间。
- 活动当天取决于并发下的稳定 → 关键是连接数受控（一个池）和库别在活动中途休眠。

**成本教训**：Neon 每月 100 CU-h 免费额度曾被「每 10 分钟心跳」耗尽（库 50% 时间醒着）；Vercel 也因心跳链耗尽 Active CPU 被封过一个月。结论：**不用常驻心跳；不关闭缩到零**；只在活动窗口有目的地预热（0.25 CU × 活动 4 小时 ≈ 1 CU-h／场，远低于额度）。

**D31 的原始目的**（W0032 / sprints README）：改密码、申请删号之后，**之前签发的所有会话立即失效**，任何实例上都不能用旧结果放行。这是安全底线，保留。

两种满足方式：

| 方案 | 怎么做 | 安全性 | 速度 |
|---|---|---|---|
| D31 不变（推荐先做） | 撤销检查从中间件挪到 DAL，**每个请求仍实时查一次**，但和「读身份」合并成一条查询；中间件不再查库 | 与现在完全相同（每个请求都实时校验） | 每请求少 2 次往返；中间件冷启动不再带建连 |
| D31 放宽（需用户授权） | 读请求在令牌里记「上次校验时间」，60 秒内不再查；写操作和敏感操作每次实时查；改密码 / 删号时把会话版本号 +1 | 读请求最多 60 秒内仍能读到数据（写不进、改不了）；风险：被盗令牌在撤销后 60 秒内还能读 | 每请求再少 1 次往返 |

建议：先做「D31 不变」那一档（已能拿到大部分收益），观察后再决定是否放宽。

## 4. 目标与验收数字

测量口径：日本访问生产，手机宽度；「冷」= 空闲 15 分钟后第一次打开；「热」= 1 分钟内再次打开。首屏 = 页面主要内容（非骨架）出现。站内点击后骨架出现 < 100ms（已达成，实测 13–15ms）。

| 页面 | 现状 冷 / 热 | 目标 冷 / 热 |
|---|---|---|
| 首页、人脉、活动、Task 各一级页 | 约 3–4s / 1.2–1.8s（估算：实测 HTML 冷 2.0s／热 0.6–1.1s ＋ 首批接口冷 1.3s／热 0.3s；P0 后逐页实测替换） | ≤ 1.8s / ≤ 0.8s |
| 「该聊的人」详情 | 5.6s（实测）/ 约 1.5s（估算） | ≤ 2.0s / ≤ 0.8s |
| 活动详情、会场页 | 约 3s / 约 1.2s（估算，同上口径） | ≤ 1.8s / ≤ 0.8s |
| 单个接口（服务端耗时） | 1.1–1.4s / 0.25–0.4s | ≤ 0.6s / ≤ 0.2s |
| 冷时数据库唤醒 | 不可控（几百 ms） | 活动窗口内 0（预热） |

验收方法：Server-Timing 响应头（每段耗时）+ 读取统计日志 + 固定脚本在日本网络下冷热各测 5 次取中位数，改前改后同一脚本。

## 5. 分期实施

| 期 | 内容 | 可直接做 / 需授权 | 预计效果 |
|---|---|---|---|
| **P0 测量** | 给页面和接口加 Server-Timing（中间件 / 鉴权 / 各次查询 / 渲染），读取统计改为 100% 记录一周 | 直接做（只加可观测性，不改行为） | 后续每一步都有数字对照 |
| **P1 连接层** | 9 个连接池合并成一个共享池，接 `attachDatabasePool`（新增依赖 `@vercel/functions`，Vercel 官方包、无费用）；上一轮的「空闲 60 秒」作为**过渡**，P1 上线后由 `attachDatabasePool` 管理的生命周期**替换**；「断线保护」**保留** | 直接做（成熟默认做法）；上线需部署授权 | 消除「空闲后第一次」的 1.1s；连接数受控 |
| **P2 鉴权路径** | 中间件改为只验 JWT 签名（不查库）；会话撤销检查 + 读身份合并成一条查询，放在 DAL，每请求一次；新用户引导与注销状态移到 layout / DAL（或写进令牌、变更时刷新） | 直接做（D31 保持不变）；上线需部署授权 | 每请求少 2 次串行往返；中间件冷启动不再带数据库 |
| **P3 取数形态** | 一级页和「该聊的人」、活动详情改为「每屏一个视图接口」或服务端取数随页面下发；子页复用父页数据；进入详情前按意图预取数据 | 直接做；上线需部署授权 | 首屏少 1–2 个往返 |
| **P4 服务端缓存** | 按「用户 + 资源」的服务端缓存，写操作和变更游标按标签失效 | 需确认：用 Vercel Runtime Cache（Pro 套餐内含，有用量上限）还是先不做 | 热态再快、Neon 出站流量下降 |
| **P5 活动当天** | 活动开始前 30 分钟到结束后 1 小时，把 Neon 最小算力设为不休眠（Neon API 定时任务），结束后恢复缩到零 | **需授权**（会产生少量 CU-h；改生产库配置） | 活动中不再有唤醒等待 |
| **P6 D31 放宽** | 读请求 60 秒内复用校验结果，写 / 敏感操作实时 | **需授权**（改用户定过的安全规则） | 每请求再少 1 次往返 |

不做的：常驻心跳 / 关闭缩到零 / 付费升级 Neon（成本教训，除非用户另有决定）。

请确认：① 方案方向；② P0–P3 按「直接做」推进（每期上线前仍单独请示部署）；③ P4–P6 各自是否做。
