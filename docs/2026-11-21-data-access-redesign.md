## 1. 现状（生产实测）

### 1.1 运行环境（已核实）

| 项 | 事实 | 来源 |
|---|---|---|
| 函数运行模式 | **Fluid compute 已开启**（项目设置 `resourceConfig.fluid: true`）；Node 24 | Vercel 项目 API |
| 函数区域 | 部署指定 `sin1`（新加坡）；项目默认区域 iad1 被 vercel.json `regions` 覆盖 | vercel.json、响应头 `x-vercel-id: kix1::sin1::…` |
| 中间件（Next 16 proxy） | 以 Node 函数运行，日志来源 `serverless-middleware`，与页面/接口函数是**不同的函数实例** | 生产日志 source 字段 |
| 用户入口 | 日本用户经大阪边缘 `kix1`，到新加坡往返约 70ms | 响应头、实测 |
| 数据库 | Neon，`ap-southeast-1`（新加坡，与函数同区域）；**连接串是直连端点，不是 `-pooler`**；PG 18.7；`max_connections = 901` | 只读探针（构建内运行后故意失败，不上线） |
| 代码里的假设 | `database-runtime-profile.ts` 注释写「serverless 走 Neon pooler（pgbouncer）」——**与实际不符**（实际直连） | 代码 vs 探针 |

中间件冷启动多的原因（108 / 127，见 1.3）：中间件是每个页面与 `/api` 请求的必经函数，被调用次数远多于任一页面/接口函数，但流量稀疏时同样会被回收；且它当前要连数据库，每个新实例都要新建直连（TLS + SCRAM，Neon 文档估约 8 个往返）。是否还有「中间件不享受 Fluid 实例复用」的平台因素，**尚未核实**，P0 的 Server-Timing 会记录实例冷热与区域后给出结论。

### 1.2 一次页面打开（点进「该聊的人」，实测 5.6s 出主卡）

| 时间段（从点击起） | 做了什么 | 耗时 |
|---|---|---|
| 0.18s → 2.83s | 新页面的服务端渲染请求（RSC）：中间件（查会话 + 注销门禁 + 新用户引导）→ layout `auth()` 再查会话 → 渲染 | 2.65s（冷；热约 0.6s） |
| 2.83s → 3.2s | 浏览器加载该路由的 JS 块、提交新页面（地址栏在 3.5s 变化，测量间隔 50ms） | 约 0.4s |
| 3.2s → 5.0s | 页面并行请求「类型详情」0.85s、「整份计划」1.78s；每个接口都走一遍中间件 + 路由鉴权 + 读身份 | 1.78s（取最慢那条） |
| 5.0s → 5.6s | React 渲染、绘制，以及测量轮询粒度（50ms） | 约 0.6s |

### 1.4 App 端

App 不走 Bearer 令牌：登录后保存 Auth.js 的会话 cookie，每个请求在 `Cookie` 头里带上（`repos/orbit-app/src/api/auth-session*.ts`）。因此 App 的每个接口请求与网页完全同路：中间件（查会话 + 注销门禁）→ 路由 `auth()` 再查会话 → 读身份 → 取数，同样 3 次串行往返；App 不取 HTML/RSC，只受接口段影响。App 端在手机网络下另有约 70ms＋移动网络延迟的往返成本，所以「减少往返次数」对 App 的收益比网页更大。现状接口耗时同 1.3（热 0.25–0.4s / 冷 1.1–1.4s 服务端 + 网络）。

### 1.5 根因

1. 中间件查库（会话 + 注销门禁 + 引导），而中间件冷启动最频繁，每次新实例新建直连。
2. 同一请求重复鉴权：中间件一次、路由/RSC 再一次，读身份又一次，三次串行。
3. 连接生命周期：9 个池各自建连，空闲即断（上一轮 10→60 秒是过渡），无挂起前收尾。
4. 瀑布式取数：HTML → JS → 2–4 个接口，每个接口再走一遍鉴权；父页刚读的数据子页再读。
5. Neon 休眠后唤醒（数百毫秒，叠加在冷连接上）。

## 2. 成熟做法对标

| 主题 | 成熟做法 | 出处 |
|---|---|---|
| 连接 | Fluid 上用 `pg` + 一个池 + `@vercel/functions` 的 `attachDatabasePool`（每个热实例只建一次连接，挂起前关闭空闲连接）；冷启动极多时才考虑 HTTP 驱动 | Neon「Connecting to Neon from Vercel」（2026-11-18）、Vercel「Connection pooling with Vercel Functions」 |
| 直连 vs pooler | serverless 推荐 pooled 端点（大量短连接）；pooler 是事务模式，不能用会话级特性 | Neon「Connection pooling」 |
| 鉴权位置 | proxy 只做乐观检查（读 cookie、不查库）；权威检查放在数据访问层（DAL），每请求一次；**不在 layout 做鉴权**（客户端导航不重跑、保护不到 route handler / server action） | Next.js 官方 Authentication 指南 |
| 会话撤销 | 短时效令牌 + 刷新时校验；敏感操作实时校验 | Clerk（60 秒会话令牌）、OAuth access/refresh、GitHub sudo mode、OWASP Session Management |
| 读取缓存 | 客户端上次结果先显示后台刷新；服务端按用户+资源缓存、写时按标签失效；变更游标 | SWR / TanStack Query、Next `use cache` + `revalidateTag`、Linear / Notion 增量同步 |
| 聚合读取 | 每屏一个视图接口（BFF），一次往返给齐首屏 | Shopify / Airbnb 的 BFF |
| 休眠与成本 | 低流量缩到零；高峰前预热而不是常驻心跳 | Neon「Scale to zero」「Cost optimization」 |

## 3. 结合 Orbit 的取舍

- **访问模式**：平时零散（冷路径决定体验 → 关键是减少串行往返、不在冷实例上反复建连）；活动当天 1–3 小时集中（关键是连接受控、库不在活动中途休眠）。
- **成本教训**：每 10 分钟心跳曾耗尽 Neon 100 CU-h 额度、Vercel 也因心跳链耗尽 Active CPU 被封一个月 → 不常驻心跳、不关闭缩到零、不在生产库上做会被遗忘的配置改动。
- **D31 的目的**：改密码 / 申请删号后，之前的会话在任何实例上下一次请求即被拒。保留且不放宽。
- **注销门禁（account-rights gate）**：与 D31 同为安全门禁；只能在 DAL 实时查，**不写进令牌、不加缓存时效**。现有实例内 15 秒缓存属于既有窗口，P2 一并去掉，与会话撤销、读身份合并成一条实时查询。
- **新用户引导状态**：非安全状态，可写进令牌（完成引导时刷新令牌），或在 DAL 与身份一起读。

## 4. 目标与闸门

**P0 是闸门**：上线测量后，用逐页实测回填下表「现状」列，并重新确认 P1–P3 预期收益，再决定是否往下走。下表目前多为估算，仅「该聊的人」冷 5.6s、接口与 RSC 冷热为实测。

| 页面 | 现状 冷 / 热 | 目标 冷 / 热 |
|---|---|---|
| 一级页（首页、人脉、活动、Task） | 约 3–4s / 1.2–1.8s（估算） | ≤ 1.8s / ≤ 0.8s |
| 「该聊的人」详情 | 5.6s（实测）/ 约 1.5s（估算） | ≤ 2.0s / ≤ 0.8s |
| 活动详情、会场页 | 约 3s / 约 1.2s（估算） | ≤ 1.8s / ≤ 0.8s |
| 单个接口（服务端） | 1.1–1.4s / 0.25–0.4s（实测） | ≤ 0.6s / ≤ 0.2s |
| App 同一屏（接口段） | 同接口 × 每屏接口数 | 每屏 1 个视图接口，冷 ≤ 0.8s / 热 ≤ 0.3s |

测量：日本网络、手机宽度；冷 = 空闲 15 分钟后首次；热 = 1 分钟内再次；固定脚本冷热各 5 次取中位数。

**读取量指标（与速度并列，用户约束：要快，但不能因此从数据库多读，进出流量不能有大的变化）**

| 指标 | 口径 | 要求 |
|---|---|---|
| 每屏查询次数 | 打开一屏（含它发出的全部接口）的 SQL 条数 | 每期上线后不高于改前；**P2 应明显下降**（每个请求少 2 条鉴权查询） |
| 每屏返回行数 / 字节数 | 同一屏所有查询返回的行数与序列化字节 | 不高于改前 |
| 每日总查询数 | 生产全天 SQL 条数 | 不高于改前（P2 预计少掉约 2／3 的鉴权查询） |
| Neon 出站流量 | Neon 控制台每日 data transfer | 不高于改前；与 D32 的月预算口径一致 |

P0 把以上四项与速度一起记成基线；之后每期上线前后用同一脚本对比，任何一项上升都不放行。

## 5. 设计要点

### 5.1 鉴权：中间件乐观检查 + DAL 权威检查（D31 不变）

- **中间件**：只解 JWT、校验签名与过期（不查库）；未登录直接跳登录 / 401，其余放行。
- **DAL 权威检查**：一条查询同时取回「会话是否仍有效（D31）＋ 注销状态 ＋ 身份（actor / workspace）＋ 引导状态」，每请求实时执行一次。
- **每请求一次的两条路径**：
  - RSC（页面、server component）：React `cache` 包装，同一次渲染内 layout / page / 组件共用一次。
  - Route handler 与 server action：React `cache` 不生效 → 用请求级作用域（`AsyncLocalStorage`）保存本请求的鉴权结果，同一请求内多处取用只查一次。
- **全覆盖保证**（中间件不再是总闸后）：
  - 所有 `/api` route handler 与 server action 统一经 `withAuthenticatedActor()` 包装器取 actor；不经包装器就拿不到 actor。
  - 新增自动化测试：枚举 `app/api/**/route.ts` 的全部导出方法与全部 server action，断言都经过包装器（白名单仅限公开接口与内部定时任务，白名单本身受测试约束）。
  - 保留并作为验收：现有 D31 测试（改密码 / 申请删号后旧会话下一请求即被拒，页面 307、接口 401）与注销门禁测试；新增「中间件不查库」断言。
- **不放在 layout**：layout 在客户端导航时不重跑、也保护不到接口，统一由 DAL 负责。

### 5.2 连接：一个池 + attachDatabasePool；直连还是 pooler

- 合并：9 个池合并为一个共享池（后台任务另设小池，见下），接 `attachDatabasePool`；上一轮「空闲 60 秒」是**过渡**，P1 上线后**被替换**；「空闲连接断线保护」**保留**（attachDatabasePool 之外仍需要 error 监听）。
- 直连还是 pooler：当前直连且 `max_connections = 901`。会话级特性排查结果：advisory lock 全部是事务级（`pg_advisory_xact_lock`），`SET` 全部是 `set local` / `set transaction`，未发现会话级锁、`LISTEN` 或具名预处理语句 → **切到 pooler 事务模式在代码上可行**。但直连在我们的规模下容量充足（见算术），切换带来的收益是连接数保护而非速度。**建议：P1 保持直连，只合并池；连接数监控进 P0，接近上限再切 pooler。**
- 容量算术（活动当天 200 人同时在线）：
  - 每人约每 60 秒轮询 1 次变更游标，加上操作时的突发，估算峰值并发请求约 20–40。
  - Fluid 单实例可并发处理多个请求，按 4–8 个实例估算 × 每实例池 max 5 = 20–40 条连接，加后台任务小池（max 2 × 实例数）。
  - 合计 < 100 条，远低于 901。
  - 风险是实例数随冷启动膨胀；P0 记录实例数，P1 设告警（连接数 > 300）。
- 池大小：页面 / 接口共享池 max 5（沿用 serverless 档位，实测 5 能覆盖一页约十几个并发读）；队列 / 后台任务（名片导入、agent worker、维护）用独立小池 max 2，避免挤占页面请求；事务池并入共享池，事务数受各自 `withTransaction` 控制。

### 5.3 取数：每屏一个视图接口（BFF）

- **定为视图接口**，不做「服务端取数随页面下发」：
  - App 与网页共用同一接口，两端同时受益；
  - 与已上线的「固定框架 + 骨架 + 上次结果 + 变更游标」直接衔接：视图接口的结果整体存进「上次结果」缓存（key = 屏 + 参数），变更游标按区域作废，回到前台重读，不需要改造页面框架。
- 视图接口 = 一次鉴权 + 一次并行取齐该屏首屏所需（只取界面显示的字段），返回一个 JSON。
- 优先级按 P0 实测「冷耗时 × 打开频次」排序，逐屏单独上线。预计顺序：「该聊的人」详情 → 活动（探す / 参加的活动）→ 首页 → 人脉列表 → 活动详情 / 会场页。
- **视图接口只合并、不多读**：只是把原来该屏多次请求读的同一批数据合成一次请求返回——不新增字段，不为了省往返而顺带多读别的数据；列表继续分页（每页条数不变）；只取界面显示的列。
- **子屏不重复返回父屏已有的数据**：父屏视图里已有的字段（例如计划概要），子屏视图不再返回，由客户端从「上次结果」取（上一轮已在「该聊的人」这样做）。
- **预取（保守）**：不在链接进入视口时预取（那样会读用户不一定打开的数据，与读取量约束冲突）。推荐**只在手指按下 / 鼠标按下时**预取该屏视图接口：按下到松开约 100–200ms，能提前这一段；只有按下后又取消才会多读一次，估计多读 < 5%。若 P0 显示这段收益很小，就不做预取，只靠「上次结果」先显示、后台刷新。

### 5.4 活动当天的数据库预热（P5）

| 做法 | 成本 | 失败时后果 | 兜底 |
|---|---|---|---|
| A：Neon API 定时把生产库最小算力调为不休眠，活动后改回 | 活动窗口 0.25 CU × 约 4.5 小时 ≈ 1.1 CU-h／场 | **忘了改回去 → 库全天醒着 → 每天约 6 CU-h，半个月耗尽额度**（与上次同类）；还要在 Vercel 放 Neon API 密钥 | 需要「改回」的二次定时 + 额度告警 |
| B：不改库配置，由已有每小时 Cron 判断「一小时内有活动开始」时发一条预热查询；活动进行中，参加者页面每 60 秒的变更游标轮询本身就让库保持活跃 | 每场多 1 次查询，几乎为 0 | 预热没触发 → 第一批进入的人多等一次唤醒（约 0.5s），之后由真实流量保持 | 不涉及配置，窗口外自动不做；Cron 失败只影响第一批 |

**推荐 B**：不改生产库配置、不引入密钥、失败后果只是第一批人慢半秒；A 的失败模式与历史事故同类，不采用。

### 5.5 区域

Neon 可选区域中离日本最近的就是新加坡（无东京）。若只把函数迁到东京 hnd1，每条查询要多一次东京↔新加坡（约 70ms）跨区往返，一屏多条查询反而更慢；函数与库同在新加坡、用户侧单个 70ms 往返由「每屏一个视图接口」把次数压到最少，是更好的取舍。**结论：不迁移。**

### 5.6 这个方案能不能解决「点开页面加载很久」

以「该聊的人」为例（现状冷 5.6s / 热约 1.5s），各期消掉的时间（估算，P0 实测后回填）：

| 期 | 消掉哪段 | 冷 | 热 |
|---|---|---|---|
| 现状 | — | 5.6s | 约 1.5s |
| P1 连接 | 空闲后每个函数重新建连（实测约 1.1s／请求；页面渲染与 2 个接口各一次，部分并行） | 约 4.0s | 约 1.4s |
| P2 鉴权 | 每个请求少 2 次串行查库；中间件不再连库（冷时中间件那 0.5s 也没了） | 约 3.0s | 约 1.0s |
| P3 视图接口 | 2 个接口变 1 个，少一次「浏览器↔新加坡」往返与一次重复鉴权；父屏已有数据不再读 | 约 2.0s | 约 0.8s |

一级页、活动页同理，P3 合并的接口越多收益越大。

**仍然会慢的情况**：长时间没人用之后的第一次打开（例如凌晨后第一个访问者）。这时三件事叠在服务端：
- 函数冷启动（Next 服务端进程起来，约 0.5–1s）；
- 数据库从休眠唤醒（Neon 缩到零后约 0.3–0.5s）；
- 建第一条连接（直连约 8 个往返，同区域约 0.1–0.2s）。

在**不付费常驻**（不关闭 Neon 缩到零、不让函数常驻）的前提下，这一下的下限约 **1.5–2s**（另加日本↔新加坡的网络往返）。P1–P3 消不掉它，只能保证之后的请求都是热的。缓解办法：
- 首屏先出骨架与「上次结果」（已上线），内容先出、数据随后刷新；
- 活动当天用 P5 做法 B 在开始前预热，让第一批参加者避开这一下。
