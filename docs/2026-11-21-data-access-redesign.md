### 1.3 鉴权链路（按实际 SQL 计，修正 v2「三次往返」的说法）

常见私有接口一个请求的逻辑链：

`proxy：会话检查（auth.ts JWT 回调 → isAuthSessionCurrent，1 条）→ 注销门禁（实例内 15 秒缓存，未命中 1 条）→ handler：auth() 再走 JWT 回调（1 条）→ 读身份：profiles → accounts（通常 2 条，兼容路径 3 条）→ 业务 SQL`

页面导航在 proxy 里还会多一次新用户引导检查（解析 actor + 读 profile，2 条左右）。同一次 RSC 渲染内，layout / page 的 `auth()` 已由 React cache 合并，不重复计。

结论：一个接口在业务 SQL 之前约 **3–5 条串行 SQL**，页面请求约 **4–7 条**；其中会话检查重复 1 次、引导检查放在每个页面请求上。

### 1.4 业务层读取成本（v2 漏掉的，源码可确认，是否占首位待 P0 分解）

| 位置 | 问题 |
|---|---|
| 计划 `overview()` | 先构建完整详情，再构建 `overviewInput`，两者重复读类型与日志（`features/plans/v2/service.ts:1147`） |
| 计划类型详情 | 复用整份计划的输入读取，包括**全部类型**的候选、相关联系人、活动条目（`service.ts:549`）；两端还另请求整份概览 / `overviewRecent` 只为 Step 序号与统计 |
| 活动事实 | 计划先读外部评估、活动窗口、本人活动，再逐场读活动事实；事实「缓存命中」仍重读整份报名名单比条数（`orbit-event-facts.ts:84`） |
| 活动页 | 挂载即并行读评估列表、未来活动、过去活动、可用时间，**不管当前在哪个页签**（`EventsScreen.tsx:97`）；探す 另读目录，目录内部再建计划上下文、逐场判断最多 40 场（`journey/service.ts:101`） |
| 冷路径 | 活动评估首次使用在请求路径上跑运行时迁移检查（`assessment/configured.ts:157`） |
| 计划读取持连接再借连接 | 计划仓储读取借出一条连接开只读事务，回调内 `buildDetail()` → `reviewBudget()` 又向另一个事务池借连接（`plans/v2/repository.ts:631`、`service.ts:457`、`service-factory.ts:56`）——合池后会死锁式等待 |

### 1.5 App

App 保存 Auth.js 会话 cookie、在 `Cookie` 头携带，与网页走同一条 proxy + handler 鉴权链。App 类型详情也并行请求类型详情与 `overviewRecent`（`PlanTypeScreen.tsx:90`）。App 的耗时按**依赖链**计（并行请求取最慢者），不是「接口数 × 单接口耗时」。

## 2. 成熟做法对标（不变，摘要）

| 主题 | 做法 | 出处 |
|---|---|---|
| 连接 | Fluid 上 `pg` + 池 + `attachDatabasePool`：管理挂起前的空闲连接生命周期；**不能消除新实例的第一次建连，也不能跨实例共用池** | Neon「Connecting to Neon from Vercel」、Vercel「Connection pooling with Functions」 |
| 鉴权 | proxy 只做乐观检查；权威检查在 DAL，每请求一次；不以 layout 作为安全总闸 | Next.js Authentication 指南 |
| 读取 | 先消除重复读与无关读；客户端「上次结果」+ 资源级新鲜期 + 在途去重 + 写后失效 | SWR / TanStack Query |
| 聚合 | 只在确有跨模块首屏依赖的屏幕做视图接口；两端共用读取服务，Web 首屏可服务端调用同一服务 | BFF 实践；Codex 审阅 §4 |

## 3. 约束与取舍

- **D31**：改密码 / 申请删号后，之前的会话在任何实例上下一次请求即被拒。**不放宽**（原 P6 删除）。
- **注销门禁**：与 D31 同为安全门禁，只在 DAL 实时查，不进令牌、不加跨请求缓存（现有实例内 15 秒缓存属既有窗口，迁移时一并评估是否保留，见 §5.3）。
- **读取量**：每期上线后同场景 SQL 数与返回量不增加；按访问量归一化后的总查询不增加，并保留总量护栏。
- **成本**：不常驻心跳、不关闭缩到零、不付费升级、不迁区（Neon 无东京区域；函数迁东京会让每条查询多一次跨区往返）。

## 4. 验收标准

1. **主内容更早出现**：以浏览器端「主内容出现时间」（主要内容块渲染完成，非骨架）为准，同场景、同版本数据、同操作序列对比。
2. **同场景 SQL 数和返回量不增加**（P1、P3 应下降）。
3. **真实流量不明显增加**：日总查询按访问量归一化后不增加，总量护栏；Neon 控制台每日出站流量不明显上升（读取指标里的字节是 JSON 序列化估算，不等于 Neon 实际流量，二者分开看）。
4. **D31 完整成立**：在最终入口（页面、接口、Server Action、`/api/auth/session`）上验证，覆盖跨实例撤销、并发、存储故障。

不以「接口数量变成 1」「类型检查通过」「截图一致」作为速度或读取量的验收。

## 5. 分期（顺序按审阅建议重排；每期单独上线、可单独回退；上线均需部署授权）

### P0 轻量测量（闸门）

- **只走日志专用通道**：不复用读取收据通道（它在生产会 insert `orbit_read_receipts`，`read-receipts-sink.ts:76`）。新增仅写运行日志的计量，限定记录期 1 周，采样开销可控。
- 口径：
  - 服务端分段：连接等待 / 实际建连 / SQL / 渲染，并行 SQL 不把耗时相加当墙钟。
  - 四种场景分开：新实例、连接过期、数据库休眠、客户端缓存命中。
  - 按访问量归一化每屏查询数、返回行与字节。
  - 浏览器端：资源加载、JS 执行、主内容出现时间。
- 固定同一版本、数据、操作序列；用当前 60 秒 idle 的版本重测（旧数据是 10 秒版本）。
- 回滚：开关关闭计量。验收：产出逐屏基线表（时间 + 读取量），回填 §1.2，并据此确认后续各期的预期。

### P1 读取去重（性价比最高，直接减少读取）

- 计划：一次计划读取内复用类型、日志、活动事实；`overview()` 不再重复读；类型详情只读本类型所需，并从已读数据生成 Step 序号与统计，两端不再为这几个字段请求整份概览 / `overviewRecent`。
- 活动事实：缓存命中时改为只读报名人数（计数），不重读整份名单。
- 活动页：只读当前页签所需，保留确实需要的公共计数（如页签上的数字）。
- 冷路径迁移检查：移出请求路径，改为部署时执行（与现有「生产迁移放进部署构建」做法一致）。
- 补齐现有客户端缓存：资源级新鲜期、在途去重、写后失效；**计划 / 活动没有变更游标区域**，失效方式为：本会话写后作废（已有）、回到前台重读（已有）；不新增轮询区域（新增区域会增加每次轮询的读取，需单独评估成本后再定）。
- 直接打开子页面（无父数据缓存）时仍能完整取数。
- 回滚：每项一个提交。验收：同场景 SQL 数、返回量下降，主内容出现时间不变或提前。

### P2 连接生命周期

- 给**现有各池**接 `attachDatabasePool`（不合池），保留 error 监听；上一轮「60 秒 idle」在此期被生命周期管理**替换**。
- 只治理挂起时的空闲连接，**不承诺消除新实例第一次建连**。
- 回滚：单独提交。验收：P0 场景「连接过期」的建连耗时与占比下降，无连接泄漏告警。

### P3 统一 DAL，再撤 proxy 查库

- **新 DAL `verifyRequest()`**：一次查询（或一次事务内）取回会话有效性（D31）+ 注销门禁 + 身份（profiles / accounts）+ 引导状态。
- **auth.ts JWT 回调里的查库**迁出：JWT 回调只解码；所有需要会话的入口改用 DAL。`/api/auth/session` 在返回会话前先过 DAL，旧会话返回空并清 cookie（与现行为一致）；`/api/auth/**` 不整体视为公开。
- **每请求一次**：
  - RSC 页面 / 服务端组件：React `cache` 包装 DAL，单次渲染共用。
  - Route Handler / Server Action：每个入口建立独立 ALS `run()` 作用域，**立即**保存鉴权 Promise（并行调用不各查一次）；不跨 HTTP 请求、不假定跨实例共享。
  - **不进入跨请求去重**：沿用现有「每次撤销检查唯一 key」的规则（`session-revocation.ts:83`），不按用户共享在途 Promise。
  - 私有业务缓存命中前，仍先完成本请求的实时校验。
  - 保留注销门禁的路径 / 方法例外与 canonical account / workspace 归属语义。
- **layout**：继续读取初始化 `SessionProvider` 与导航壳所需的身份，但不作为安全总闸。
- **全覆盖**：统一包装器；自动化测试枚举全部 `/api` 路由方法、Server Action、`app/(app)/app/**/page.tsx` 与读数据的服务端组件，断言都经过 DAL（公开白名单受测试约束）。
- **验收（最终入口）**：页面 307、接口 401、Action 拒绝、`/api/auth/session` 返回空；跨实例撤销（两个服务进程，一个撤销、另一个下一请求被拒）；并发（撤销提交后才开始的请求必被拒）；存储故障时失败即关（与现行为一致）。现有直接调 proxy 的集成测试（`session-revocation-auth-integration.test.ts:119`）改为验证最终入口。
- 全部通过后才撤掉 proxy 里的查库。回滚：开关恢复 proxy 查库（并存一版）。

### P4 分批合池、按实测做聚合

- 先列出全部「持有连接时再借连接」的调用。方法：静态检索 `pool.connect` / 事务回调内对其他池的调用，加上运行时检测（借出期间再借即打日志，P0 / P1 期间开启）。已知一例：计划读取 → `reviewBudget()`。改法：传递已有 executor，或把独立查询移出持连接范围。
- 修完后分批合池：统一连接配置、关闭所有权与计量层，避免某模块关闭共享池、同一 SQL 重复计量。
- 容量：按实际 compute 配置（CU 与对应 `max_connections`）、函数实例分布（含滚动部署、后台任务）、连接持有时间重算；P0 记录实际峰值连接数后再定告警阈值。直连暂时保留。
- 聚合接口只给 P0 / P1 后仍存在跨模块首屏依赖的屏幕；两端共用读取服务，Web 首屏是否由服务端调用同一服务按实测决定。并行接口合一不自动减少串行往返，收益以实测为准。
- 回滚：每批一个提交。

### 暂缓 / 删除

- **服务端缓存**：另行评估（失效与读取成本）。
- **活动当天预热（原 P5）**：暂缓。原做法 B 无法可靠预热（Neon 空闲 5 分钟即休眠；整点维护任务本身已访问数据库；用户轮询会因页面不可见而停止）。若以后需要，应是临近入场、次数有硬上限、自动结束的活动级一次性触发，并先算成本。
- **按下预取**：当前约束下先不做（额外读取没有证据）。
- **放宽 D31（原 P6）**：删除。

## 6. 能否解决「点开页面加载很久」——待验证假设

v2 的固定数字（5.6s → 2.0s 等）删除，改为待 P0 验证的假设：

- P1 减少计划、活动的重复读与无关读，预期同时缩短等待与减少读取。这是对「该聊的人」和活动页**最有把握**的一期。
- P2 降低「连接过期」场景的建连占比；对新实例的第一次建连无效。
- P3 去掉每个请求上重复的会话检查与 proxy 里的引导检查，减少串行 SQL；对 App 与网页同样有效。
- P4 视实测决定。

仍会慢的情况：长时间无人访问后的第一次打开，会同时遇到新实例、数据库唤醒、第一次建连。本方案不承诺这一下的时长，只通过「骨架 + 上次结果」让内容先出；具体组成与时长由 P0 的四种场景分开测出后再写。
