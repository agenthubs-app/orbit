# Sprint 0070 — 三层数据流测试拓扑与读取成本基线

## 要实现什么

把设计案 Rev 4 图 6 的三层拓扑做成可重复执行的测试：**本机 Postgres 扮演云端**，装全量多用户数据
（用户 A、用户 B、主办方）；**客户端镜像只装当前登录用户自己的行**；授权过滤只发生在服务端同步接口这一处。
同时把"一次业务操作花了多少次 SQL、多少行、多少字节"做成账本，冻结当前基线，作为后面所有读取优化 Sprint 的验收尺。

## 做完能看到什么

- 跑一条测试就能回答"A 登录时，B 的数据有没有漏进 A 的镜像"——host 里同时有 A、B、主办方，
  A 的镜像里 B 的行必须为零；这不是靠读代码相信，是断言。
- 切账号：A 登出、B 登录，A 的镜像不可读；B 拿不到 A 的行。撤权：host 侧撤销 A 某域授权后，A 的该域镜像清空。
- 三次拉取呈现 **全量 → 增量 → 0 行**：首次同步拉全量，写入一条后只拉这一条，再拉一次一行都不传。
- `tests/performance/read-cost-baseline.json` 记录每条操作链（联系人列表、待办、笔记、看板、活动）的
  `{queries, rows, bytes}`；测试断言当前成本不超过基线——后面的 0071（LIMIT/投影）必须把这个文件往下改，
  而不是往上。
- 同一操作链跑两次得到完全相同的数字；把预算调到比实际低一点，测试必须变红——证明这把尺子会咬人。
- `npm test` 不再静默漏掉 `tests/*.test.mjs`（0068 发现的缺口）。

## 怎么验收

全部在本机跑，不连云端。三层拓扑用 0067 带来的"非本地数据库 URL 拒绝"闸门保护。
服务端侧用 0069 已落地的 `/api/sync` 读取服务和 0067 的联系人 scoped reader 做被测对象；
客户端侧用 App 既有的 v2 本地仓库与测试用 SQLite 做镜像。Web 侧当前如实断言为 online-only，0077 再扩。
按常设要求，收口时起 Simulator 与 phoneweb 各跑一次确认无回归（本 Sprint 不改产品代码，属无回归确认）。
