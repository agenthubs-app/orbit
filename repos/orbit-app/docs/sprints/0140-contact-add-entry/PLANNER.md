## 已确认的设计与事实

- 现有 App `prepareBatchImage` 在读取前就拒绝超过 10 MiB 的图片，上传 API 和服务端也有 10 MiB 二进制上限。服务端仅对已通过大小检查的 HEIC／HEIF 做转码缩边，不能挽救超限原图。直接扫描页目前从相机／相册取得 base64 和原文件大小；批次流程还包含正面、反面、补拍、替换及 phoneweb 选图。
- 压缩属于客户端上传前步骤：超限图片先生成本机可读的较小副本，再以该副本的真实字节数、格式和 URI 走后续校验／上传；批次 manifest 的摘要必须取自实际上传的副本，直接扫描请求的 `imageSizeBytes` 也必须是副本大小。原图保留在本机且不误作已上传图片。未超限的图片不额外压缩。处理后仍超限、格式不受支持、无法读取或用户取消时，给出可恢复的错误，不发起上传或创建联系人。压缩后的名片文字必须仍可供用户核对与 OCR 识别；尺寸／质量策略须写成确定性代码并用样本验证，不由模型临场决定。
- 扫描入口的目标是[方案 C 黑白版](../../designs/2026-10-03-card-scan-simplify/README.md)：标题“扫描名片”，提示“选择一种方式”，仅有“拍一张名片”和“从相册选择”；底部“核对信息后，再保存到人脉”。进入核对页用“核对名片信息”，最后明确“保存到人脉”，成功提示“已保存到人脉”。相机权限在选择拍摄后才请求。
- 手动添加的目标是[方案 2 姓名先行](../../designs/2026-10-03-manual-add-redesign/README.md)：从人脉页独立进入；姓名必填，先显示姓名／公司／职位，展开“补充关系信息”后填写关系备注／下一步／标签。主按钮“下一步：核对信息”，提示“核对后再保存到人脉”；核对后再明确保存。
- 当前 `/contacts/new` 由 `ContactAcquisitionScreen` 承载名片、QR、手动来源标签及额外导入卡片；`ContactsScreen` 有手动添加和扫描入口。重排用户入口不等于删除 QR、外部导入、引荐、重复检查或它们的业务能力。
- 0007 已实现本地双面名片聚合与一次创建，但实体 iPhone、真实 OCR 和同一联系人跨端回读仍受阻；0140 不代替其关闭条件。Bridge BR-012 是现有共享契约。
- 编制时 GitNexus `prepareBatchImage` 上游 impact 为 LOW，9 个已索引影响点，包含正面／反面选择、批次复选、替换和上传；该索引落后工作树，实施前必须在实际基线重新分析，不能用 LOW 跳过直接扫描页或 Web 的文本补查。

## 一次 Generator 的执行顺序

1. 实施获准后冻结 Planner、基线和文件边界；确认与其他进行中线路无覆盖。实现前逐符号 impact，HIGH/CRITICAL 风险先报告，UNKNOWN 以文本补查。
2. 先写大图压缩、真实上传字节／摘要匹配、压缩失败不上传的行为失败测试，再在相机／相册取图后、10 MiB 校验与网络请求前接入有界本机处理；复核双面、替换和 phoneweb 的路径，不改变服务端上限或按卡确认语义。
3. 按用户操作链先写扫描与手动页的失败行为测试，再以最小改动接线两个入口；不把“生成候选”一词留在用户可见的确认按钮上，也不改变底层确认语义。
4. 跑图片处理、定向交互、view-model、类型检查以及实际受影响消费者；按影响范围决定是否需要 App 集成检查。真实相机、OCR 或联系人写入若缺环境／对象授权，只暂停对应验收，不把它记成通过。
5. 按 Sprint RULES 完成图变更分析、报告和主线交接；未获实现授权时止于定义文档，不启动 Generator、不提交或合并代码。

## 失败与交接

三项问题均已纳入定义；第一项的“过大”按现有客户端和服务端 10 MiB 二进制上限解释，不擅自更改服务端阈值。若 App 处理后仍受 HTTP 请求体限制，须在实现报告中给出实测值与失败原因，再调整客户端目标或提出明确的契约变更，不把失败写成通过。0007 的实体设备／OCR／跨端遗留验收仍独立存在。Bridge 交接须记录本端版本、另一端影响、未完成项及验证范围。
