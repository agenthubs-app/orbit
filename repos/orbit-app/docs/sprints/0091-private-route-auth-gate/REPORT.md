# Sprint 0091 报告 — "正在确认登录状态"六秒：前提不成立

**状态:** 见登记表（**failed**）。**run-01。** 不是实现失败，是**要修的东西不在了**——这条也要如实记，不能因为"结果是好的"就当没发生。

## 结论

复核记录的"六秒以上"**无法复现**。同一 phoneweb、同一演示账号、同口径重测三轮：

| 路由 | 冷跑一次 | 第二轮 | 第三轮 |
| --- | --- | --- | --- |
| `/followups` | 193ms | 142ms | 147ms |
| `/contacts/dashboard` | 2241ms | 280ms | 176ms |
| `/ai` | 1419ms | 177ms | 124ms |

第一列是重新 `expo export` 之后的首次导航，缓存未热；随后稳定在 124–280ms。没有六秒，也没有需要拆解的耗时构成——**SC-0091-01 和 SC-0091-03 因此无法产出有效证据**。

## 归因

复核当时磁盘只剩 226MB。同一轮复核还产生了 82 条后来证明是环境造成的测试失败。六秒最可能与它们同源，而不是 `auth.ready` 本身的问题。这一点是推断，不是实测——当时的环境已经不在，无法回放。

## 做过并已撤销的改动

度量前我先试过一个看起来显然的提速：把 `sync-lifecycle.web.ts` 里 `expo-sqlite` 的静态 import 改成动态，让它离开登录门的关键路径。

1. **第一次度量是无效的**：三条路线复用同一个浏览器 context，WASM 已被缓存，"改后"反而比"改前"慢。
2. 换成冷 context、并对调先后顺序重测，结果是**没有变化**。
3. 原因写在代码里：那行静态 import 是 0077 特意留的——动态 import 会把 expo-sqlite 挪进异步 chunk，Expo 的 serializer 随后把与 sqlite Worker 共用的模块搬进 `__common.js`，而 Worker 从不加载它（"Requiring unknown module"）。

改动是个 no-op，而我给它写的注释声称它"从登录门上省掉了几秒"。**已整体撤销**，代码回到 0077 的形状。

## 剩下的两条仍然成立，但不该由本 Sprint 承担

- `OrbitRouteAccessBoundary.tsx:34-42` 确实只有三态，没有"已有本地会话、正在后台校验"这一档（Planner 事实表第 2 行）。这是结构事实，与六秒无关；要不要加这一档是**安全语义决定**（Planner 判断 2 已写明不在本 Sprint 内自行放宽），没有性能压力推动它，就更不该顺手改。
- `useSyncedCollection.ts:165-172` 会跟着 auth 一起等——在 auth 只要 200ms 的情况下，这不是问题。

## 教训

先复现，再度量，再改。这一轮的顺序反了：我先假设症状在、直接去找提速点，做出一个 no-op 还给它写了个夸大的注释。度量之所以最终没骗过去，是因为第二次换了冷 context——如果当时接受了第一次那份"改后更慢"的数据，我会得出一个同样错误的相反结论。
