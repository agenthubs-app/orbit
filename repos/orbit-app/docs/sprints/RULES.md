## 1. 用户指定的 long-run-harness 简化版

保留：SprintContract（可验证验收项）、Handoff（上下文交接）、existing-codebase 文件边界、证据归档、预算、逐功能提交和明确终止。
取消：独立 Evaluator、打分／rubric、契约协商循环、self_assess 模型调用、REFINE/PIVOT、最小迭代次数、评审后自动再次 Generator。
本规程是文档驱动，不新增 Python／TypeScript SDK 编排程序，不选择或安装额外 provider／模型。若以后要实现后台调度器，其语言、模型与权限需要另行设计，不能假定本文已授权。

`已批准 PLANNER.md → 一个 Generator 执行 → 必要验证 → Sprint 分支 commit → REPORT.md／交接 → 协调者合并 chat-agent → 合并树验证 → 结束`

“一次”指同一契约的一次完整执行，不是只允许一次工具调用。Generator 可正常阅读、TDD、编辑、运行命令和有限修复；不能以自评分、外部 AI 评审或“再优化一版”为理由重开生成阶段。每个 Sprint 最多一次 Generator run，执行前登记为 run-01。

## 2. 角色与并行

- Planner 是每个 Sprint 的 `PLANNER.md`；本轮编制，不在运行时再启动 Planner 模型。它定义目标、输入、输出、范围、SC 验收项和必要检查。
- Generator 是该 Sprint 唯一实现者，承担范围内实现和基于证据的自检；禁止再派另一个实现／评审代理形成隐式循环。
- 协调者只领取就绪任务、管理文件／环境锁、维护登记表和统一 Git 集成，不增加一个模型评判阶段。Generator 在自己的 Sprint 分支提交本线改动；协调者核对最终 SHA 后合并到主线 `chat-agent`。Generator 就是当前主代理时可直接承担这些管理动作。
- 默认逐个执行。确需并行时最多两个独立就绪 Sprint，各自一个 Generator；必须预先确认文件不重叠、没有依赖和共享运行环境争用。不是一个 Sprint 同时派两个 Generator。
- 共享工作树中只有协调者操作暂存与 commit；通用 API/hooks、语言／时间基础设施和跨页共享 view-model 不并行修改。完整类型／全量测试前冻结全部相关写入者。
- 同一 Simulator、浏览器账号、真实写入对象、付费账本和服务生命周期只有一个持有者。暂停一个界面步骤不等于允许另一个代理切换其账号。
- 同一代理可合并独立只读查询，并行执行互不争用的定向检查。重测试运行期间继续必要的只读调查，不修改被测版本、不启动重复进程；先看原句柄。多个浏览器／数据库重套件争用资源时顺序执行，不靠增加进程数提速。本次提速不授权额外 Generator 或评审代理。

- 四位十进制编号从 `0001` 递增；已登记编号不复用、不重排。目录为 `NNNN-short-name/`，新增 Sprint 用下一个空号。
- 本目录 `README.md` 是全局运行状态和 Sprint 生命周期的唯一登记表；每份 Planner 不复制一份可变运行状态。
- 每个 Sprint 必须有 `GOAL.md`：一句话说明要实现什么，列出具体可见结果，再用短段说明怎么验收。用用户操作或交接成果描述，不只写技术名词；它是 Planner 的易读说明，不另设验收契约，也不记录可变状态或提前声称完成。
- `PLANNER.md` 是本 Sprint 的唯一契约。必须包括原需求编号、基线、依赖、白名单、排除范围、最多五项可验证 SC、测试映射、失败处置和交接。
- 目标页和登记表中的目标必须与 Planner 一致，不能补写未批准功能或省去必需验收。给已执行 Sprint 补目标说明时，保留冻结的 Planner、哈希和历史报告；有真实契约变更仍走原审阅流程。

- `REPORT.md` 仅在实际执行结束后创建；失败／受阻也必须报告。模板不能作为实际完成报告，不能提前填成功。
- 中断时先保存脱敏 `checkpoint.md`：已改文件、已提交 SHA、未完成、活进程句柄、当前测试与预算。恢复同一未结束 run，不清空工作重开。完整报告已关闭该 run 后不得当“恢复”启动第二次生成。
- 原计划继续保存全部 R-00～R-14 需求；新的 Sprint／报告只记录其自身范围，不把依赖移动等同需求删除。

## 4. 启动前最小检查

1. 读规则、本 Sprint 目标页、Planner 和它声明的前序报告；目标页不能代替 Planner，不反复遍历全部历史。
2. 查看当前 HEAD、`git status --short` 和计划涉及文件的 diff。未知用户改动不得覆盖；0001 只承接明确列出的既有四文件。
3. 按第 0 节复用适用批准，核实依赖／环境／对象和当前暂停状态。用户明确恢复后先同步过期登记，不把旧 PAUSED 或“待审”标签当成新的审批门槛。确实缺前置则只暂停对应动作，不消耗 Generator run，不尝试假接口；继续独立调查或其他已就绪 Sprint，整体停止须满足第 11 节。
4. 分配唯一 owner／文件锁，登记 run-01、Planner 哈希和基线。没有此登记不开始编辑。
5. 仅当旧结果不能证明当前版本或修改影响扩大时重跑基线。发现基线失败时，保留已有专项批准门槛，不自行跳过。
6. 每个待改符号先 GitNexus upstream impact；固定 `repo: "/Users/xzhao/Projects/orbit"`，避免同名旧 worktree。HIGH/CRITICAL 先报告；索引未收录用源码补查，不能视为无影响。工具提示 stale 才按项目规则刷新，保留根 AGENTS 不被生成覆盖。

同一 run 已完整读过且未变化的规则、技能和源码可复用，不在每次检查点重读整套文档。恢复时先核对最新用户指令、当前 diff、原进程及已有记录，仅补读缺失或变化部分；首次必读要求不省略。已完成的同一符号 impact 在目标和相关调用关系未变时复用，新增符号或依赖变化再分析。允许一次批量查多个待改符号，不用“查询→长汇报→再查询”切碎工作。

选定一个可验证的用户操作链后连续实现：接口、消费者和失败保护尽量在同一批完成。事实已能从源码确定就直接落地，不再为已批准功能反复写候选方案或新增准备文档；只在目标／安全边界有新冲突时暂停相关动作。

## 5. 最小执行与测试设计

每个 SC 对应一个可观察行为及一个主要验证方式。默认路径是“改变行为的 RED→最小实现→定向 GREEN→操作链收口”，不是“每改一处→全量”。测试集按实际影响选择，不能因文件名字包含 profile／auth 就运行整个相关目录。

### 5.1 分档与全量触发

| 验证档 | 适用条件 | 必需检查 |
| --- | --- | --- |
| D 文档／只读盘点 | 不改变运行行为 | 必要路径／链接、规则冲突和diff检查；不跑产品测试或typecheck，不为文字新增源码断言测试 |
| L 局部实现 | 影响边界清楚且不触发H的局部功能 | 开发时只跑改变行为的用例；该操作链提交前跑修改测试所在完整文件及实际受影响的直接消费者，相关端typecheck一次。默认不跑全量 |
| H 高风险／共享实现 | HIGH/CRITICAL，或身份／权限／写入／幂等／通用基础设施／共享契约发生变化 | 定向集必须覆盖相关失败、隔离、并发及传递消费者；可在这些检查通过后提交独立功能。全量延后到本 Sprint 本地代码收口，不逐子功能触发 |
| I 集成收口 | 含H变更的 Sprint 本地代码收口、明确集成 Sprint 或最终主链路验收 | 仅受影响端运行一次全量与尚未覆盖的类型／同步检查，加该阶段实际业务／设备 SC；没有变化的另一端复用有效证据 |

删除“三个L提交后自动全量”的计数规则；提交次数、检查点、文档变更和上下文恢复都不是全量触发器。纯L Sprint 用定向验收收口即可。含H的 Sprint 即使暂缺真实账号／设备，也在本地代码交付时做一次I检查，不能以外部阻塞无限推迟集成验证，亦不能据此把外部SC标记通过。

仅以下证据可提前／再次触发全量：依赖或测试／构建基础配置改变；多个原本无关模块出现回归且无法可靠圈定影响；修改使上一轮全量覆盖的其他路径失效；用户明确要求。运行前用一句话说明“改了什么、为何定向集不够、测哪一端”，这是说明，不新增审批。局部实现修复、测试夹具修订或文档更新本身不要求全量重跑。

### 5.2 测什么、何时复用

- 一项业务规则优先在所属层测一次；UI只测接线、可见结果及UI特有状态，不在每层复制整套输入组合。优先复用真实路由／HTTP边界夹具；不新增管理用产品接口，不测mock自身，不为常量、私有实现文字或覆盖率数字堆测试。
- 每条新增路径覆盖正常结果和最相关的失败边界；身份、隐私、并发、重试等发生变化时必须加对应反例。语言×字号×账号×状态的全排列只在这些维度确实影响行为或SC明确要求时运行；没有变化的视觉、OCR、AI或其他页面不陪跑。
- 开发时可用精确文件／test-name筛选快速反馈，不能拿被筛掉用例的报告充当完整文件通过。操作链收口再跑必要完整文件；共享夹具或helper变化时，包含实际受影响的使用者，不只看失败用例。
- typecheck按操作链、相关端运行，不逐文件／逐断言运行；仅文档或运行记录改变时不跑。契约／schema／字典源文件改变才运行sync；其余场景不重复生成。本库`npm test`已含三项同步检查，不与同版本成功检查重复跑。
- 证据按“命令＋相关源码／测试／依赖／环境版本”复用，不因无关commit或文档SHA变化作废，也不把旧结果冒充新执行。同一检查支持多个SC只运行一次；有变化仅重跑覆盖变化的检查，记录复用依据和待完成的I检查。

### 5.3 失败后的最短验证路径

TDD 不是被取消的 Evaluator 循环：观察预期失败→最小实现→必要回归仍保留。已存在且版本未变的 RED 记录可承接。非预期失败先定位；同一失败最多两个本地修复轮次（内部循环上限，不是用户费用额度），每次只重跑失败用例及受影响最小集，仍不过则结束为 failed。既有“同一假设最多三次只读诊断”上限亦保留。不得提高任一用户硬预算。

全量出现单个局部失败时，保留原日志，定位并修复后跑该完整文件和受影响消费者；未命中5.1的再次触发条件就不再跑全量。交接如实写“全量曾失败，局部修复回归通过”，附原全量与后续diff，不能改记为“最终全量通过”。既有获准基线失败按名称和影响对照，只调查新增或被本次变更影响的项，不每轮重新诊断整份旧失败清单。

无需额外Lighthouse、axe、构建、全平台截图或全用户旅程，除非SC或实际影响需要。原生体验用原生证据，跨端持久化用同记录双向回读；缺环境单列，不用便宜单测替代，也不靠跳过必需SC换取完成。

### 5.4 App 开发期间的 Web 运行门槛

- 涉及 App 可见行为、HTTP API、共享契约或跨端状态时，必须启动一套 App 实际可访问的 Web/API 服务，并让 Web 浏览器与原生 App 登录同一验收账号、连接同一数据库。组件测试、mock service、路由单测或仅启动 Metro 都不能替代该运行时验收。
- Web/API 或共享契约源码发生变化后，现有 Web 进程的证据立即失效。先停止旧进程，在目标环境完成 Web 生产构建，再启动新产物并检查健康端点；随后才运行 App 验收。不得让 App 对着修改前的 Web 进程验证修改后的源码。
- 每轮跨端证据至少记录 Web commit、构建结果、启动地址与模式、数据库／账号的脱敏标识、App API base URL、App 构建版本，以及同一记录的 Web→App 和 App→Web 回读。服务重启后重新确认登录与健康状态。
- 本地共同环境可以证明本地跨端契约和原生运行行为；只有发布验收明确要求远程或实体设备时，才必须另补对应部署或物理设备证据。报告必须区分本地生产进程、远程部署、iOS Simulator 和实体设备。

- Python 工具始终经 `uv` 环境运行；本规程不需要 Python 编排器。

## 7. 状态与失败终止

| 状态 | 条件与允许下一步 |
| --- | --- |
| planned | 计划已写，未完成启动就绪／批准；不执行 |
| ready | 进入条件与适用批准齐全，仍需全局 ACTIVE 才能领取 |
| running | 唯一 Generator 的 run-01 正在执行 |
| paused | 同一 run 因用户暂停或中断待恢复；先留 checkpoint，不默认重启未知活进程 |
| completed | 本 Sprint 所有必需 SC 有同版本有效证据，功能与报告已提交，固定最终 SHA 已合并到 `chat-agent`，且合并树验证通过；不代表所有 R 项完成 |
| blocked | 缺外部条件；启动前 run_count=0 可在条件齐全后 ready；运行结束后 run_count=1 必须交报告，不能直接再运行 |
| failed | Generator run 已结束，必需 SC 失败／预算到限；保留部分成果和报告，不自动二次生成 |

completed 由验收清单逐项事实决定，不由 Generator 的信心、平均分或“看起来差不多”决定。failed／已结束 blocked 若需再实现，由 Planner 明确补新 Sprint（关联原失败 SC），复用仍有效的批准；重大变更重新审阅。不得自动克隆失败 Sprint 换编号绕过单次限制。原 Sprint 保留失败事实，新 Sprint 成功不能改写历史。

## 8. 提交与总结

提交单位是可独立验收的用户操作链或确有消费者可复用的能力；同一链路的类型、存储、界面和错误处理尽量合成一批，不把每个helper或测试修订拆成“功能”。完成第5节对应定向检查后路径限定提交；需要I检查的中间提交明确标记“集成待验”，不因此宣称Sprint完成。已经形成独立交付不拖到整个项目结束，也不为增加提交数拆分工作。

提交前必须：
- 对照 Planner 文件表及第 0 节的追加记录审查实际 diff 和行为覆盖；只暂存该功能明确文件，禁止 `git add .`／`git add -A`。
- 执行 `gitnexus_detect_changes({repo: "/Users/xzhao/Projects/orbit", scope: "staged"})`，核对意外流程与其他 Sprint 改动，必要时补测。
- 对当前提交版本完成第5节适用检查和相关SC证据；未到收口点的全量不作为中间提交门槛。保留失败历史，未满足必需功能门槛不提交成“已完成”。
- 在 `REPORT.md` 列：需求／SC→文件变更→功能 commit SHA→验证证据；未提交改动、失败、回退方式、其他端影响、下一步和预算单列。
- 报告先用易读文字说明目标实现情况：已验证能做什么、仍不能做什么及原因；再列技术证据。不能把目标页的预期结果直接复制成已完成成果。

功能 commit 完成后再填写真实 SHA 并单独提交报告／登记表，如 `docs(sprint-0001): record execution report`。报告以最后功能提交作为被验收 HEAD，不要求写入包含报告自身的 commit SHA；它可由 Git 历史查到，避免自引用不断提交。部分失败、纯文档或“无需改代码”的 Sprint 也要报告，不能虚构功能 SHA。

运行中只维护一份简短进度／checkpoint；不在每个小提交后同时重写README、PROGRESS、交接和总结，也不强制配一条纯进度文档commit。生命周期、授权／文件边界变化及时登记；普通验证细节留在原日志和当前记录，Sprint结束时一次汇总REPORT／登记表。对用户的简短进度更新照常，不把写报告当成实现工作。

### 8.1 Sprint 必须提交并合并回主线

每个 Sprint 的实现收口必须完成以下 Git 闭环；任何一步缺失都不能把 Sprint 标为 `completed`：

1. Generator 只暂存本 Sprint 的源码、测试和报告，执行 staged `gitnexus_detect_changes` 与适用验证后，在本线命名分支创建 commit；不得把其他线或用户的未提交文件带入。
2. Generator 在交接中给出分支名、最后功能 SHA、报告 SHA、工作树剩余改动和完整验证结果，然后释放文件／环境锁。只有“改动仍在工作树、尚未 commit”不算交付。
3. 协调者以交接中冻结的 commit SHA 为输入，不使用仍会移动的分支 HEAD；确认依赖顺序、提交归属及主线状态后，把该 SHA 合并回 `chat-agent`。执行线不得自行并发合并主线。
4. 冲突只按两端已批准行为解决，不丢弃任一条线；冲突修改需补 impact／测试。合并后在精确合并树运行受影响测试、相关端 typecheck，以及第 5 节要求的集成／构建／运行时验证。
5. 合并验证通过后，协调者在登记表／交接中记录 Sprint 最终 SHA、`chat-agent` 合并 SHA 和验证证据，才可写 `completed`。若合并或合并后验证失败，保留分支和 worktree，状态继续为 `running`、`blocked` 或 `failed`，不得假报完成。

若 Sprint 以 `blocked`／`failed` 结束，已经独立验证且可安全复用的部分仍应路径限定 commit，并在报告中明确“部分提交、未完成”；是否合入主线由协调者按依赖和兼容性决定，但部分合入不会把 Sprint 状态改成 `completed`。远程 push 只有在已有适用授权时执行；push 后必须核对 `origin/chat-agent` 与本地主线 SHA 一致。

## 11. 自主推进与整体停止核查

遵守根 [AGENTS.md 的自主执行与停止条件](../../../../AGENTS.md#自主执行与停止条件)。协调者在现有执行清单或 checkpoint 中维护“可执行、可调查、等待决定”三类动作；它们不是新的 Sprint 生命周期状态，不替代 README 登记表，也不消耗 Generator run。

单个 Sprint 不满足启动条件、完成报告或按规则结束为 failed／blocked，只结束该 Sprint 的对应步骤或 run，不自动结束用户授权的整体任务。原单次 Generator、文件锁和失败重试上限保持不变；不得重开已结束的 run 绕过这些限制。文件补充和批准复用依第 0 节办理，不再把它们误判为新的审批阻塞。

因阻塞结束整体任务前，必须逐项列出剩余任务的具体缺项、证据、受影响动作，以及为什么不能继续任何独立部分。若仍有已授权且有价值的实现、调查或待审方案完善工作，先执行下一项；不能仅凭登记表没有 ready Sprint 就停止。阶段性提交／检查通过不是整体完成，不用重复文档、无关测试或空等填时间。

核查场景：A 等设计批准、B 已满足实现条件、C 可安全调查且三者互不依赖时，隔离 A，继续 B 和 C；不得为实现 A 绕过审批，也不得因 A 停止全部工作。只有用户暂停、任务完成、明确硬限额或真正全部受阻才结束整体执行。

自动续跑时先复核最新用户批准、实际工作区和当前进程句柄，区分已经完成、仍在运行、可立即执行及真正缺少外部条件的动作。旧“缺批准”标签、某个进程已结束或连续几次没有提交，都不能单独证明整个目标受阻。若进程仍在运行，观察原句柄；若已结束且有就绪动作，直接继续。只有排除全部有价值的独立工作后，才按运行平台的受阻审计规则处理目标状态；不能靠重复同一个失效的审批判断累计受阻次数。
