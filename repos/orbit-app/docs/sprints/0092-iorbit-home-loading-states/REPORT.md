## 先说一件与原需求不符的事

复核记录说这两块"一直转圈"。**量下来不是这样**：最近会话 267ms 清空，下一步 320ms 清空。和 0091 一样，这个症状在今天的环境里复现不出来，最可能与复核当时磁盘只剩 226MB 同源。

**冷跑要单独说**：每次重新 `expo export` 之后的第一次导航是 1920ms／2404ms，第二次起回到 263ms／318ms。这是构建缓存，不是产品耗时；0091 那边也是同一个现象。记在这里免得下次又把冷跑当成回归。

## 做了什么

`useLoadingDeadline`：加载持续超过上限就判定逾期。

- **上限取 8s**，与 `useSyncedCollection` 的 `DEFAULT_INVALIDATION_TIMEOUT_MS` 一致，不另造一个数。实测这两块约 300ms，8s 只会在真卡住时触发。
- **重试会重置计时**。重试可能不经过"已结束"状态就重新进入 loading，不重置的话用户刚点掉的超时会立刻又出现。
- 计时器单独导出成 `scheduleLoadingDeadline`，因为本仓库只有静态渲染，走 React 的测试让不动时钟——真实的调度与取消逻辑因此能被直接测到。

两块区域的接法不同，各自沿用已有结构：最近会话多一条带重试的通知；下一步复用它本来就有的错误行与重试按钮（`todayError` 多一个来源）。下一步原来没有重试计数器，补了一个并接进 `scopeKey`，否则点重试不会真的重新请求。

## SC-0092-02／03：三终态

`tests/ai-home-loading-terminal-states.test.tsx`，两块区域 × 四种情形各有断言：

| 情形 | 断言 |
| --- | --- |
| 还在读 | 两块都显示进行中文案，且**不**出现"超时" |
| 读完确实没有 | 显示"现在没有必须处理的事项"，且不再显示进行中文案 |
| 读失败 | 显示原因 + 重试，且不再显示进行中文案 |
| 读不完（逾期） | 显示超时 + 重试，**且不再声称还在读** |

外加一条：逾期的下一步区域**不能**同时说"现在没有必须处理的事项"——没读到不等于没有。这正是 0087 在待办页确立的那条规则。

去掉接线后复跑，逾期那条确实变红。
