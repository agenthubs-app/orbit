## 环境

- 服务端：主检出本地生产构建 `ORBIT_DATABASE_TARGET=local npx next build --webpack` + `npx next start -p 3100`，连本机库 `orbit_events`（严格版流水号）。3000 端口是用户的 dev server，不动。
- App：iOS Simulator（iPhone 17 Pro，iOS 26.4），Debug 版 + Metro 8081，App 内服务器地址指向 3100；结束后改回 `http://127.0.0.1:3000`。
- 账号：现有演示账号（只读浏览为主）+ 新建 QA 账号（写操作），另需一个主办方账号与一个管理员账号；跨端读回用网页（3100）配合。结束后删除全部 QA 数据并报告行数。
- 语言：中文完整走一遍；英文、日文各抽查首页、联系人、活动现场、设置。
- 付费调用上限：AI 对话 ≤ 6 次，名片识别 ≤ 2 次，自我介绍生成 ≤ 2 次；逐次登记。

## 范围

**A. 路由矩阵**：`repos/orbit-app/app/` 下全部路由（约 90 个，含动态路由用真实 id）。每个路由记录：能否打开、内容是否正确（不是空白、不是报错页、数据与网页一致）、主要操作、返回。重定向路由记录落点。

**B. 核心流程**（每条从头走到尾，写操作在网页或第二账号读回）：
1. 注册 → 5 步引导（逐步保存）→ 首页；中途退出再进入续填。
2. 登录、退出、切换账号：上一账号的数据不残留（含本地副本）。
3. 联系人：列表、搜索、详情、手动新建、批量导入入口、关系图、看板、分析钻取、匹配、引荐、进度。
4. 活动：列表 → 详情 → 报名 → 现场页五个标签与资料面板（签到、交换名片与第二账号互认、笔记、约时间）→ 主办方运营页（入场、签到、角色、体验、分析）。
5. 待办、笔记、个人日程：新建、编辑、删除；停掉 3100 模拟断网，页面显示「截至」且写入入口禁用；恢复后同步；重启 App 后本地内容仍在。
6. 收件箱：通知、会话、消息收发、草稿、未读数、全部已读；网页与 App 互相读回。
7. AI：发起对话、历史会话、动作账本「加载更多」。
8. 个人资料：编辑、标签、建议、预览、设置、API 设置。
9. 管理员：`/admin`、`/admin/access`、`/admin/events`（管理员账号）；普通账号被拒。
10. 旧地址：`/party*`、`/events/[id]/attendees`、`/events/[id]/participants/[pid]`、`[...legacy]` 等跳转落点正确。

**C. 通用检查**：视觉语言一致（黑白、细分隔线、蓝色只做链接）；键盘遮挡；44 点触控；加载与错误态可见；无红屏、无控制台未捕获异常（Metro 日志）。

## 已知 P1（开工前已查明，必须处理）

- **Node 版本钉死让关系跟进失效**（0123 报告第 10 节第 1 条，协调者已核实）：
  - `features/followups/storage/lifecycle-task-pages.ts` 的 `assertLifecycleNodeSortRuntime()` 要求 Node 25.6.0、ICU 78.2、Unicode 17.0，不满足就抛出 `LIFECYCLE_SORT_RUNTIME_UNVERIFIED`。本机 Node 是 25.8.1，Vercel 只提供 LTS 版本。
  - 后果一：首页「关系跟进」被 `home-facts-route-service.ts` 的 `catch` 吞掉，静默显示「关系跟进来源未配置或读取失败」。
  - 后果二：关系待办分页（`lifecycle-task-pages.ts`、`connections/lifecycle/task-page.ts`）直接报错。
  - 联系人搜索（`contact-list-postgres-reader.ts` 的 `APPROVED_CONTACT_SEARCH_RUNTIME`）同样钉死了 Node 版本，但会退回慢路径。
- **修复方向**：让结果的顺序不依赖 Node 的具体版本。先查清这个检查保护的是什么（JS 端 `localeCompare` 与数据库 ICU 排序一致），再选一种做法：
  - 排序完全交给数据库；
  - 或者改用与运行时无关的确定性比较；
  - 或者把检查放宽到真正影响结果的条件，并证明在 Node 24（Vercel）和 25.8.1 上结果一致。
- **要求**：
  - 不许简单删除检查而不证明顺序不变。
  - 用真库测试对照旧顺序。
  - 首页跟进和关系待办在 Simulator 上复验。
  - 联系人搜索的快路径一并评估。

- P0/P1：本 Sprint 内修复，每个先写能复现的测试（RED）再修；修复后在 Simulator 上复验。同一问题最多两轮修复，仍不行如实记为未满足并停下报告。
- P2：登记到报告的问题清单，写明建议归属的后续 Sprint。
- 修复需遵守 GitNexus 影响分析规则；UI 改动只限于修缺陷，不引入新样式。
