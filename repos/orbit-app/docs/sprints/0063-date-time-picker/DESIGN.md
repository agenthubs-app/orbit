# Sprint 0063 日期时间选择方案（用户已批准）

批准依据：用户明确回复“没问题按这个设计走，开始实现。”本方案已获准，不再重新索取同一设计批准。

## 问题与参考

现有 PersonalScheduleTimeBlock 日期行和“改期”只切换 expanded，展开后仍是日期／时间 TextInput。开始／结束时间使用普通 View，无法直接点击选择。新建草稿开始日期和时间为空，快捷时长要求先填有效开始时间，不能独立解决输入负担。

Apple 官方日历说明采用点击 Starts／Ends 字段调整日期时间，支持全天、多日和时区；Google Calendar 官方说明允许从日历日期／时间位置创建事件及切换全天。参考这些产品的字段点选、日历上下文与快捷操作，具体底部弹层和控件安排是针对 Orbit 的设计建议，不声称官方文档证明某一滚轮样式。

- Apple：https://support.apple.com/en-ca/guide/icloud/mmfbbb32be/icloud
- Google：https://support.google.com/calendar/answer/72143?hl=en

## 推荐交互

1. 日期行直接打开月历弹层：标题显示年月、上一月／下一月、星期行、日期网格，今天与选中日期有不同标记；提供“今天”“明天”。未选日期时打开日程时区的当前月份，尚不自动写入草稿。已有日期打开对应月份。选中日期后点击完成才应用，取消／关闭／返回键放弃本次弹层选择。
2. 开始和结束时间各自成为可点击字段，打开小时／分钟选择弹层；24小时制，小时00–23、分钟00–59，可触摸滚动或直接选择，不要求输入数字。保留已有精确分钟，不能统一取整为5／15分钟。屏幕阅读器和键盘可操作，焦点打开后进入弹层、关闭后返回原字段。
3. 新建时在用户确认完整开始日期时间后，若结束未设置，建议默认30分钟。已有日程调整开始时间时保留有效的原实际时长；原无结束的已有日程不擅自补结束。手工调整结束必须明确选择结束日期／时间；结束早于开始时给出可理解提示，不悄悄改为次日。
4. 保留30分钟／1小时／2小时及全天。跨天时明确显示结束日期。全天只展示日期；界面结束日期表达最后占用日，转换为原契约下一日零点的排他结束，避免多一天或少一天。
5. 重复结束日期复用同一月历选择器，允许清空表示不设结束日期；沿用开始日期约束。整个系列／仅本次编辑范围及提醒规则不由本Sprint改变。

## 实现边界和方案比较

推荐用现有 React Native／Web 组件和设计主题实现共享的月历与时间底部弹层，App 和 PhoneWeb采用同样的交互语义。浏览器原生 date／time 控件实现较小，但不同手机浏览器外观及唤起方式不同，难保证稳定月历体验；新增日历库可节省控件工作，但增加原生构建及依赖适配。本方案先复用现有能力，实施调查发现不能满足可访问性或触摸体验时再提交具体依赖选择，不能自行扩大方案。

主要改动预计为 PersonalScheduleTimeBlock、可复用的日期时间选择组件、相关草稿更新纯函数、PersonalScheduleRules 的重复结束日期入口、四字典和必要行为测试。后端API／存储契约不因选择器而改变。Main Next独立页面是否同期使用对应Web入口，由ROOT按0061实际交付和文件锁确认，不把App／Phone通过写成所有Web端通过。

日期作为日程时区的日历日期处理，时间作为当地小时分钟处理。复用现有 resolveLocalDateTime／localParts／shiftCalendarDate 校验和转换，不用浏览器本机 Date 构造器偷换日程时区；不存在或重复的当地时间仍明确拒绝。保存、幂等、CAS、版本回执和正式回读沿用当前流程。
