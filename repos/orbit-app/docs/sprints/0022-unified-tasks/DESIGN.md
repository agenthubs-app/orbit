# 待办统一设计

2026-09-14。产品方向已获用户确认；本书面规格与 PLANNER 的技术边界仍须审阅。界面延用 Orbit 现有风格，不另做一套视觉系统。

## 领域与数据

“待办”是一件具体行动；“人脉待办”是待办的筛选结果，不是第二类存储实体。“需要联系”是联系人的状态，不等于已经创建事项。

现有 TasksScreen 与 FollowupsScreen 都读取 `/api/tasks`。人脉谓词沿用 `followups-page.ts` 的现有语义：`category === "relationship"` 或存在 `relatedContactId`。因此只有 category 的服务端过滤不能代替这个筛选。当前实际 collection handler 返回全部匹配任务；若接口以后分页，须取得完整集合或发布等价服务端筛选，不能拿第一页当总数。

一条事项在全部、人脉、首页和日历中使用原 canonical ID。完成／重新打开复用原任务 API，不创建副本，不修改联系人状态，不把未确认建议计入事项数量。关联联系人不存在或不可访问时保留事项，不伪造姓名或身份。

## 待办页

保留现有新建和详情能力，增加“全部／人脉”范围选择；状态单独选择“未完成／已完成”。默认全部、未完成。未完成页按逾期、今天、以后、未安排分组；不再在该状态下附加已完成列表。数量按同一任务集合与筛选计算。

人脉事项显示可取得的真实联系人上下文。完成控件、事项详情和联系人详情为独立触点；保持可访问标签及至少 44 点触控目标。加载、空列表、请求失败分别显示，不把错误显示成没有待办。

| 地址／入口 | 目的地与兼容规则 |
| --- | --- |
| `/tasks` | 全部未完成待办 |
| `/tasks?scope=relationship` | 人脉未完成待办 |
| `/tasks?scope=relationship&view=completed` | 已完成人脉待办 |
| `/tasks/[id]` | 原事项详情，不改变 ID |
| `/followups` 及已有对应旧入口 | 在能力迁移完成后，认证内跳转人脉待办；支持的状态参数保留 |
| AI 面板“查看全部待办”、通用待办快捷入口 | 全部待办，不误筛掉个人事项 |
| Pipeline 的人脉跟进入口 | 人脉待办；Pipeline 本身保留 |
| 消息／日历中有 canonical task ID 的入口 | 对应事项详情 |
| 只有候选信息、没有任务 ID 的旧入口 | 人脉待办中的待确认建议区域，不伪造事项详情 |

参数只接受明确枚举，重复参数按现有首值约定解析，无效 scope 回到全部、无效 view 回到未完成。登录返回保留已验证的内部路径与上述参数，不引入任意 return URL。`/tasks` 和详情路径纳入现有私有路由识别；原私有页面包装仍保留。

## 旧跟进能力的归宿

先完成能力接线，再切换旧路由。人脉待办页有单独的建议／草稿工具区；它不参与已保存事项的计数。

- 0006 已确认的起草消息、待办候选和提醒候选入口消费同一模板接口，带授权引用进入 IORBIT，由用户编辑并主动发送。
- 对某个联系人起草必须基于用户明确选择的事项／联系人，不能自动选列表第一人。
- 已存在的未确认候选和草稿仍可查看；沿用原允许的确认行为，不因迁移自动接受或丢弃。
- 提醒候选不是已创建提醒；已创建任务的提醒编辑归 0010。
- 0021 起源接口就绪时沿用其入口元信息，不另存一份私密 prompt，不让导航自动调用模型。

如果新工具区尚不能承接原能力，保留旧页面，不先做一个只跳转但丢功能的兼容壳。不会新建跟进表、批量迁移事项、重写联系人状态或删除历史建议。
