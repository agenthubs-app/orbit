# Sprint 0089 报告 — 联系人列表那个"价值分"

**状态:** 见登记表。**run-01，唯一一次 Generator。**

## 先用人话说

你看到的是：78 个联系人，76 个显示 84，2 个显示 72。

查下来这个数字的产生方式是（`features/contacts/contact-graph-query.ts:233`）：

```ts
function valueScore(valueTypes: readonly ContactValueFilter[]): number {
  return Math.min(95, 60 + valueTypes.length * 12);
}
```

**它就是 `valueTypes` 的个数换了身衣服。** 0 个→60、1 个→72、2 个→84、3 个及以上→95。数据库里 76 条连接有 2 个 valueTypes、2 条有 1 个——所以 76 个 84、2 个 72，和你看到的完全一致。

一个只有三种可能取值、实际只取到两种的数字，被写成 0–95 的分数，占着每一行最显眼的右侧位置。它不是"分数不准"，是**假精度**。

但它算自的那个东西是有信息的：同样 78 个联系人，valueTypes **有 14 种不同组合**。

所以这一格换成它本来算自的内容：`引荐路径 · 战略契合`、`知识交流 · 社群资源`、`商业机会 · 引荐路径`……

| | 这一格能区分出几种状态 |
| --- | --- |
| 原来（价值分） | **2** |
| 现在（价值类型） | **14** |

## 与 PLANNER 的偏差

**1. 没有改评分算法。** Planner 留了"修算法 vs 换内容"两条路。选了换内容，因为这个分数**不是算错了**——它精确地表达了 `valueTypes.length`，只是那个量本身几乎不变。要让它有区分度就得引进新的评分维度（互动频次、证据强度、目标匹配……），那是一个新的评分系统，不是本 Sprint 的范围，而且 Planner 判断 3 明确说"换成什么由列表已有字段决定，不新增数据依赖"。

**2. 服务端的 `valueScore` 保留了。** 只是不再显示。它仍在契约里，`contact-pipeline` 等处还在用；删掉它是另一件事，本 Sprint 不做。

**3. 搜索结果里那个分数也去掉了。** 同一个数字，而且那一行**下面本来就把同样的价值类型渲染成 chips**——同时显示两者，等于邀请读者把数字当成额外信息。顺带删掉了因此没人用的 `searchResultScore` 样式。

**4. 推翻了一条既有的显式决定，并把新决定写回测试。** `contacts-screen-source.test.ts` 原有一条 `contact rows keep only identity and match score visible`，里面**明确断言** `doesNotMatch(cardSource, /contact\.valueLabels/)`——也就是说"行里显示分数、不显示价值类型"是以前有人特意定下的。我反了这个决定，所以把那条测试改写成新的契约（名字也改了），而不是让它悄悄消失。

它原本要守的"行要紧凑"没有被牺牲：新内容仍是**单行、`maxWidth: 40%`、超出省略**，测试里现在明确断言这两点，行的结构依旧是「身份 + 一个紧凑信号 + 箭头」。
