# Sprint 0139 — 通知发现入队的整表谓词锁

**Plan revision:** 1。**模式:** existing-codebase / single-generator。运行状态只在登记表。
**原需求:** 0137 REPORT 第 8 节第 1 条。由协调者按用户 2026-09-28 的授权立项。
**单一目标:** `enqueuePage` 在共享的 `orbit_records` 上，不再因谓词锁升级而和无关账号的写入冲突；入队的正确性保持不变。
**基线:** 0137 合并后的 `chat-agent`（`c4c4b3cf4` 之后，开工时追加提交号）。执行顺序：0137 → **0139** → 0133 → 0134 → 0135 → 0136。
**进入条件:** 无。

## 已查明的事实

- `enqueuePage` 在 serializable 事务里最多读 52 行 `orbit_records`。
- 本机 `max_pred_locks_per_transaction=64`，`max_pred_locks_per_relation=-2`，即每张表 32 个。超过以后，谓词锁升级成整表的 SIREAD 锁。
- 0137 的复现方法：另一个进程在别的 workspace 并发写 `orbit_records`，5 次全部 40001（证据见 0137 的 `red-discovery-contention-*.log`）。
- 0137 只修了测试，改到独立 schema，没有改产品代码，也没有调重试上限。

## 范围

1. **先在真库上写一个稳定复现的测试**：在和生产一样的单一 schema 里，一边持续写入无关账号的行，一边执行 `enqueuePage`。修之前应当频繁 40001。
2. **找出让入队既正确、又不需要整表锁的做法**，选一种并写明理由。可选方向：
   - 把读取改成按主键或唯一键的点查，并配上合适的索引，让谓词锁停留在行级；
   - 用唯一约束加 `on conflict do nothing` 保证不重复，把隔离级别降为 read committed；
   - 用咨询锁加 read committed，只在账号范围内串行化（注意 0123 记录的咨询锁键冲突）。
   不允许只调大重试次数，也不允许改数据库配置来掩盖问题。
3. **正确性测试**：重复入队不产生重复项；并发的两次入队结果和顺序执行一致；别的账号的数据不受影响。
4. **生产说明**：如果需要新索引，给出 `create index concurrently` 的步骤，写进上线清单。
