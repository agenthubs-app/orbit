# Sprint 0139 报告：通知发现入队的整表谓词锁

## 1. 结果

**已完成，包括协调者追加的扩展范围。**

- `enqueuePage`、`claim`、`updatePreferences` 不再在共享的 `orbit_records` 上拿整表 SIREAD 锁，其他账号的写入不再让它们报 40001。
- 提交：`6195b9cc2`、`fc6248df0`。
- 没有改迁移、索引或数据库配置，重试上限也没动。

## 2. 根因（更正 0137）

有两条路会让锁升级成整张表：

- **小表走顺序扫描**：表很小时，查询直接扫全表，入队 10 条也会拿到整表锁。测试全量里的 40001 就是这个原因。
- **生产的大表上**：worker 每轮都会从头重扫一遍。已经存在的 50 个 job 散在大约 50 个数据页上，每条记录都要加一个锁，超过每张表 32 个的上限后，升级成整表锁。`claim(20)` 要扫这个账号的全部 job，也会这样升级。

## 3. 方案

- 这三个方法改用 read committed，在原有的「按账号加锁」之后执行。
- **为什么安全**：discovery 的状态、偏好、job 这几类数据，只有 repository 在写，而且都要先拿这把账号锁，所以同一账号的操作仍然一个接一个执行；通用迁移不会改这些行的内容。
- **`complete` 保持 serializable**：它会把结果发布到收件箱，而用户自己操作收件箱时不拿这把锁，降级就不安全了。
- **否掉的两个方向**：
  - 点查加索引：50 次点查本身就是 50 个锁，照样会升级；
  - 唯一约束加 `on conflict`：唯一约束已经有了，锁也是现成的，改写入路径没有额外收益。
