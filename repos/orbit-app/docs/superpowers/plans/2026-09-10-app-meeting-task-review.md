## Global Constraints

- 本轮只制定任务，不修改功能代码，不操作业务数据库，不提交、合并、推送或部署。
- 后续 App 实施仅编辑 `repos/orbit-app`；Web、后端和根目录 bridge 台账由对应负责人处理。
- App 只通过 HTTP API 访问业务数据，不直连 Postgres、Supabase、`orbit_records`，不创建业务双写或离线写回系统。
- 共享契约、Schema 和批准的行业／语言字典只通过 `npm run sync:contract` 同步，不手改副本，不扩大同步白名单。
- 保留现有用户修改、设计原件和 `prototypes/` 独立仓库；不清空数据或恢复演示数据来通过验收。
- 实施前逐符号执行 GitNexus upstream impact，报告调用者、受影响流程和风险；HIGH／CRITICAL 必须先向用户提示。图索引不可靠时不得用空结果证明低风险。
- 业务修改采用 TDD；已有失败必须先复现、归类并满足对应基线审批要求，不能删除断言、空接路由或跳过用例换取绿色结果。
- 本任务稿审批不自动代替新增视觉稿审批、基线失败处置审批、工作树安排、真实外部调用或提交发布授权。
- 不自动发送邮件／邀请消息，不因查看页面重复调用 AI，不把失败和权限不足显示为“没有数据”。

## 一、范围与设计建议

### 推荐：沿现有功能分批调整

本次跨导航、账号、AI、人脉、活动和日程，属于架构级调整，不能当成一次统一换皮。

建议按可独立验收的子项目推进：先锁定导航和接口边界，修复核心流程，再补协作体验，最后完成三语和原生回归。已有能力直接复用，不整体重写 App。

其他路径的取舍：仅先做视觉调整能较快看到变化，但无法解决重复生成、报名状态和联系人身份问题；整体重建则会扩大接口和原生回归范围，也不符合会议提出的逐步确认方向。

### 产品结构建议

- 底部顺序建议为：首页、人脉、IORBIT、活动、我的。其中 IORBIT 是中央动作入口，打开独立全屏 AI 页面，不作为第五个持续显示底栏的普通根页面。
- 默认首页展示待办、近期日程与推荐活动；日历入口保留。首页不再放大聊天输入区，不把空联系人用户送去多层演示流程。
- 主动 AI 提问、分析和写作汇入 IORBIT；名片 OCR、报名过程中的辅助问答保留为嵌入式能力。
- 人脉页继续使用现有列表；联系人详情展示事实资料、资料备注和关联笔记。互动内容统一到笔记编辑，人脉页只保留资料字段编辑，不再提供互动备注输入。联系人不等于平台用户，站内聊天必须有服务端确认的资格。
- 笔记是后续新增的人脉互动内容入口；一篇笔记可添加一位或多位相关人脉，同一内容无需在每个人的详情下重复填写。具体页面与入口留待后续设计审阅，不在本轮实现。
- 活动页既能看推荐，也能浏览／搜索全部公开活动；主办方功能留在同一 App、同一账号的活动模块中。
- 首页和人脉分析不因进入页面自动生成付费 AI 内容；已有分析可回看，数据变化时提示用户重新分析。

### 2026-09-11 设计变更：笔记记录互动，人脉展示资料

设计方向已确认，实施留待后期。用户记录一次沟通时，先写笔记，再添加相关人脉。以内容为起点，既便于回看完整过程，也避免多人会面时在多个人脉详情下重复记录。

| 概念 | 内容与职责 | 输入／编辑位置 |
| --- | --- | --- |
| 笔记／互动记录 | 沟通过程、会面纪要、约定、互动心得等内容；一篇笔记可关联多位人脉，一位人脉可关联多篇笔记 | 笔记编辑界面；在笔记内添加或移除相关人脉 |
| 人脉资料 | 姓名、身份、公司、职位、联系方式等资料，以及用户填写的备注称呼、背景说明等资料备注 | 人脉资料编辑入口，限当前用户有权修改的字段 |
| 人脉详情中的关联笔记 | 当前人脉相关笔记的摘要及原文入口，引用同一篇笔记，不另存一份正文 | 只展示与跳转；需要修改内容时进入笔记编辑界面 |

“资料备注”说明这个人是谁或用户如何识别他；“互动记录”描述某次沟通发生了什么。二者不能因为旧字段或界面都叫 Memo／备注，就被合并处理或一起删除。

后续实施必须包含以下变更：

- 新增笔记的列表、查看、编辑和关联人脉能力。关联使用稳定人脉 ID；同名人脉可区分，多人笔记只维护一份正文。
- 移除人脉详情内专用于录入互动的输入框、添加／保存备注按钮及对应写入接线，重点检查现有 `ContactNotesSection`。不能只增加笔记页，却继续保留原来的互动备注编辑器。
- 人脉列表和详情以展示、检索、筛选及查看关联内容为主；资料备注、身份和其他授权资料字段仍能通过资料编辑入口修改。不把这些字段改成只读，也不借资料编辑入口继续录入会面纪要。
- 关联人脉只帮助当前用户整理内容，不等于向被关联的人分享笔记、发通知或发消息；保持既有私密内容的权限边界。
- 保留现有备注原文、所有者和可用来源信息。旧数据可能混有资料说明与互动内容，具体映射和迁移方案须另行确认，不直接把所有旧备注清空或一律当成互动笔记。
- 笔记写入、关联回读和旧内容保全就绪后，再切换并移除旧互动输入入口；切换后的验收必须证明旧入口已移除，不能长期双写或让用户暂时失去内容访问能力。

这次只确定手工记录互动的内容入口；现有消息、报名事实和系统时间线继续保留真实来源，不因此改造为手填笔记，也不自动归档或复制全部聊天。首页稿中的“写笔记”可作为后续入口候选，但当前稿不冻结笔记页面、路由或底栏位置，不提前接入空页面或伪装成已可用功能。

### 2026-09-11 补充：全 App 字号与信息密度轻量微调

采用已选定的[第三轮首页 02（Split Day）](../../designs/2026-09-11-home-directions-v3/02-split-day.png)作为紧凑程度和文字层次的参考。其他页面也要检查过大的标题、正文、行高和留白，避免首页紧凑、二级页面仍然大字稀疏。

这是一轮排版微调：调整字号、字重层次、行高、列表间距、卡片内边距和区块留白。保留现有页面结构、模块顺序、品牌色、导航和业务操作；已另行批准的导航或笔记功能变更按对应任务执行，不借排版任务扩大改版范围。

不同内容保留各自的阅读节奏。人脉／活动／待办列表可更紧凑，资料表单仍需清楚的字段与输入区，AI 长回答保持连续阅读体验。先检查共享文字与间距 token 的使用范围，再按组件和页面微调，不对整个 App 做统一缩放，也不从栅格稿直接推导所有页面的固定字号。
