# 名片大文件上传：问题与实现约束

状态：线上问题已复现，原文件持久化、服务端授权接口、受限读取、队列清理、V2 消费接口及 V2 网页直传已实现；V1 图片/PDF 消费与客户端尚未接入，不能视为全部上传问题已修复。

## 已实现的基础与验证

新增第 4 号迁移与 `business-card-upload-sources.ts`：上传记录先于授权持久化；许可绑定工作区、用户、服务器路径、大小和固定有效期；处理租约支持接管并拒绝旧租约提交；目标写入与消费回执使用同一数据库事务。删除在许可过期并经过一分钟余量后执行，先提交 deleting 状态，删除中断可重试，删除后的消费回执仍支持幂等查询。

真实 PostgreSQL 的 31 项针对性测试通过，覆盖新记录的归属隔离、并发租约、事务回滚、唤醒失败、许可过期、删除中断，以及已有 V1/V2 图像日志和 V2 仓储回归。

后续实现增加 `POST /api/contact-drafts/business-card/uploads` 上传预约与 `/uploads/token` SDK 令牌入口，要求当前会话、同源 Origin、最多 16 KiB JSON 元数据。签发前按持久化记录校验用户及路径，保持原许可的大小、类型和有效期；不请求完成回调，也不接受客户端回调作为消费凭据。SDK 内部使用部署凭证，不导出配置值。

`business-card-upload-source-reader.ts` 只读取当前工作区、用户和记录绑定的私有路径，限制实际流量、验证精确字节数及 SHA-256，并在整个打开/读取过程使用 60 秒超时。它仅验证字节完整性，解码是否有效仍由后续转换流程负责。到期记录及删除重试已接入两条队列和独立扫描的待办查询；未来未到期记录不触发空转，过期后的活动租约与删除退避仍保留待办。

这一阶段的 22 项针对性测试通过，包括 6 MiB 图片与 50 MiB PDF 字节流读取、超限/摘要不符/超时、真实 PostgreSQL 的扫描恢复与删除退避、HTTP 会话/同源/归属和授权约束。本地合成字节流不代表合法图片/PDF 已通过线上转换。

V2 新增 `POST /api/contact-drafts/business-card/uploads/consume-v2`，接受 sourceId、batchId、itemId、operation，以及替换必需的 expectedVersion。首次上传核对原文件记录与 manifest 的摘要、大小和类型；原文件读取和真实图像归一化受现有并发门限控制。仓储上传/替换支持借用消费事务连接，通过 savepoint 保留原有批次锁与版本规则，不提前提交外层事务。衍生图先进入持久化写入日志；目标变更与原文件消费回执原子提交后才发送工作队列消息。回执绑定目标、操作及替换版本，失败重试不会再次替换同一项目。

V2 消费阶段的 33 项相关测试通过：27 项既有仓储、worker、衍生图日志回归，以及消费集成与 HTTP/授权测试。集成使用超过 4.5 MB 的真实 JPEG（尾部填充至 6 MiB），验证实际归一化、目标写入后的回执失败回滚、提交后的发送失败、重复消费、替换版本、旧图清理任务和已取消目标。该阶段完成 V2 服务端消费；V1 消费与后续客户端、线上验收分别记录进展。

V2 客户端现由登录后的 `GET /uploads` 查询服务端存储模式。私有存储模式只向应用接口发送元数据，文件通过 Blob SDK 直传；本机文件系统模式保留原上传路径。会话缓存仅保存预约标识及对象路径，不保存文件或上传令牌。重复操作先查询消费回执，只有服务端明确返回缺失原文件或过期时才补传或重新预约；网络超时、未知错误不丢弃已有回执。上传与替换共用这一恢复流程，替换回执仍绑定原版本。上传队列遇到失败后停止当前循环并保留文件，避免无限自动重试。

客户端接入阶段 23 项针对性测试通过，覆盖预约/上传/提交响应丢失、并发重复调用、刷新后恢复、过期预约、本机路径、请求超时、HTTP 恢复状态以及真实数据库消费回归。类型检查无新增诊断，仍有原有 109 项错误。实际浏览器仍受 Vercel 登录保护，浏览器完整旅程需单独验收。

现有 V1 将全部图片或 PDF 放进一个 FormData 请求，图片上限 10 MiB、PDF 上限 50 MiB、批次上限 500 张；V2 按单项 PUT 上传，原图上限 10 MiB、批次上限 100 张。两条通路仍受函数入口限制，即使单个文件不大，多张图片的总请求也可能超限。

[Vercel 函数限制](https://vercel.com/docs/functions/limitations)规定请求体上限 4.5 MB；[Blob 客户端上传](https://vercel.com/docs/vercel-blob/client-upload)允许浏览器直接传文件到私有 Blob，由服务端授权单次上传。项目已安装的 `@vercel/blob` 类型声明支持 private upload、路径授权、maximumSizeInBytes、validUntil、allowOverwrite 和签名完成回调。无需读取或导出已部署的 Blob 配置密钥。

## 保持的产品范围

- 保留 V1 多图、50 MiB PDF 和现有每页一张名片的解析流程；不能只修 V2 或把 PDF 功能删除。
- 保留 V2 manifest、单项上传/替换、摘要匹配与续传，不改变 10 MiB 原图上限来绕开平台限制。
- 文件字节不再经过浏览器到应用函数的大请求体。应用接口只处理有明确数量和大小限制的上传元数据与文件标识。
- 保留本机开发路径；旧 API 的小文件兼容不能被当作大文件功能完成。

## 原始上传的持久化边界

原文件与供识别/复核使用的 JPEG 衍生图必须分开管理。原图或 PDF 在转换前也可能遇到断网、取消、函数重启，不能成为无记录的对象。

1. 服务端先创建上传记录，再签发有期限的上传许可。记录包含工作区、actor、服务器生成的对象路径、预期 MIME/字节数/摘要、目标通路、过期时间和处理状态。对象路径不得直接使用客户端提供的 URL 或文件名。
2. 令牌生成入口逐次校验当前会话、上传记录归属、路径和状态，限制大小与内容类型并禁止覆盖。完成回调必须通过 SDK 签名验证；回调不依赖浏览器登录 Cookie，也不能独自作为业务写入成功的依据。
3. 消费原文件时，从记录中的私有对象路径读取，按实际流量限制字节数，验证摘要和解码结果。不可根据客户端声称的大小直接无限读取，也不可接受任意远端 URL。
4. 消费需要持久化租约。目标批次/项目写入与上传记录的消费回执必须在同一事务中完成，或使用可证明等价的幂等目标标识；不能先创建批次再在另一个事务标记 consumed，否则超时重试会创建重复批次。
5. V1 的 PDF 解析和大批量转换需要验证函数执行时间与内存，而非只证明传输突破 4.5 MB。若必须移到后台，需持久化分页/项目进度、失败重试和取消，不用一个无进度的长请求替代。

## 删除与许可重放

不能在原文件消费后立即删除对象、却让同一路径的上传令牌继续有效：对象删除后，旧令牌可能重新上传并留下孤立文件。清理时间必须晚于该记录所有已签发许可的最大有效期及明确的时钟余量，或者采用经过验证的等价重放防护。

清理先提交不可再消费的 deleting 状态，再执行物理删除，最后写删除回执；崩溃后可重复删除。尚未完成上传的记录也要到期回收。待办判定、延迟唤醒及独立扫描应覆盖原文件，OCR 不可用不能阻止清理。原文件处理成功与衍生图回收记录的存在不能相互替代。

## 验收必须覆盖

- 真实 Preview：超过 4.5 MB 且不超过 10 MiB 的图片、超过 4.5 MB 的合法 PDF、多张图片合计超过 4.5 MB，均可进入正确批次/项目；随后取消并核对清理状态。
- 10 MiB 图片与 50 MiB PDF 的边界；超出应用限制时在上传授权前拒绝；实际对象大于声明时仍拒绝消费。
- 匿名、其他 actor、其他工作区、伪造路径/回调、过期许可、取消后的消费与重复提交。
- 上传成功后浏览器中断、转换失败、消费事务回滚、写入后响应丢失、删除后状态回写前重启。
- PDF 和批量转换的资源限制、部分进度及恢复；V2 替换/续传；本机小文件兼容。
- 浏览器成功、失败、进度、重试和重新选择文件的实际操作；不能用一次小图片 API 成功代替这些证据。

现有阻塞条件仍独立存在：Vercel 浏览器登录、有效 SMTP、真实模型/OCR、独立调度和目标用户试用。直传完成也不代表这些验收完成。

## V1 PDF 分段转换基础

`renderBusinessCardPdfPageRange` 支持指定起始页和本次页数，逐页等待 `acceptPage` 完成，再生成下一页；返回总页数、下一页及是否结束。画布在等待页面保存前释放，PDF 解析任务在成功、失败、超出批次上限和取消时销毁。原 `paginatePdfToCardImages` 通过这一入口保留数组返回值，兼容现有小请求接口。

12 项 PDF/批次接口测试通过，包括实际 500 页 PDF、包含 49 MiB 合法流对象的 PDF、分段结果与完整转换一致、保存失败后的起始页恢复和取消。它们证明本地转换与资源边界，尚未证明 V1 云端大批量导入完成。

下一步 V1 后台集成必须持久化每页接受结果与进度，不能仅在内存保留 `nextPage`。现有批次创建仍接收完整图片数组，不能直接用它在单个函数中完成最大批次。原文件有效期、处理中租约及衍生图写入日志必须覆盖准备阶段；取消必须阻止迟到的页面写入，完成时目标批次和源文件回执必须原子提交。当前分段转换函数不创建任务、不发送队列消息，也不改变 V1 网页仍走旧上传路径的事实。

## V1 后台准备任务存储

`business-card-v1-preparation/repository.ts` 沿用 V1 的通用记录表和工作区事务锁，新增任务、原文件绑定和请求幂等记录三个集合。任务记录在同一 JSON 中保存页面索引、下一文件/页、租约、失败次数、过期时间及最终批次 ID；单次保存原子更新索引和进度，页面不包含图像字节。一个原文件只能绑定一个任务，重复请求或同源列表的新请求键返回既有任务，改变源列表顺序会发生冲突。

处理租约为 15 分钟，过期后另一连接从已提交页接管；失败采用 60 秒退避，连续五次失败终止，成功提交页面会清零失败计数。任务期限取所有原文件期限的最早值，不延长原件保存期。取消会拒绝迟到的页面提交，并让原文件进入到期清理；仍保留原件与衍生图日志，不能声称物理删除已立即完成。准备页面要求独立的、仍为 pending 的衍生图写入日志，页面 ID 不可复用，图片摘要必须匹配原文件。

最终完成入口只接受已经打开的原文件消费事务，借用其连接写入目标批次和任务完成状态；外层消费回执提交之前不会独立提交。原文件行锁先于 V1 工作区锁，取消和完成遵守同一顺序。

15 项相关 PostgreSQL 测试通过，其中 7 项覆盖新任务仓储，其余回归原文件与 V1 图像日志。测试涵盖发布失败、并发去重、租约接管、进度回滚、取消、混合文件页序、退避、过期，以及模拟目标记录与任务/原文件回执一起回滚。实际 V1 转换 worker、正式批次写入器、任务 API 和网页仍待装配；这一存储阶段尚未部署，也不代表 V1 后台导入已经运行。
