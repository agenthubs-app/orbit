# Sprint W0028 — 本人报名只读「哪场、报没报」

## 要实现什么

已登录用户打开活动页 `/app/events` 或活动详情页 `/app/events/[id]` 时，系统判断「我报没报这场活动」只从数据库取两样东西：活动 id 和报名状态。不再把整条报名记录（含参与者画像，每条 2.0–2.6 KB）拉回来。旧报名数据（legacy 投影）也只取当前页面涉及的那几场，不再先读出这个人的全部报名再筛。

页面看起来和现在完全一样。

## 为什么要做

W0024 让活动页按账号 id 读本人报名以后，每次打开都要拉整行报名。按 1000 人估算，每月多出约 311–383 MB 的数据库出站，上限是 30 MB（决定 D18）。W0027 会让活动详情页也按账号 id 判断「已报名」，同样的问题会出现在详情页。本 Sprint 必须在上线清单 W0019 之前完成。

## 做完能看到什么

- 活动页的「已报名」标记和「我的活动」筛选结果不变。legacy 和 canonical 两类报名都照常显示。
- 活动详情页的「已报名」、报名者名单是否显示、私密活动能否打开，这些判断结果都不变。
- 查询次数不增加。
- 实测的返回字节表：
  - 活动页：一个人有 5 场报名时，单次读取在 1,000 B 以内。
  - 这个人另有 20 场旧活动的报名时，读取字节不变。
  - 按「1000 人，每人每天开 1 次活动页、2 次详情页，每人 5 场报名」估算，两页的本人报名读取合计每月 ≤30 MB。
- 出错时和现在一样：
  - 读取失败不会被当成「未报名」静默显示。
  - 账号解析不到时，不改用会话 id 去读。
- 顺带受益：iOrbit 首页 `/app/agent` 和引导页 `/app/start` 用的是同一个读取函数，也会一起变轻。它们的页面行为同样不变。

## 怎么验收

- **数据库测试（本机测试库）**：造出已报名、已取消、别人的报名、页面以外的旧报名、重复记录、损坏记录这些情况。证明轻量读取和原来的整行读取得出的「报没报」完全一致。legacy 和 canonical 两条路径都要测。
- **页面测试**：W0024 和 W0018 的页面测试断言不变，只把存储替身换成新的轻量方法。另外还要证明两件事：这些页面对整行读取的调用次数是 0；「目录失败时不解析账号」「解析不到账号时不读本人报名」这些保护照旧。
- **本机实测**：用和 W0024 相同的口径出一张「改前／改后」字节对照表，写进 REPORT。
- **浏览器**：在 3001 验收 server 上，用 verify-plan 看活动页和已报名活动的详情页，桌面 1440、手机 375 各看一次，控制台 0 错误。

报名者名单本身（已报名用户在详情页看到的其他人列表）本 Sprint 只实测，瘦身由 [W0029](../W0029-attendee-roster-trim/GOAL.md) 做（D19）。报名数据有损坏时是否仍然报错，按 PLANNER 的 W28-4 执行，推荐保持和现在一样。完整验收项见 [PLANNER.md](PLANNER.md)。本页只说明预期目标，不代表已实现；当前状态以[登记表](../README.md#sprint-登记表)为准。
