# Sprint W0042 — 资料「更新建议」只读本人相关数据

## 要实现什么

用户打开 App 资料页或资料建议页，或者采纳／忽略一条建议时，服务端读取「更新建议」所需的数据，只读本人相关的行。现在的做法是把整个 workspace 的资料、联系人、关系、互动记忆、证据五个集合全部读出来，再在 Node 里筛选。改完后返回的建议、证据、状态，以及出错时的成败，都与现在逐项相同。

## 做完能看到什么

- 本机三个验收账号调用建议接口，单次数据库读取从约 9.53 MB 降到几十 KB。规划估算 `user_verify_plan` 约 31～42 KB，以实测为准。资料编辑页默认路径同样下降。
- 别的账号往同一 workspace 写入再多数据，本人这几条读取的字节数和语句数都不变。
- App 的建议列表、采纳、忽略、重复提交、冲突提交、「建议不存在」等结果与改前相同。接口契约与 App 代码不改。
- 坏数据下接口的成败与现在完全相同。现在 workspace 里任何人的一行坏数据，都会让所有人的建议接口失败。这个既有问题本 Sprint 不改，因为改了会改变用户看到的行为，需要另行决定。只有两处允许不同：排序键完全相同的平局行，相对顺序原本就不确定；同时存在多条坏行时，先报哪一个错误可能不同。

## 怎么验收

- 在本机测试库建随机 schema 造边界数据，新旧两种读法并排跑，比对整份建议图：每个集合的行、行的顺序、`generatedAt`。坏数据的每一种情况都先记下旧读法的结果，再要求新读法得到同样的结果。
- 按 W0017 口径（每条语句返回行的 JSON 字节）实测改前和改后，并做噪声对照：其他账号的数据增加时，本人读取应保持不变。
- 建议接口与采纳／忽略接口改前改后逐项比对。
- 重算数据库月预算表。App 资料建议的调用频次未知，所以按频次给出敏感度表，并算出每档剩余额度允许的最高频次。
