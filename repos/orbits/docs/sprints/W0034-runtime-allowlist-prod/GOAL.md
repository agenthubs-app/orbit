# Sprint W0034 — 排序与联系人搜索运行时白名单覆盖生产组合

## 要实现什么

在本机复现与生产相同的排序环境（Node 24 最新版的 ICU 78.x，加上与 Neon 同样链接 ICU 67、`und-x-icu` 排序规则版本 153.14 的 PostgreSQL 16），在上面跑通与 W0025 同等的差分测试，并补一组「Unicode 13 之后新增字符」探针。全部通过后，把生产组合加入跟进排序和联系人搜索的运行时白名单。白名单改为按排序真正依赖的版本（Node 侧的 ICU／Unicode 版本，PG 侧的主版本和 ICU 排序规则版本）判定，不再卡 Node 或 PG 的 patch 号。检查不通过时，服务端日志记下实际版本元组。

## 做完能看到什么

- 生产组合通过差分测试后才进白名单。进了白名单，生产上的「先联系谁」、`/app/tasks` 跟进分页、首页跟进补位、关系任务分页接口和联系人搜索就不再因为运行时检查显示「暂时不可用」。
- 白名单以外的组合仍然拒绝（`LIFECYCLE_SORT_RUNTIME_UNVERIFIED`／`CONTACT_SEARCH_RUNTIME_UNSUPPORTED`），页面仍显示来源不可用，不会给出可能漏数据或重复的分页。
- 被拒绝时，服务端日志有一条结构化记录，只含版本号：Node、ICU、Unicode、默认排序 locale，以及 PG 主版本、编码、排序规则版本等。上线后看 Vercel 日志就能知道生产实际跑的是什么组合。
- 本机 3001 验收 server（Node 26.10.0 / ICU 78.3 + 本机 PG 16.12 / 153.136）继续可用，数据库请求次数和返回字节不增加。

## 怎么验收

- 在本机复现的 PG（`collversion` 和 actual 都是 153.14，链接 ICU 67）上，分别用 Node 24（ICU 78.3、78.2）跑跟进排序和联系人搜索两组差分测试，外加新增字符探针：0 skip，全部通过后才改白名单。复现方法见 PLANNER 开放问题 W34-1，不在 Neon 上写入任何东西。
- 单测证明：已验证组合在不同 Node patch 号下都放行，其他组合都拒绝；拒绝时日志字段正确，且同一进程同一元组只记一次。
- 回归：本机组合的定向测试、typecheck、一次全量基线对照，3001 浏览器复验策略页和联系人搜索。
