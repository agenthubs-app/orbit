# Sprint W0034 — 排序与联系人搜索运行时白名单覆盖生产组合

## 要实现什么

生产环境是 Vercel 的 Node 24.x 加 Neon 的 PG 16.15。Neon 上 `und-x-icu` 的排序规则版本是 153.14，按推断对应 ICU 67，这是高度可信的复现代理，判定时仍以生产实测元组为准。本 Sprint 要在本机复现这个生产组合，跑通与 W0025 同等的差分测试，再按显式矩阵逐项检查「Unicode 13 之后新增的字符」。全部通过后，才把生产组合加入跟进排序和联系人搜索的运行时白名单。

白名单改为按排序真正依赖的版本判定：

- Node 侧：ICU、Unicode 版本和默认排序 locale；
- PG 侧：主版本、编码和 ICU 排序规则版本。

白名单不再卡 Node 或 PG 的 patch 号。联系人搜索还要把匹配路径（PG 或 JS 回退）绑定进分页游标，保证一段分页不会中途换路径而漏人或重复。检查不通过时，服务端日志记下实际的版本元组。

## 做完能看到什么

- **生产组合通过差分才进白名单。** 进了之后，生产上的这些功能不再因为运行时检查显示「暂时不可用」：「先联系谁」、`/app/tasks` 跟进分页、首页跟进补位、关系任务分页接口、联系人搜索。跟进和联系人两侧分别判定，互不牵连。
- **联系人搜索翻页全程只走一条路径。** 路径变了，旧游标会明确失效，页面提示「分页已失效，请从第一页重新加载」，不会混拼出漏人或重复的结果。做不到这一点时，只要新增字符的转小写结果不一致，联系人生产组合就不加入白名单。
- **白名单以外的组合仍然拒绝，并留下日志。** 页面照旧显示来源不可用。服务端记一条只含版本号的结构化日志，日志出错也不影响拒绝。上线后看 Vercel 日志，就能知道生产实际跑的是什么组合。
- **本机 3001 不受影响。** 本机验收 server（Node 26.10.0 / ICU 78.3 + PG 16.12 / 153.136）继续可用；数据库请求次数和返回字节不增加。

## 怎么验收

- **本机复现生产 PG。** 在 Docker 的 Debian bullseye 里，用 ICU 67 从源码编译 PG 16.15，实测排序规则版本为 153.14，并记录镜像 digest、源码 SHA、实际链接的 ICU 库和架构。
- **在复现的 PG 上跑差分。** 分别用官方 Node 24 二进制（ICU 78.3、78.2）跑跟进排序和联系人搜索的差分测试，0 skip，全部通过。
- **跑探针矩阵。** 对全部码位比较 PG 与 JS 的排序和转小写，把有差异的字符整理成矩阵，每一项都有断言，只打日志不算通过。
- **联系人搜索跑双向切换测试。** 覆盖 PG→JS 和 JS→PG 两个方向，以及每个有差异的字符和每个搜索字段：不能漏，不能重，总数必须等于逐页合计。
- **单测。**
  - 已验证组合在不同 Node patch 号下都放行，其他组合都拒绝。
  - 日志字段固定，同一组合只记一次；日志出错时仍返回原来的错误码。
  - 查询次数不变。
- **查 PG 小版本的 release notes。** 逐一查阅 16.15 之后各小版本的发布说明，记录与 ICU、排序、`lower()` 有关的条目。
- **回归。** 本机组合的定向测试、typecheck、一次全量基线对照；在 3001 上用浏览器复验策略页、跟进和联系人搜索。
