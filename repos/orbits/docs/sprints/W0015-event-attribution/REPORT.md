# Sprint W0015 — 执行总结

## 目标实现情况

- 本轮要实现：活动当天或次日扫的名片，审阅时问「是在 X 活动认识的吗」，确认后记下来源、计划里的活动标「已参加」。
- 已验证能做到：
  - 时间窗口：以名片条目不可变的 `createdAt`（双面名片取 seq 最小的一面）为扫描时间，东京自然日落在已报名活动开始日当天或次日才算；扫描后数日才确认仍按扫描时间判定；多个候选取开始时间最近的一场（同时刻按 eventId）（SC-01）。
  - 候选接口 `GET /api/agent/event-attribution/candidates?batchId=` 只读本人批次与本人报名（他人批次 404）；活动标题与开始时间取自已发布的权威活动目录（SC-01）。
  - 审阅页每张名片只在自己有候选时显示「这张名片是在「X」认识的吗？」，默认勾选、可取消，决定按名片保存；有候选的名片不会被自动导入（审阅页与后台宿主都一样），必须由用户看到询问后确认（SC-01，review 后补）。
  - 确认时服务端按扫描时间与本人 userId 重算候选：非字符串 400，不在候选内 409 `EVENT_ATTRIBUTION_REJECTED`，均不写库；新建联系人写 `metEventId`／`metEventTitle`，OCR `source` 不变；合并到已有联系人只补空值；取消勾选不写（SC-02）。
  - 本人生效计划中对应活动项变为「已参加」，只写一条幂等进展记录（从「推荐」开始也只写一条）；无计划或计划无该活动时只写联系人（SC-03，review 后补一条）。
  - 联系人已提交而计划写入失败时，每日维护任务 `plan-event-attendance`（每次最多 50 条、按 actor 隔离）幂等补写（SC-03，review 后补）。
  - W0010 匹配：与该活动同一计划阶段的人脉需求排在前面，排序在 SQL 的 `LIMIT` 之前完成（SC-04，review 后补）。
- 仍未实现或未验证：
  - **浏览器验证没做**：询问只在「本人报名了某活动且当天／次日扫过名片」时出现，本机账号没有这样的数据；制造它需要写报名和上传名片（会写用户数据、产生 OCR 费用）。
  - 联系人详情页暂不显示「认识于」某活动。
  - `metEventId` 只在 Web 端，未进共享 schema，App 暂不能提交。
  - 完成页的归属摘要只在内存里，刷新后消失。

## 决定与口径

| 问题 | 决定 |
| --- | --- |
| 「与该活动关联的人脉需求」 | 人脉需求不能带 `linkedEventId`，定义为与该活动项同一计划阶段的需求 |
| 活动项只是「推荐」 | 内部经「已报名」推进到「已参加」（服务端已核实报名），只写一条记录 |
| 候选查询失败 | 等待期间暂停自动导入，2 秒后重试一次；仍失败则照常自动导入、不询问（核心入库优先，归属只是不提供） |
| 计划写入失败 | 联系人为主，请求照常成功；每日维护任务对账补写 |

## Codex 代码 review 与处理

第一轮：

| 意见 | 判断 | 处理 |
| --- | --- | --- |
| 自动导入在用户看到询问前写入归属与「已参加」 | 采纳（阻塞） | 有候选的名片不自动导入 |
| 联系人与计划非原子双写，失败后永久不一致 | 采纳（阻塞），不做 outbox | 每日维护任务对账补写 + 故障注入测试 |
| 混合批次回退到第一场活动、全局勾选、摘要错误 | 采纳 | 按名片取候选与保存决定，摘要按回执分组，改为交互测试 |
| 从「推荐」写两条记录 | 采纳 | 只写一条 |
| 活动优先排序在 `LIMIT` 之后 | 采纳 | SQL 内排序后再截取 |

复查（原 5 项均确认解决）：

| 意见 | 判断 | 处理 |
| --- | --- | --- |
| 候选查询失败被当成「无候选」放行自动导入 | 部分采纳 | 区分失败与空结果、重试一次、已配置来源抛错返回 503；不无限期暂停自动导入 |
| 对账会把以后新建计划里的该活动标为已参加 | 不采纳 | 报名与扫描时间在确认时已由服务端核实，「参加过」是事实；W0007 新版本本来就继承「已参加」 |
