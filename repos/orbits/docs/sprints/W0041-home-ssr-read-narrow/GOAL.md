# Sprint W0041 — 首页服务端只读首页要用的那几样东西

## 要实现什么

每次打开 iOrbit 首页 `/app/agent`（以及 `/app/home/events`），服务端都要先组一份「首页数据」。W0040 去掉资料「更新建议」之后，这一步仍会读 58.8 KB（本机 `user_verify_plan`，11 条语句）。原因是它借用了三个完整页面的读法：

- 借联系人页的读法：读回全部联系人卡片、关系和证据，首页却只用两个数字（联系人数、跟进中人数）。
- 借活动页的读法：把整个 workspace 的旧活动表全读回来，再在 Node 里挑出本人的。
- 读「已报名活动」时：先读整个活动目录和带报名资料的报名记录，再挑出本人报了名的。

本 Sprint 让首页只读它真正显示的东西：

- 联系人改成在数据库里直接数出那两个数。
- 旧活动表在数据库里按本人筛选。
- 已报名活动先查本人报了哪几场，再只取那几场。

首页每一块显示都和现在一样。联系人页、活动页和其他用到这些读取的地方，结果不变。

## 为什么要做

- W0040 第一次把首页这笔读取记进数据库月总账：每人每天 4 次 × 30 天 × 1000 人约 7.06 GB／月。加进去后总账是 8.5～9.1 GB，约为 D39 上限 1.6 GB 的 5 倍。
- 要让总账回到 1.6 GB（按无目标用户占 20% 的档、示例期不重复计），首页这一步每次要降到约 **2.6 KB**；按 10% 的档约 **3.1 KB**。计算见 [PLANNER.md](PLANNER.md)「预算目标」。
- 无目标用户占 100% 的档，不算首页就已经超 1.6 GB。那一档靠 D39 记的「服务端共享缓存活动目录」解决，不在本 Sprint。

## 做完能看到什么

- 首页服务端那一步：`user_verify_plan` 从 58,808 B／11 条，预计降到约 2.5 KB／6 条（中心估算 2,530 B），以实测为准。
- 别人的联系人、关系、证据、旧活动、报名记录，以及本人没报名的活动再多，本人首页这一步读到的字节也不变（本人自己的报名与旧活动越多，读得越多，REPORT 给实测敏感度）。
- 首页的账户卡、今日要事里的补人脉提示、活动小模组、已报名栏、月历、`/app/home/events` 的活动与统计数字，改前改后逐项相同。
- 联系人页、活动页、其他读旧活动表的功能（活动接口、计划、AI 助手等），以及示例期和开关关闭时的读取次数，都和现在一样。

## 怎么验收

- **实测**：本机按 W0017 口径（每条语句返回行的 JSON 字节）测三个验收账号改前改后的字节与语句数。在临时 workspace 给其他账号灌噪声数据，本人首页字节不变。
- **对比**：改前改后各跑一遍「首页输出对照表」。包括沿用 W0040 的 33 组 mock 组合，以及本机数据库里覆盖各种边界数据的 live 组合，输出逐字节相同。
- **测试**：新读法与旧读法在同一批数据上结果相同（GitHub Scientist 式「新旧并跑比对」）。其他调用方的既有测试通过。示例期／开关关闭读取次数的测试通过。
- **预算**：REPORT 重算数据库月预算表，写明落在哪一档、差多少。
- **收口**：真实页面桌面 1440、手机 375 各看一次。H 档收口跑一次全量对照和一次 Codex 代码 review。
