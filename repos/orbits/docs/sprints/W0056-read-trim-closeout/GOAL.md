# Sprint W0056 — 读取瘦身收尾：已报名活动按月读取、建议图坏行隔离、建议图只读本人联系人

## 要实现什么

W0040～W0042 收尾时留下的三项一起做完：

1. iOrbit 首页（`/app/agent`）服务端不再读本人**全部历史**报名过的活动。它只读两部分：东京当月 1 日起的已报名活动（含未开始的全部），以及当月之前最近的 2 场。首页上能看到的结果和改前完全一样。
2. 资料「更新建议」不再因为同一 workspace 里**别人**的一行坏数据而让所有人的建议接口出错。别人的坏行不再读取，服务端会记一条不含个人数据的结构化日志，供排查。本人图内的坏行仍和现在一样失败。
3. 资料「更新建议」图的五类数据（资料、关系、联系人、互动记忆、证据）只取**真属主是本人**的行，规则和联系人列表的归属规则一样。别人的联系人即使被本人的关系引用，也不再进入本人的建议图。

## 做完能看到什么

- 首页的已报名栏、月历上的点、时间线、「下一场活动」、活动池去重，都与改前一致。当月已经过去的报名在月历上照常有点；如果本人没有未开始的报名，已报名栏照常显示最近结束的 2 场，即使那两场在上个月或更早。`/app/home/events`（「我的活动」）照常列出全部报名，这一页不加窗口。
- 本人报名历史越长时，首页读取的活动整行不再随之增长；本人报名状态行仍要逐条读取并校验，所以这部分照旧按条数增长（每行约一百多字节）。下面三处读取都实测改前改后，两条增长斜率分开报告，并重算数据库月预算表：首页服务端读取、页面上的报名状态读取、建议图读取。
- 别人往同一 workspace 写入坏数据（payload 是非法 JSON、`null`、数组或数字）后，本人的建议接口和采纳／忽略照常返回，不再报 500。服务端日志里能看到一条带集合名和计数的告警，不含任何记录 id 或用户 id。
- 正常数据下（本机统计：间接引用进入的他人行为 0，非对象 payload 为 0，属主冲突行为 0），建议接口的 JSON 与改前逐项相同。只有三种情况结果会变：引用了他人行；存在他人的坏行；一行的 `user_id` 与 `payload.accountId` 指向不同的人（这种行改后不进任何人的图）。三种变化都用测试锁定。

## 怎么验收

- 首页：对两条读取路径做 mock 和 live 并跑对照。边界数据包括跨月、月初零点、整月没有报名、只有更早的报名、同一开始时间、会话 id 与账号 id 不同、旧活动去重等，用来证明可见结果逐项相同；再用真实页面在 1440 和 375 两个宽度截图对照。
- 建议图：内存 store 路径与 Postgres 读取器用同一份数据并跑，证明两边规则一致。正常数据与 W0042 版本逐项相同；在他人坏行、间接引用两种情况下，只出现约定的变化。
- 按 W0017 口径实测读取的字节与语句数，做噪声对照，并重算 D32 预算表。
