# Sprint W0030 — 认出「你是哪个账号」只取必要的几项

## 要实现什么

已登录用户打开 Orbit 的大多数页面或调用接口时，系统都要先把登录会话认成「哪个账号」。这一步现在每次从数据库拉回两整行记录：一行资料、一行账号。每行里约 60% 是记录自带的管理信息（来源、证据编号、时间戳、工作区等），认账号根本用不到。

本 Sprint 让「认账号」只取判断需要的几项：资料的 id、所属账号 id、显示名，账号的 id，再加上判断这条记录是否有效要用的几个字段。认出来的账号、页面看到的内容、出错时的表现，都和现在一样。

## 为什么要做

W0027 让活动详情页 `/app/events/[id]` 在登录时先认账号，再用账号 id 判断「已报名」「主办方」和私密活动能否打开。实测每次认账号约 1,959–1,984 B。按 1000 人、每人每天打开 2 次详情页算，每月约 118–119 MB 数据库出站，上限是 60 MB（决定 D22）。

认账号这一步有 23 个页面或接口直接调用它（iOrbit 首页、活动页、人脉页、任务页、引导页、通知接口等），2 处通过依赖注入调用，另有 143 个接口文件通过 `resolveAuthenticatedApiActor` 间接用它，其中收件箱会定时轮询。所以改轻以后，全站都会少读数据。本 Sprint 必须在上线清单 W0019 之前完成，执行顺序是 W0028 → W0030 → W0029。

## 做完能看到什么

- 所有已登录页面和接口认出的账号不变：
  - 用资料 id 登录的用户（Auth.js 常见情况）→ 认成它所属的账号；
  - 用账号 id 登录的用户（verify 账号、旧集成）→ 认成这个账号；
  - 没有资料、资料无效或账号不存在 → 认不出来，页面照旧按各自的方式处理（例如详情页显示「暂时不可用」，接口返回 401）。
- 查询次数不增加（每次 2–3 条）。
- 实测字节表：活动详情页每次认账号 ≤1,000 B，每月合计 ≤60 MB；另附一张「全站少读多少」的估算表，列出经过这一步的高频页面和接口；轮询接口先实测每轮实际请求了哪些接口，再逐个接口计算。
- 出错时和现在一样：数据库出错照样报错，不会被当成「没登录」；数据有问题的记录照旧被跳过或报错；读取预算闸门对账号、资料这两类记录照旧放行。
- 账号会话服务（`/app/account` 用的完整会话信息）不变，仍然读完整字段。

## 怎么验收

- **数据库测试（本机测试库）**：在临时 schema 里造出各种账号和资料（正常、按账号 id 登录、无资料、资料字段缺失或只有空白、账号缺失、重复记录、已删除、已归档、别的工作区、时间戳为无穷），对照新旧两种读取认出的账号完全一致；旧读取报错的情况新读取也报错。
- **读取封装测试**：闸门检查的次数和记录类型不变；同时发起的相同读取只查一次数据库；失败不缓存；写入之后不会复用写入前的读取；在真实配置下，新读取的行数和字节照样计入读取预算。
- **回归测试**：认账号相关的现有测试全部通过，页面测试断言不改；报告里逐个列出每个调用入口由哪份测试覆盖，没有专门测试的入口说明为什么由集中等价测试覆盖；审计棘轮里无上限读取的计数不增加。
- **流量实测**：按 W0017 口径（每条语句返回行的 JSON 字节之和）出改前改后对照表和月估算。
- **真实页面**：在 3001 验收 server 上用 verify 账号打开活动详情页、活动页、iOrbit 首页、人脉页，桌面和手机各看一次，控制台无错误。

完整验收项和启动条件见 [PLANNER.md](PLANNER.md)。本页说明预期目标，不代表已实现；当前状态见[登记表](../README.md#sprint-登记表)，实际执行结束后再记录报告。
