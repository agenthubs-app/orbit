# Sprint W0032 — 登录状态检查少读数据库

## 要实现什么

用户登录后，每打开一个页面、每调一次接口（包括收件箱每 15 秒一轮的自动刷新），服务器都要先确认这个登录还有效：账号还在不在，登录之后有没有改过密码。改过密码的话，旧的登录要立刻作废。

这项检查现在每次都从数据库读出这个账号的整条记录，约 850 字节。整条记录里有密码哈希、找回密码的加密信息、来源和证据编号，这些检查时都用不上。而且一个请求往往要检查两三遍：先在请求入口检查一次，页面或接口自己再检查一次。W0031 在生产构建下实测，每个 `/api/account/me` 请求平均读 1.55–1.67 条这样的整行记录，比 W0031 瘦身后的账号读取本身还多。

本 Sprint 做两件事：

1. **先查清楚**：用生产构建实测，每类请求（打开页面、普通接口、收件箱轮询）各检查了几次，每次读多少字节，平均为什么多于 1 次。
2. **只读需要的内容**：检查时只从数据库取判定要用的几项：账号记录是否存在、状态、账号编号、密码修改时间，外加一个「这条记录能不能正常读」的标记。密码哈希、找回密码信息等不再读出来。

## 做完能看到什么

- 安全行为和现在完全一样：改密码（找回密码重设）之后，旧的登录在下一个请求就失效，时机不变；账号不存在、被删除、被归档、账号编号对不上时，登录照旧作废；数据库读不到或数据坏了时，结果也和现在一样。**不加任何跨请求缓存**，不会出现「改了密码，旧登录还能再用几秒」。
- 一张生产构建实测表：打开页面、普通接口、收件箱轮询各检查几次，改前改后每次读多少字节。
- 每次检查从数据库读的字节降到改前的 30% 以下（约 850 B 降到 150–250 B，以实测为准）。
- 一张月流量表：按 1000 人每天使用，改前、改后每月多少，单位用十进制（1 GB＝1,000 MB）。同时给「单台服务器实测」和「多台服务器、不合并查询时的上限」两个数，按用户定的上限判定。

## 怎么验收

- **数据库测试（本机测试库）**：同一份数据分别用旧读取和新读取，得到的判定完全相同，覆盖的情形包括：正常、改过密码（改前登录与改后登录）、密码修改时间格式不对、账号编号不符、账号被删除或归档、记录不存在、别的工作区，以及时间字段坏掉、记录内容不是对象这类坏数据。另走一遍真实的「找回密码 → 重设」流程：重设前旧登录有效，重设后第一次检查即失效。
- **读取规则不变**：读取预算闸门、同时发起的相同读取只查一次、读取失败不记住、流量计量，都和现在一样；新读取返回的内容里没有密码哈希和找回密码信息。
- **生产构建实测**：改前、改后各用一个独立的构建目录和空闲端口（如 3012、3013）跑生产构建，按 W0031 的操作规程只关自己启动的进程、只删自己的构建目录，不碰 3000、3001 和它们的构建目录。
- **真实页面**：在 3001 验收 server 上用验收账号正常浏览页面和收件箱，桌面和手机各看一次，控制台无错误；再用脚本把该验收账号的密码修改时间改到现在，确认原来的登录在下一个请求就被要求重新登录，最后把账号恢复原状。
