- **P1｜`PLANNER.md:39、130、151、194`；`GOAL.md`“下一个请求即失效”**：方案承认密码重设 `consume` 使用原生 SQL，不会驱逐正在进行的 session-revocation 去重读取，因此“重设提交后的第一次调用必为 false”并不成立：若旧读取在提交前启动，提交后的请求仍可能复用旧结果。当前 SC 只测顺序执行，无法覆盖该竞态。建议二选一：把 `consume` 接入同一去重驱逐机制，并增加“旧读取 pending → consume 提交 → 新检查不得复用旧结果”的可控竞态测试；或者明确由用户接受现存窗口，并删除“下一请求立即失效/第一次调用即 false”的绝对承诺。

- **P1｜`PLANNER.md:55–61、150–152`**：`readable !== true` 后再调用 `store.getRecord` 并不与旧读取完全等价。一次逻辑检查会先经过 `customRead` 闸门，再经过 `getRecord` 闸门，与 SC-03“每次逻辑调用 assertAllowed 1 次”冲突；第二次闸门还可能拒绝，使原本会由 `rowToRecord` 返回或抛出特定错误的坏数据变成预算拒绝。此外，两条 SQL 之间发生写入时会读取两个不同快照。建议改成单条 SQL：正常行只返回轻量投影，不可读行条件性携带完整兼容字段，并在同一查询结果上执行 `rowToRecord`；至少也应让兼容读取留在同一次 `customRead`/同一次闸门内，并补闸门临界值与两阶段写入竞态测试。

- **P1｜`PLANNER.md:32、144、151–154、189、193`**：W32-5 要求保持“读失败或闸门拒绝即清 cookie/登出”，但验收只证明 `isPasswordSessionCurrent` reject，没有可执行 SC 证明 Auth.js 最终清 cookie、页面按未登录跳转、API 返回 401。该关键安全失败语义目前仅依赖对 `node_modules` 的静态判断，升级或接线变化都可能漏检。建议增加生产依赖版本下的 Auth.js session 集成测试，分别注入 SQL 错误和闸门拒绝，断言响应清除 session cookie，并验证后续页面/API 未认证。

- **P2｜`PLANNER.md:37、75、150`**：对“每请求为何平均只有 1.55–1.67 条”的实测归因仍不够可判定。`sql-tap.cjs` 把共享 SQL 只归给真正发出查询的请求，串行探针只能证明无并发时的次数，不能直接证明真实场景中的缺口来自跨请求 in-flight 去重。建议为每个逻辑检查记录 request/call ID、去重 key 及“leader/shared”状态，或增加受控的双请求并发实验；报告同时列逻辑调用数、leader SQL 数和共享命中数。

- **P2｜`PLANNER.md:83–103、150、153`**：流量表的编制基线只统计“已知部分”，页面内其他 API、RSC 导航仍是待测，却已给出约 1.5–2.5 GB/月并设置 2.0 GB 硬上限；当前数字不能作为可靠容量预测。建议 SC-01 明确每个日常页面场景的完整网络请求清单及 RSC 导航复现方式，并要求 SC-04 对未观测项给出显式上界或敏感性区间，不能以“待实测”计为零。
